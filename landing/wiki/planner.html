계획

마지막 수정 2026-10-29

이 페이지에서계획 한 편의 모양글리프 여섯 개완료 조건 · 확인 명령 · 마지막 판정변경 로그 — 누가 언제 왜 바꿨나결정 잠그기상태와 잠금계획 화면(`⌘3`)새 계획은 누가 만드나다음 걸음

일지가 지나간 일이라면 계획은 지금의 계획입니다. 다른 점이 하나 있습니다 — 사람이 관리하는 할 일 목록이 아니라, 에이전트가 일을 마칠 때마다 갱신하는 문서입니다(plan_create · plan_update).

파일은 .oculpm/planner/*.md, 역시 평범한 마크다운입니다.

계획 한 편의 모양

---
oculpm_plan: v1
id: session-attribution
title: "세션 귀속 정리"
status: active
owner: claude-code
---

**완료 조건:** 세션 없이 쓴 일지도 작성 시각으로 귀속되고, 그다음 오늘 화면이 대화별로 셀 수 있다
**확인 명령:** `cargo test --test session_verdict`

## Phase 기반 다지기 {#foundation}
- [x] 타임스탬프 귀속 함수 {#resolve-by-time}
- [~] MCP 도구가 라이브 세션을 채택 {#mcp-adopt}
  - [x] sessions.json 동기 읽기 {#sync-read}
  - [ ] 폴백 경로 테스트 {#fallback-test}
- [ ] 링크 파생 {#derive-links}
  • Phase 는 ## 헤딩으로 묶는 단계입니다. 글리프가 없습니다 — 진척은 하위 항목에서 자동 계산됩니다
  • 항목은 한 줄, 끝에 {#안정적인-id} 가 붙습니다
  • 중첩은 한 단계까지. 하위가 있는 부모의 글리프는 하위에서 굴러 올라오므로 직접 건드리지 않습니다

글리프 여섯 개

글리프뜻
[ ]할 일
[~]진행중
[x]완료
[!]막힘
[>]이월
[-]폐기

지금 상태의 정답은 본문 글리프입니다. 아래의 변경 로그는 이력이고요. /oculpm:next 는 항목을 잡자마자 [~] 로 먼저 바꿔, 병렬로 도는 다른 세션이 같은 항목을 잡지 않게 합니다.

완료 조건 · 확인 명령 · 마지막 판정

항목이 다 닫혔다는 것과 목표가 이뤄졌다는 것은 다른 주장입니다. 그래서 계획 머리에 두 줄이 섭니다.

  • 완료 조건 — 할 일이 아니라 결과: 무엇이 참이 되면 끝인가, 그다음 무엇이 일어나야 하나
  • 확인 명령 — 돌리면 통과/실패가 나오는 명령. 에이전트가 정하지 못하면 그것부터 만듭니다

확인 명령을 돌린 결과는 변경 로그의 메모 칸에 한 줄로 남깁니다:

판정 ✓ 418 passed · exit 0
판정 ✗ 2 failed, 418 passed
verdict ✓ …        (영어 템플릿 — 소문자, 공백 하나, 콜론 없음)

이 줄의 가장 최근 것이 그 계획의 마지막 판정입니다. 플러그인의 시작 훅과 앱의 계획 화면이 같은 규칙(^(판정|verdict) (✓|✗))으로 읽으므로, 다음 세션의 에이전트와 사람이 같은 판정을 봅니다. 「판정:」 처럼 콜론이 붙은 평범한 메모는 판정이 아닙니다. 항목이 다 닫혀도 판정이 통과해야 끝입니다 — 판정이 실패면 오늘 화면 「먼저 볼 것」 맨 위에 섭니다.

변경 로그 — 누가 언제 왜 바꿨나

계획 문서 맨 아래에는 표가 하나 붙습니다. 에이전트는 항목을 옮길 때마다 여기에 한 줄을 덧붙이기만 합니다 (기존 행은 절대 고치지 않습니다):

| 시각 | #항목id | 에이전트 | 이전→새 글리프 | 일지 경로 | 짧은 메모 |

일지 경로가 함께 적히므로 계획의 한 줄에서 그 일을 설명하는 일지로 바로 건너갈 수 있습니다. 계획에 일지 내용을 복사해 넣지 않는 것이 규칙입니다 — 참조만 합니다.

팁

"이 항목이 왜 폐기됐지?" 가 궁금할 때, 로그의 그 줄에 달린 일지를 열면 당시 판단이 그대로 남아 있습니다.

결정 잠그기

되돌리기 어려운 선택은 ## 결정 섹션에 블록으로 못 박습니다:

### Decision 3 — SQLite 캐시를 파생으로 유지 {#dec-cache-derived}
잠금: 2026-08-21 · claude-code
근거: 디스크 마크다운이 SSOT. 캐시를 정본으로 삼으면 …
영향: #resolve-by-time, #derive-links

나중에 "왜 이렇게 했더라" 를 다시 논쟁하지 않기 위한 장치입니다. 4.0 에서 논의 화면을 걷은 뒤로 큰 결정과 옵션 비교는 이 블록이 맡습니다.

상태와 잠금

계획 문서 자체도 상태를 가집니다.

status뜻에이전트가 고칠 수 있나
active진행 중예
done끝남아니오
archived보관아니오

done 이나 archived 인 계획은 에이전트가 수정하지 않습니다. 끝난 계획이 슬금슬금 되살아나 이력이 흐려지는 것을 막기 위해서고, 이어서 할 일이 생기면 새 계획을 만듭니다. 계획 화면의 레일에서는 「끝난 계획 N」 한 줄로 접힙니다.

계획 화면(⌘3)

  • 레일 — 진행 중 계획마다 진척 막대 · 판정(✓ / ✗ / 없음) · 갱신 시각, 최근 갱신 먼저
  • 판정 카드 — 제목 바로 아래 완료 조건 · 확인 명령 · 마지막 판정(결과 끝 줄). 아직 없으면 「아직 안 돌렸어요」
  • 다음 할 일 — 첫 미완 항목(사람 몫은 건너뜀)과 [터미널에서 실행] · [끝까지 (/goal)]. 앞의 것은 앱 안 터미널의 새 세션에서 claude 가 그 항목을 잡게 하고, 뒤의 것은 계획의 완료 조건 · 확인 명령을 Claude Code 의 /goal 로 넘겨 조건이 참이 될 때까지 이어 가게 합니다. 항목마다 「Claude 에게 보내기」 도 있습니다
  • 항목 상태 — 상자를 눌러 여섯 상태 중 고릅니다. 검증 일지 없이 완료로 바꾸면 한 번 묻습니다
  • 「갱신 기록 N줄 · 결정 M」 은 접혀 있습니다

새 계획은 누가 만드나

4.0 에서 계획은 에이전트가 씁니다 — 앱 화면에서 계획을 만들거나 항목을 더하는 버튼은 없습니다. 새 기능 영역이라면 터미널에서 /oculpm:inception 이 「그다음 무엇이 일어나야 하나」 와 깊이 네 질문을 거쳐, 첫 항목이 지금 빨간 확인 명령인 계획을 plan_create 로 만듭니다. 직접 만들어도 됩니다 — 위의 머리말 + 완료 조건 · 확인 명령 + Phase 헤딩 + 항목 줄 순서면 앱이 읽습니다.

주의

항목 줄을 쓸 때 {#id} 는 반드시 줄 끝에 두고 줄바꿈하지 마세요. 둘째 줄로 넘어간 {#id} 는 파서가 읽지 못합니다.
