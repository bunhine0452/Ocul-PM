프로젝트 시작부터 구현 루프까지

기능 추가는 /oculpm:inception(계획만 확장) 또는 바로 /oculpm:next 부터 — 인셉션의 질문·리서치는 낯선 영역일 때만 처음부터 다시 돕니다.

→ /oculpm:inception → /oculpm:next until-done (판정이 통과할 때까지)

슬래시 커맨드 4종

타이핑 한 줄로 부르는 것.

/oculpm:inception새 프로젝트/기능 영역의 시작

어떻게 시작하든 결과가 좋도록 순서를 잡습니다: 「이게 되면 그다음 무엇이 일어나야 하나」로 결과를 정하고 → 깊이 네 질문(최고의 전문가라면 무엇을 더 하나 · 어떤 날것의 재료에서 · 어떤 도구로 · 나나 모델이 아닌 무엇이 맞다고 보여 주나) → 목표를 동사로 바꿔 닿는 분야의 방법 둘~셋(역할극이 아니라 그 전문가가 하는 조사) → 어려운 숫자 목표 한 줄 → plan_create. 계획의 첫 항목은 확인 명령을 만들어 지금 실패(빨강)함을 보이는 것입니다. 스택을 골라야 하면 기억이 아니라 웹 검색으로 버전·출처를 붙여 추천합니다. 질문은 한 번에 지금 답해야 할 것만, 추천 답과 함께. 아이디어를 인자로 줄 수 있습니다: /oculpm:inception 할 일 앱을 만들고 싶어

/oculpm:next구현 루프 — 반복 실행

활성 플랜의 다음 미완 리프를 먼저 진행중([~])으로 잡고 — 병렬 세션이 같은 항목을 잡지 않습니다 — 구현 → 확인 명령 → 일지 → 플랜 갱신 한 사이클을 돕니다. 확인 명령의 결과는 플랜 로그에 판정 ✓/판정 ✗ 로 남아 다음 세션의 시작 훅이 「마지막 판정」으로 싣습니다. /oculpm:next until-done 이면 판정이 통과하거나, 막히거나, 사용자 결정이 필요하거나, 바꿀 접근이 없을 때까지 리프를 이어 잡습니다. 앱 플래너의 ▶실행과 같은 역할의 플러그인 대응물입니다. 특정 항목을 지정하려면: /oculpm:next login-happy-path

/oculpm:redteam합류·릴리스 직전, 「뭐가 틀렸지」

플랜·일지의 주장을 원재료(테스트·로그·diff)와 대조하고 직접 돌려 반례·검증 불가·유지된 주장으로 나눠 보고합니다. 숏셀러처럼 쓰는 게 아니라 숏셀러가 하는 일을 합니다 — 자기 판단은 증거가 아닙니다. 고치지는 않습니다.

/oculpm:help뭐가 있는지 잊었을 때

플러그인 표면 전체(커맨드 4 · MCP 도구 7 · 스킬 1 · 훅)를 레퍼런스 카드 한 장으로 보여주고, 지금 상황에 맞는 다음 한 걸음을 추천합니다.

MCP 도구 7종

에이전트가 마크다운 규격을 흉내 내는 대신 도구로 기록하고, 쌓인 기록을 도구로 되찾습니다 — 경로·frontmatter·항목 id 규격은 서버가 보장합니다. 모든 도구는 .oculpm/ 이 있는 추적 프로젝트에서만 동작합니다 (유일한 예외: project_init).

도구하는 일
journal_search과거 일지 검색 — 질의(제목·본문·태그)에 더해 그 파일을 건드린 일지·종류·상태·기간·태그로 좁힘. 본문 전문 대신 압축 히트 목록을 돌려주고, 관련도순(제목>태그>슬러그>경로>본문 가중치 + 최신성 소량 가산)으로 정렬 — 오래된 일지도 강하게 걸리면 위로 온다. 앱이 켜져 있으면 SQLite 캐시를, 아니면 디스크를 읽는다(응답의 source). 작업 시작 전 호출이 규칙.
journal_read검색이 고른 일지 1건의 본문 전체. 목록을 훑는 용도가 아니라, 읽을 값어치가 있다고 판단한 뒤에만.
journal_write작업 단위(버그/기능/리팩토링/에러/잡일) 하나가 끝날 때마다 일지 1건을 규격대로 기록. 과거 일지와의 related 링크와 session_id 를 받고, 본문의 시크릿은 마스킹한 뒤 응답으로 알림. 같은 파일을 만진 지난 결함이 있으면 followup 으로 자동 연결(auto_related), 태그는 정규화하고 기존 어휘와 비슷하면 tag_hints 로 제안.
plan_status활성 플랜의 항목·상태를 조회 — 「지금 어디까지 됐나」의 근거. 플랜마다 현재 파일 hash 가 함께 오고, 그것이 plan_update 의 base_hash 재료입니다.
plan_update플랜 항목의 상태를 갱신하고 plan-log 를 남김. 하위를 가진 부모는 롤업 자동이라 직접 갱신 거부. 확인 명령을 돌렸으면 메모를 판정 ✓ <결과 끝 줄> / 판정 ✗ … 로 — 시작 훅이 「마지막 판정」으로 싣습니다. base_hash 필수 — plan_status 로 읽은 해시와 디스크가 어긋나면 덮어쓰지 않고 현재 해시를 담아 거절합니다. 병렬 세션이 같은 플랜을 고칠 때 한쪽 변경이 조용히 사라지던 자리입니다.
plan_create새 계획을 3-depth(마일스톤→작업→하위 작업)로 생성 — frontmatter·id 규격 서버 보장. done_when(완료 조건)과 check(그것을 통과/실패로 판정하는 명령)을 받아 본문 첫 줄에 두고, 시작 훅이 항목보다 먼저 싣습니다. 제목·id 가 겹치는 활성 계획이 있으면 만들지 않고 그 후보를 돌려줘 재사용을 권합니다(allow_similar 로 통과). check 를 생략하면 매니페스트(package.json · Cargo.toml · pyproject · go.mod · Makefile)에서 확인 명령을 감지해 적고 warnings 로 알립니다 — 틀리면 그 줄을 고치세요.
project_init미추적 저장소의 추적 시작 — 사용자의 명시적 요청·확인(confirm)이 있을 때만. 심볼릭 링크 거부·홈 디렉터리 가드.

동봉 스킬 1종

상황에 맞게 스스로 발동하는 방법론입니다. 플러그인을 설치하면 함께 들어오고, 앱의 스킬·규칙 화면에서 개별 설치도 됩니다. 앱에서 열기는 oculpm:// 딥링크라 앱이 확인 창을 띄우는 데까지만 하고, 승인 전에는 아무것도 바뀌지 않습니다.

스킬 샵 카탈로그 26종

앱의 스킬·규칙 → 샵 탭은 프로젝트의 매니페스트(package.json·Cargo.toml·pyproject.toml 등)로 스택을 감지해 아래 카탈로그에서 맞는 스킬을 추천합니다. 전부 MIT 제3자 스킬(ECC · ponytail · i-have-adhd)의 커밋 고정 사본입니다 — 원문 무수정, 런타임 네트워크 0(설치 시점에 아무것도 받지 않습니다). 설치하면 .claude/skills/ 에 들어가며 이는 Claude Code 네이티브 기능이라 플러그인 없이도 동작합니다. 하나는 스택이 아니라 출력 형태를 바꿉니다 — i-have-adhd 는 매니페스트에 걸리지 않으므로 추천이 아니라 검색으로 찾고, 사람이 이름을 쳐야만 뜹니다.
