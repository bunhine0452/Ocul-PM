Five principles for getting the best out of an agent

How to use agents well is known.
The problem is forgetting it every session.

Anthropic's Claude Code guide, Simon Willison's agentic engineering patterns, Sonar's 2026 developer survey and METR's productivity measurements all say the same five lines. And all five vanish on /clear. Ocul-PM is the place where those five questions survive the session boundary — Rieseberg's altitude, depth and range, as is.

① A done condition before code

Write the goal behind the goal

"Write the spec first, then build from it" — Anthropic. Every plan carries one done condition, and the session-start hook ships it before the items. The agent starts from an outcome, not a to-do list.

② Something that passes or fails

Give it a check command

"Give Claude something it can run that comes back pass or fail" — Anthropic. The plan's check command result is logged as verdict ✓|✗ <last line>, and the start hook and the Plan screen read the last verdict by the same rule. All items closed is not done until it passes.

③ Output, not claims

Entries without evidence come first

"'All tests pass' on its own tells you very little" — Anthropic. An entry whose verification section lacks the command and its last result line lands in Today's "To check", and the entry detail calls it a claim.

④ Green is not running

The verdict comes from something that isn't you

"Just because the test suite passes doesn't mean the server will boot" — Willison. Rules template v20 says: with no check command, make one first, and even when green, launch it and use it once if you can. Failures get an error entry too.

⑤ An outside judge

Red team and a daily line

96% of developers don't trust AI code, yet only 48% always check it (Sonar 2026). /oculpm:redteam hunts counter-examples before a merge, and the line at the top of Today shows the share of entries with outside-judge evidence every day — the target is a number, 97% (METR: feeling ≠ measurement).

What it can't give

Ambition itself

Asking the bigger question is the human's job. Ocul-PM doesn't write the done condition for you and doesn't hand down the verdict — it asks and points, never blocks. Past that line the model would be judging itself.

What's left is solid
because of what we took out.

Last verdict

What did the judge say?

A check command's result as one line, verdict ✓|✗ <last line>. The start hook and the Plan screen read it by the same rule, so the next session and you see the same verdict.

/oculpm:inception

Lay the verdict down first

"What should happen next" → four depth questions → the field's methods → a hard numeric goal → a plan whose first item is a check command that is red right now.

/oculpm:next

Claim it, finish it

It claims the item as [~] first, so parallel sessions don't grab the same work. With until-done it keeps going until the verdict passes.

Unrecorded changes

It points at files nobody wrote down

Files no entry mentions sit at the top of Diff. [Copy record request] turns that list into text to paste to your agent.

One window = one project

OS windows instead of tabs

⌘O recent projects, ⇧⌘N new window, ⌘W close window. Pick a project that's already open and its window comes forward.

⌘K · ⌘1–4

Command palette

Find screens · projects · entries · plans by title and open them. Today is finished from the keyboard — j/k · v · c.

Zero LLM

The agent does the thinking

In-app summaries · rollups · AI refresh · API keys are gone. The app shows the evidence, deterministically, and its screens reach no outside host.

/plugin, two lines

Claude Code plugin

You can start without the app — a hook bridge, 7 MCP tools and four commands install in two lines.

What a review means

Changed after review? It asks again

A verified mark is stored with the body's fingerprint. If an agent edits the entry later it stops counting as verified; read it again, click again, and it binds to the current text.

FAQ

Frequently asked

Who is this for?

People who build with an AI coding agent every day and are tired of re-explaining yesterday's context to a fresh conversation. When Claude Code finishes a unit of work a journal entry is left behind, and the next conversation receives those entries and the remaining plan as its starting context — that is the one round trip above. If you only use an agent now and then, you may not need this round trip — and that's fine: the app is free and the data is markdown in your project folder, so you can stop at any time.

How does the next session pick up where the last one stopped?

The Claude Code plugin's SessionStart hook carries the recent plans' done condition · check command · last verdict · open items and the last three journal entries into the session-start context — no network, reading only the project's .oculpm/. In the app, the Plan screen's [Copy prompt] (c on Today) puts a prompt that picks up the next item on your clipboard, and [Copy with until-done] one that keeps going until the verdict passes, ready to paste into the agent in your terminal.

What is the "last verdict"?

The result of actually running a plan's check command. When the agent logs it as one line in a plan-log note — verdict ✓ 418 passed or verdict ✗ 2 failed (판정 in Korean) — the plugin's start hook and the app's Plan screen read it by the same rule (^(판정|verdict) (✓|✗)). The Plan screen puts done condition · check command · last verdict right under the title, and a failed verdict goes to the top of Today's "To check". All items closed is not done until the verdict passes — "done" is decided by the last line of output, not by the agent's word.

With 60 entries a day, doesn't Today overflow?

No. The 4.0 principle is "show only the exceptions". Today unfolds only what a person must see — failed verdicts · entries without command evidence · changes no entry mentions · blocked items · decisions that are yours · a new plugin version — and folds work whose evidence is complete into one line per plan. Someone with 3 entries a day and someone with 60 use the same screen, with no modes; that is why the 3.x simple/pro density toggle is gone.

Will macOS warn me when I install it?

Not since v2.45.0. Builds are signed with an Apple Developer ID and notarized, so you open the .dmg, drag it into Applications and launch it. Earlier versions were unsigned, so macOS refused them with "is damaged and can't be opened" — not real damage, just the quarantine flag macOS puts on downloaded files — and you had to run xattr -dr com.apple.quarantine yourself.

What is Ocul-PM?

A local-first AI project manager for developers who work with AI coding agents. It gets a person to trust what the agent did, and decide what's next, in three minutes — and gets the agent to lay down a verdict first, whatever it starts. Of the journals, diffs and plans the agent leaves, it unfolds only what a person must see, and it reads the verdict from a check command's last line of output, not from the agent's word. The app calls no LLM.

Which AI coding agents does it work with?

"Supported" hides three different promises, so we split them into tiers. ① Rules-compatible — we only plant a rules file, and journals get written as far as the model obeys it: Gemini CLI · Cursor · GitHub Copilot · Windsurf · Cline · aider · Zed · Antigravity · pi (anything that reads AGENTS.md lands here). ② Structured journaling — the agent calls the oculpm MCP journaling tools. ③ Session observation — hooks deliver start/stop and conversations that ended without a journal are flagged: Claude Code · Codex (each through its plugin, ② included). Agents run in your own terminal; the in-app tier went with its screens on 2026-10-28. Per-agent evidence and when each tier was last verified are in the wiki tier table.

What leaves my machine?

Two things. ① The update check — one GitHub release file on launch and when you check manually; the destination is fixed in the app's configuration and the signature is verified. ② Links you click — the app doesn't send them; your OS default browser opens them. The 4.0 app calls no LLM (it doesn't even take an API key), its screens (the webview) reach no outside host, and it downloads no embedding model. Never leaves: journals · plans · everything under .oculpm/ · your source code. No usage statistics, no crash reporting — there is no analytics SDK in the app. A test in the repository keeps this list honest in the build; the full list, and how to count it yourself, is on the privacy page.

What happens if an agent edits a journal entry after I verified it?

Since v3.2.0 the verified mark is stored with a fingerprint of the body you verified. If the body changes afterwards it stops counting as verified, and an entry without command evidence goes back into Today's "To check". Read it again and mark it checked to bind the mark to the current content. Entries verified before 3.2.0 have no fingerprint and are honoured as-is — nothing is retroactively unverified. The fingerprint lives in the entry's front matter (verified_hash) under .oculpm/, so it is readable without the app.

If the app never calls an AI, how do I get summaries or reports?

Ask the agent in your terminal. 4.0 removed every in-app LLM call (summaries · standups · weekly rollups · release-note drafts · plan AI refresh) — even the most-used repository had zero weekly rollups. The agent does the thinking; the app shows the evidence, deterministically. The agent can find and read past entries with the MCP tools journal_search · journal_read, and the app builds prompts to paste to it (next item · until-done · record request) on your clipboard.

Where did the 3.x Search, Discussions, Branch and Skills screens go?

4.0 removed them; the app is down to five surfaces — Today · Work Journal · Plan · Diff · Settings. The reasons are measured: the semantic-search index was 358MB of an 837MB database (agents have their own grep), discussion documents numbered 18 across 12 projects, and automation never ran once. Journal search lives in Work Journal (/), big decisions go in a plan's decision block, and skills live in the plugin. Your .oculpm/ files (discussion documents included) are never deleted. The first launch after updating drops the old index tables, keeping an ocul-pm.db.bak-v42 copy first. The full table is in the repository's docs/PROMISE.md.

What happens when the network drops?

It keeps working. The 4.0 app needs no network to draw its screens — journals, plans and diffs are read from the project folder and the local cache, and the app calls no LLM. The only thing that fails while you're offline is the update check, and the automatic check at launch passes quietly.

Can I change the theme colors?

Settings → Display picks light · dark · system (follows the OS) and the text size. The 3.x theme files, five preset palettes and per-project themes were removed in 4.0 — a saved old theme setting is read as "system".

Can I tell my own journal entries apart from the ones AI wrote?

Yes. Every record carries a provenance badge — by hand (a person writing in the app) · by agent (Claude Code and friends following the journaling rules) · MCP · backfill (restored from git history) and so on; 3.x auto-draft, schedule, watcher and imported entries still read with their badge. No new field was invented: it is read deterministically from the session id and agent id already written in the entry file.

Can I open several projects at once?

Yes, in several windows. Since 4.0 one window is one project — the 3.x Chrome-style tabs and tear-off are gone, and your OS switches between project windows. ⌘O opens a recent project (if it's already open, its window comes forward), ⇧⌘N opens a new start window, ⌘W closes the window. Each project remembers its own screen and filters, and on macOS closing the last window keeps the app alive — a Dock click reopens one.

The app is desktop-only. The mobile beta added in v2.18.0 (a phone browser inside your Tailscale network) has been removed — its surface was large for how much it was used. The v3.13.0 claude.ai board skill (/oculpm:board) went on 2026-10-28 too. To follow progress away from your Mac, read the plan files in .oculpm/planner/ wherever your repository is — the markdown is always the source.

Does the app notice when an agent finishes without writing an entry?

Yes. A plugin hook judges each conversation as it ends, and if code changed with no entry it blocks the turn once and asks for the record (once per conversation). From v2.43.0 that verdict is per conversation. It used to be a single number — the newest journal timestamp anywhere in the project — so with several terminals open a neighbour's entry hid your own miss, and a neighbour's edits were read as yours. Counting the record showed the 164 signals were session segments, not sessions, and of 117 unique conversations only 2 had genuinely skipped. Now, with no grounds it says "undecided" rather than folding not-knowing into not-recorded. One deliberate trade-off: while several conversations are alive at once the gate stays silent — rather than accuse the wrong one when attribution is not certain, it says nothing, and still records "undecided" in the ledger. On the app side, Today flags conversations that ended without an entry and changes no entry mentions under "To check".

Does my code or data leave the machine?

No. Everything lives in your project's .oculpm/ folder and a local SQLite cache. The app calls no LLM and its screens reach no outside host. Only two things leave, and you start both: the update check, and links you click (your OS browser opens them).
