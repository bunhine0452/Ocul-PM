Commands · tools · skills — the whole surface

From project kickoff to the implementation loop

For a new feature, start with /oculpm:inception (planning only) or go straight to /oculpm:next — inception's questions and research are worth a full lap only in unfamiliar territory.

→ /oculpm:inception → /oculpm:next until-done (until the check passes)

4 slash commands

Things you call with one typed line.

/oculpm:inceptionStarting a new project or feature area

Puts the start in an order that gets the best result however you begin: settle the outcome with "once this works, what should happen next?" → four depth questions (what would the best expert do that you didn't ask for · which rawest material to start from · which tools · what — not you, not the model — shows the result is right) → turn the goal into a verb and borrow the methods of two or three fields that reach it (the investigation that expert does, not a role-play) → one hard numeric target → plan_create. The plan's first item builds the check command and shows it failing (red) now. If a stack has to be chosen, it recommends from a web search with versions and sources, not from memory. It asks only what has to be answered next, each question with a recommended answer. You can pass an idea as an argument: /oculpm:inception I want to build a to-do app

/oculpm:nextThe implementation loop — run it repeatedly

Picks up the next unfinished leaf on the active plan, marks it in progress ([~]) first so a parallel session won't take it too, and drives one cycle: implement → run the check → journal → update the plan. The check's result goes into the plan log as verdict ✓/verdict ✗, and the next session's start hook ships it as the plan's last verdict. With /oculpm:next until-done it keeps taking leaves until the check passes, something blocks it, a decision needs you, or no approach is left to try. It's the plugin's counterpart to the app planner's ▶ Run. To target a specific item: /oculpm:next login-happy-path

/oculpm:redteamBefore merging or shipping — "what's wrong here?"

Checks the claims in a plan or entry against the raw material (tests, logs, diffs), runs them, and reports counter-examples, unverifiable claims and claims that held. It does what a short seller does rather than writing like one — your own judgment is not evidence. It never edits.

/oculpm:helpWhen you've forgotten what's there

Shows the entire plugin surface (4 commands · 8 MCP tools · 1 skill · hooks) as one reference card, and recommends the next step for where you are now.

8 MCP tools

Agents record through tools instead of imitating the markdown spec by hand, and pull the accumulated record back through tools — paths, frontmatter and item ids are guaranteed by the server. Every tool works only in a tracked project with .oculpm/ (the sole exception: project_init).

ToolWhat it does
journal_searchSearch past journal entries — narrow by query (title, body, tags) plus entries that touched a given file, type, status, date range, tags. Returns a compact hit list instead of full bodies, sorted by relevance (title > tags > slug > path > body weights plus a small recency bonus) — an old entry still comes first when it matches strongly. Reads the SQLite cache when the app is running, the disk otherwise (see source in the response). The rule is: call it before starting work.
journal_readThe full body of one journal entry the search picked out. Not for skimming a list — only after deciding it's worth reading.
journal_writeRecords one journal entry to spec every time a unit of work (bug/feature/refactor/error/chore) finishes. Takes a related link to past entries and a session_id; secrets in the body are masked and the response says so. A bug/error entry touching the same files as an earlier defect is linked automatically as followup (auto_related); tags are normalized and near-duplicates of existing vocabulary come back as tag_hints. The title is area: what changed, one sentence within 40 characters — anything else is refused with how to fix it and the areas this project already uses (the area can also come as the area argument, and is kept as the first tag).
plan_statusReads items and status on the active plan — the evidence for "how far are we." Each plan comes back with its current file hash, which becomes the base_hash for plan_update.
plan_updateUpdates a plan item's status and logs it. A parent with children rolls up automatically, so a direct update is refused. After running the check command, start the note with verdict ✓ <last result line> / verdict ✗ … — the start hook ships it as the plan's last verdict. base_hash is required — if it doesn't match the disk, the write is refused, never silently overwritten, with the current hash attached instead. This is the spot where one parallel session's change used to vanish silently under another's.
plan_createCreates a new plan at 3 depths (milestone → task → subtask) — frontmatter and id spec guaranteed by the server. Takes done_when (the done condition) and check (the command that passes or fails it), writes them as the first lines of the body, and the session-start hook ships them before the items. If an active plan with an overlapping title or id already exists it refuses and returns that candidate, nudging reuse (allow_similar overrides). If check is omitted, the server infers one from the project manifests (package.json · Cargo.toml · pyproject · go.mod · Makefile), writes it and says so in warnings — fix the line if it guessed wrong.
project_initStarts tracking on an untracked repository — only on the user's explicit request and confirmation. Rejects symlinks and guards against the home directory.
ask_userWhen a decision needs a person who may not be watching the terminal — puts the question (and up to 6 answers to pick from) on the Ocul app's Today screen, waits, and returns the answer as is. With no answer in 25 minutes it withdraws the question and returns answer: null — ask in the terminal then. Not for trivial confirmations.

1 bundled skill

Methodologies that fire on their own when the situation calls for them. They arrive with the plugin install. (The 3.x Skills & Rules screen in the app and its per-skill install deep links were removed in 4.0 — skills live in the plugin.)

oculpm-journal v2.36.0The full-spec carrier for the recording spec

Loads when the fine detail of journal/plan rules is needed — the full text of folder conventions, frontmatter fields, section order and related-link rules.

SKILL.md ↗

The safety contract — what it reads, writes and never does — is pinned in the repository's plugin contract document, alongside tests. The hook is one local append with no network, and .oculpm/hooks/, which holds the conversation log, is blocked from commits by a gitignore-managed block. There's one more gate here — a delivery gate: if code changed and the session is about to end with no journal entry, it instructs the agent to write one, once per session (grounded in an internal benchmark that measured 0% headless-session recording compliance from rule injection alone).
