# /oculpm:inception — 아이디어를 설계 산출물로

`$ARGUMENTS` 가 있으면 그것을 아이디어로 삼는다 (없으면 무엇을 만들지 먼저 묻는다). 아이디어를 ocul-pm 파일 체계에 **그대로 물리는** 세 산출물(논의 문서 · 플랜 · 초기 규칙)로 바꾼다. 성공 기준은 문서를 "만드는 것"이 아니라 **기존 도구가 무수정으로 소비하는 것**이다 (논의 → 플래너 승격, 플랜 → `/oculpm:next`, 규칙 → 에이전트 자동 로드).

## STAGE 0 — 문제 파악 (리서치 방향을 정할 만큼만)

`.oculpm/` 이 없는 저장소라면 먼저 사용자에게 **"이 프로젝트를 ocul-pm 으로 추적할까요?"** 를 물어보고, 동의를 받으면 `project_init` 도구(confirm=true)로 초기화한다 — 동의 없이·선제적으로 호출하지 않는다. 도구가 없으면 ocul-pm 앱에서 프로젝트 추가를 안내한다.

**정보가 부족한 채 계획을 지어내지 않는다.** 단, 여기서는 리서치의 방향을 정하는 데 필요한 최소만 묻는다 — 문제(누구의 어떤 문제), 완성의 정의(첫 데모 한 장면), 비목표, 플랫폼·강한 제약(기한·오프라인·보안). 아이디어에 이미 담긴 것은 다시 묻지 않는다. 답을 받아 `.oculpm/agents/discussion-spec.md` 규격대로 `.oculpm/discussion/<slug>/discussion.md` 를 만들고 `## 문제 정의` 를 채운다.

## STAGE 1 — 환경 탐색 (웹 리서치)

사용자에게 더 묻기 **전에**, 웹 검색(WebSearch/WebFetch)으로 환경을 직접 조사한다. 문제에 맞는 후보 스택 2~3개에 대해: 현재 안정 버전과 권장 조합(프레임워크 + 빌드 도구 + 테스트 러너) · 공식 스캐폴드 명령 · 그 도메인의 표준 라이브러리·흔한 함정 · 필요한 개발 환경(런타임 버전·패키지 매니저·필수 CLI). 조사 결과를 논의 문서의 `### 방안 {#opt-id}` 후보안에 **버전·출처와 함께** 적는다. 기억 속 버전을 단정하지 말 것 — 검색으로 확인한 것만.

## STAGE 2 — 대화로 최적 사양 확정

리서치 근거를 들고 사용자와 대화해 사양을 함께 확정한다. 질문은 기능 나열이 아니라 **제품 렌즈**로 — 누가 쓰는가, 어떤 가치 가설인가, 안 만들면 사용자는 뭘 하는가, 성공을 무엇으로 알아보는가. 남은 미결(선호 언어·프레임워크, 규모, 비용 허용치, 기존 자산)은 **리서치가 뒷받침하는 객관식**으로 한 번에 묻는다 — "무엇을 쓸까요?"가 아니라 "A(버전·근거) vs B(버전·근거), 이 상황엔 A 추천". 모호한 답은 재질문하고 추측으로 메꾸지 않는다. 사용자가 방안을 고르면 `## 결론` 을 쓰고 status 를 resolved 로. **증거 게이트**: 결론·계획의 모든 주장에 근거(조사 출처·사용자 답변·측정)를 병기한다 — 근거 없는 수식어("빠르고 확장 가능한")는 쓰지 않는다.

## STAGE 3 — 계획 (plan_create, 3-depth 로 매우 자세히)

결론을 **3-depth 계획**으로: `plan_create` 도구로 phases(마일스톤) → items(작업) → children(하위 작업, 1단계)을 만든다. 플랜에는 **`done_when`**(할 일 너머의 결과 — 무엇이 참이 되면 끝인가)과 **`check`**(그것을 통과/실패로 판정하는 명령 — `pnpm test && cargo test`, `curl -f …/health`)를 반드시 준다. 시작 훅이 매 세션 이 두 줄을 항목보다 먼저 싣고, 마지막 항목을 닫는 에이전트는 그 명령을 돌려 결과를 로그에 적는다. 리프는 반나절 이하 단위의 "검증 가능한 동사구"("로그인"이 아니라 "이메일 로그인 happy-path 가 동작한다")로 구현 순서대로 배열하고, 리프마다 확인 방법(돌릴 명령 또는 재현 시나리오)을 문구에 담는다 — `/oculpm:next` 가 그것을 완료 기준으로 쓴다. Phase 1 의 첫 항목은 "리서치에서 확정한 버전으로 환경 구성·스캐폴드". 도구가 없으면 AGENTS.md §5 의 폴백 규격으로 직접 작성.

## STAGE 4 — 초기 규칙 (.claude/rules)

리서치·대화에서 확정된 것 중 **근거가 있는 것만** 1~3개를 `.claude/rules/<name>.md` 로 남긴다 — 확정한 런타임/프레임워크 버전, 도메인 제약, 금지 라이브러리. 조건부 규칙은 frontmatter `paths: ["src/api/**"]` 로 스코프를 좁힌다(없으면 상시 로드 — 토큰 비용을 의식할 것). 범용 조언("좋은 코드를 쓰자")은 금지 — 이 프로젝트에서만 참인 제약만. 확정 스택에 맞는 검증된 스킬은 ocul-pm 앱의 스킬·규칙 → 샵 탭이 스택 감지로 추천한다(설치된 스킬의 설명은 매 세션 실리므로 2~3개만).

## 끝낼 때

플랜의 Phase 1 첫 리프를 보여주고 제안한다: "구현을 시작하려면 `/oculpm:next` — 항목 하나씩 구현 → 확인 명령 → 일지 → 플랜 갱신으로 돕니다." 기능 추가는 STAGE 3 부터 반복한다(기존 플랜에 phase/항목을 더하거나 새 플랜). STAGE 0~2 는 그 영역이 낯설 때만.

## 금지

- 리서치 없이 기억으로 버전·도구를 단정하지 말 것 · 대화를 건너뛰고 추측으로 사양을 정하지 말 것.
- 논의 문서에 진척/실행 로그를 쌓지 말 것 — 그건 플래너·일지의 일.
- 산출물 셋(논의 · 플랜 · 규칙) 외의 문서를 남발하지 말 것.
- 이 스킬은 **설계 시드까지만** — 구현은 `/oculpm:next` 로 항목 단위 진행.
