## 1. Executive Summary

여러 Claude Code 해커톤(Built with Opus 4.6 / 4.7 / 4.8, Cerebral Valley × Anthropic 등)의
수상작을 분석한 결과, **만든 결과물은 제각각이지만 일하는 방식은 강하게 수렴**했다.

핵심 결론 세 가지:

- **(A) 도메인 명료함 > 코딩 실력.** Opus 4.6 해커톤은 우승자 5명 중 4명이 전문 개발자가 아니었다
  (변호사·심장전문의·도로 인프라 전문가·전자음악가). 이들은 "내 기술로 풀 문제"가 아니라
  "내가 이미 가진 문제에 맞는 기술"을 찾았다.
- **(B) 속도는 규율에서 나온다.** 코드보다 스펙·계획·평가(eval)를 먼저 만든 팀이 이겼다.
  느리게 시작해서 빠르게 끝냈다.
- **(C) 규칙을 파일로 외부화한다.** 승자들은 도메인 지식과 판단 기준을 프롬프트에 매번 넣지 않고,
  구조화된 파일(지식 JSON, eval, 규칙 파일)로 만들어 반복·검증·자기개선이 가능하게 했다.

이 (C)를 Claude Code의 설정 계층(CLAUDE.md / rules / skills / subagents / hooks / 자동 메모리)에
맞춰 "**도메인별로 규칙을 스스로 만들고 유지하는 시스템**"으로 확장한 것이 6장이다.

## 3. 수상작 케이스 스터디 (9선)

각 케이스는 **[결과물] → [Claude 활용법] → [뽑아낼 규칙]** 순으로 정리한다.

### 3.1 Medkit — 1위 (Bedirhan Keskin, 의사 출신 개발자)
- **결과물:** 의대 전공의용 시뮬레이션 학습 도구. 가상 환자 문진·검사·진단·처방 후 에이전트가 임상 가이드라인 기준으로 채점.
- **활용법:** 음성 엔진·콘텐츠 생성·3D 게임 레이어·코어 앱을 **4개의 별도 Claude Code 세션**으로 분리해 각 컨텍스트를 깨끗하게 유지하며 동시 진행. 거의 전부를 음성으로 작업하는 **"타이핑 말고 말로"** 접근. 음성 엔진을 직접 호스팅하려 했으나 Claude가 클라우드 사용을 제안 → 채택.
- **규칙:** *Claude를 코드 생성기가 아니라 "옵션을 보게 해주는 사고 파트너"로 대하라. 큰 프로젝트는 도메인별 세션으로 쪼개라.*

### 3.2 Wrench Board — 2위 (Alexis Chapellier, 전자수리공 출신)
- **결과물:** 회로도·보드뷰를 넣으면 에이전트가 통합 전기 그래프를 만들고 추론해 정확한 측정 지점을 짚어주는 전자기기 진단 도구.
- **활용법:** **Claude Design에서 프로토타입** → 앱의 책임(디자인·스키마 수집·보드뷰·진단 에이전트)을 분리 → 각각 **스펙 먼저, 그다음 계획**. 실행은 **멀티 에이전트 모드**로, 도메인마다 전담 에이전트 하나씩, 디버깅 땐 5~6개 병렬. **Superpowers** 스킬 프레임워크로 브레인스토밍→계획 단계를 구조화. 모델이 "시간 없다"고 해도 밀어붙임.
- **규칙:** *책임을 분리하고 도메인마다 전담 에이전트를 둬라. 모델의 "안 된다"를 그대로 믿지 마라.*

### 3.3 Maieutic — 3위 (Paula Vásquez-Henríquez, 컴퓨터과학 교수)
- **결과물:** 학생이 코드를 쓰기 전에 명세부터 쓰게 강제하는 IDE. 자동완성을 끄고, 추론형 질문엔 답 대신 반문. 의도-결과 diff 리뷰로 메타인지 유도.
- **활용법:** 코드 한 줄 전에 **이틀을 순수 사고 작업**(설계 스펙 + 기술 스펙)에 투자. "느리게 느껴졌지만 그 이틀이 나머지 주를 빠르게 만들었다."
- **규칙:** *만들기 전에 생각하라. 명세가 먼저다. (자기 철학을 자기 도구로 도그푸딩.)*

### 3.4 Virtual Puppet Theater — Most Creative (Rene H. Møller, 풀스택 개발자)
- **결과물:** 웹캠·음성으로 즉석 인형극을 만드는 브라우저 앱. 실시간 3D 렌더(Three.js, 60fps), 손 추적(MediaPipe/WASM), Claude로 인형 대사·3D 소품 생성.
- **활용법:** Claude를 **컨셉·계획·코드 전 과정**에 쓰되, **방향·아키텍처·리뷰·의사결정은 사람이** 소유. 시각 출력은 **스크린샷 피드백 루프**로 개선.
- **규칙:** *전 파이프라인에 Claude를 쓰되 판단은 사람이 쥔다. (해커톤이면 데모 영상 제작에 마지막 하루를 통째로 비워라 — 3분 영상은 생각보다 훨씬 오래 걸린다.)*

### 3.5 MaestrIA — "Keep Thinking" (Benjamin Torralbo, 프로그래밍 무경험)
- **결과물:** 사진·음성으로 집수리 문제를 마스터급으로 진단하고 근처 장인을 연결하는 웹앱.
- **활용법:** **eval 우선.** 아버지(공인 장인)가 정답을 기록한 **실제 12케이스에 9차원 eval**을 만들어, 직관이 아니라 eval로 방향을 잡음. 진단 규칙 17·현지 목재 7·방언 16·기준가 19 등을 담은 **JSON 지식 파일 하나**를 모든 진단에 주입 → 시스템 프롬프트를 안 건드리고 eval을 **74%→81%**로. 기능마다 Claude에게 **스펙·액션플랜·보안모델**(입력 소독·속도제한·출처검증·Zod 스키마)을 먼저 설계시키고 **diff 단위 리뷰**.
- **규칙:** *"eval이 첫 커밋이어야 한다." 도메인 지식은 파일로 주입하라. 보안 모델을 기능 전에 설계시켜라.*

### 3.6 ARIA — Best Use of Managed Agents (Idriss Benguezzou & Adam Hnaien)
- **결과물:** 제조사 PDF와 4개 질문으로 15분 만에 공장을 프로파일링, 5개 에이전트가 실시간 신호를 감시해 고장 예측·작업지시서 생성.
- **활용법:** 해커톤 **둘째 날 전체를 GitHub 프로젝트 보드로 계획**(마일스톤·이슈·수용 기준)에 쓰고 나서야 첫 코드 작성. Claude가 **원시 코드 ~80%**를 썼지만 도메인 로직·디자인 결정은 손으로. 인프라는 Managed Agents에 위임. **"다음 걸 만들기 전에 만든 걸 Claude에게 감사(audit)시켜라 — 그 루프가 과소평가돼 있다."**
- **규칙:** *하루의 계획이 나머지 주를 즉흥이 아닌 실행으로 만든다. "취향은 프롬프트로 못 만든다" — 아키텍처·UX는 사람이. 자기 감사 루프를 돌려라.*

### 3.7 everything-claude-code — Cerebral Valley 우승 (affaan-m)
- **결과물:** 8시간 만에 만든 14개 스킬 컬렉션 = **eval-driven development(EDD)** 방법론. 65% 빠른 기능 완료, 첫 패스 리뷰 이슈 75% 감소.
- **활용법:** ① **eval 먼저 정의**(다차원 성공 기준) → ② eval에 맞춰 구현 → ③ **검증 루프**(타입·테스트·린트·보안·성능) 통과 전 완료 금지 → ④ **eval 점수로 반복**. 부가: `tdd-workflow`(RED-GREEN-REFACTOR 강제), `strategic-compact`(핵심만 요약해 긴 세션 3배 유지).
- **규칙:** *검증을 워크플로우에 내장하면 "빠르게"와 "제대로"가 같은 것이 된다.*

### 3.8 CrossBeam — Opus 4.6 (Mike Brown, 비개발자)
- **결과물:** 캘리포니아 28개 법령에 건축 도면을 대조해 수주짜리 심사를 15분 리포트로 자동화.
- **활용법:** **100만 토큰 컨텍스트**를 "원시 현실을 담는 버킷"으로 사용. 카운티마다 다른 비표준 XML의 의미를 주변 필드로 추론하게 함(파서를 직접 짜지 않음).
- **규칙:** *지저분한 데이터는 큰 컨텍스트에 넣고 의미 추론을 모델에 맡겨라.*

### 3.9 PMF Probe / Zenith — Forum Ventures × Anthropic (Affaan Mustafa & David Rodriguez)
- **결과물:** 합성 사용자 인터뷰로 초기 아이디어를 검증하는 창업 도구. 실제 검증 결과가 합성 프로필로 피드백되는 지속 학습 구조.
- **활용법:** 제품을 거의 전부 Claude Code로 완성. 저자는 "손으로 코드 한 줄도 안 썼다"고 함.
- **규칙:** *구조를 잘 잡으면 구현 전량 위임도 가능하다 — 단, 그 구조 설계가 진짜 일이다.*

## 4. 공통 패턴 8가지 — 원리·근거·실행법

| # | 패턴 | 왜 통하나 | 실행법 |
|---|---|---|---|
| 1 | **스펙 먼저, 코드는 나중** | 초반 사고가 후반 재작업을 없앤다 | `SPEC.md`/`PLAN.md`를 첫 산출물로. Claude에게 스펙·액션플랜·보안모델 먼저 설계 요청 |
| 2 | **기능보다 eval 먼저** | 직관이 아니라 증거로 반복 가능 | 정답 있는 실제 케이스로 다차원 eval → "첫 커밋" |
| 3 | **Claude = 사고 파트너** | 코드뿐 아니라 도구·아키텍처 선택까지 도움 | "이 스택 맞나?", "직접 호스팅 vs 클라우드?"를 상의 |
| 4 | **컨텍스트/세션 분리** | 컨텍스트 로트(rot)로 품질 저하 방지 | 도메인별 세션·전담 에이전트, 긴 세션엔 compact |
| 5 | **도메인 지식 파일 주입** | 튜닝 없이 정확도 급상승 | 규칙·용어·기준값을 `knowledge.json`/rules로 |
| 6 | **인간이 아키텍처·취향·리뷰 소유** | 도메인 판단·미감은 프롬프트로 안 됨 | 큰 기능은 diff 단위 리뷰, 핵심 결정은 손으로 |
| 7 | **모델에 밀어붙이기** | 모델의 시간·난이도 추정은 종종 보수적 | "안 된다"에 "그래도 해볼게"로 한 번 더 |
| 8 | **자기 감사 루프** | 다음 작업 전 결함 조기 발견 | "방금 만든 것에 문제 없는지 찾아줘"를 정례화 |

> **컨텍스트 로트 주의:** 2025 벤치마크에서 프런티어 모델들도 컨텍스트가 길어지면 정확도가 떨어졌다.
> 그래서 4·5번(세션 분리·파일 외부화)이 단순 취향이 아니라 성능 문제다.

## 5. 바이브 코딩 표준 워크플로우 (STAGE 0–5)

```
STAGE 0  도메인 선정 ── 내가 남보다 깊이 아는 문제를 고른다 (해자)
STAGE 1  스펙/계획  ── SPEC.md, PLAN.md (코드 0줄)
STAGE 2  평가 설계  ── EVALS.md: 정답 케이스 + 다차원 통과기준
STAGE 3  지식 주입  ── knowledge.json / .claude/rules/<domain>.md
STAGE 4  구현       ── Claude 70~80%, 아키텍처·취향은 사람, diff 리뷰
STAGE 5  검증·감사  ── 검증 루프 + 자기 감사, eval 점수로 반복
              └── (실패한 케이스 → 6장: 규칙으로 승격)
```

각 단계 산출물이 다음 단계의 입력이 되도록 **파일로 남기는 것**이 핵심이다.
이 파일들이 6장의 "자기생성 규칙 시스템"의 원재료가 된다.

## 6. 도메인별 자기생성 규칙 시스템 ★

목표: **프로젝트가 진행될수록 Claude가 도메인마다 규칙을 스스로 초안하고, 사람이 큐레이션하며,
실패에서 배운 것을 규칙으로 승격시켜 점점 똑똑해지는** 루프를 만든다.

### 6.1 먼저: Claude Code의 규칙 계층을 이해하라

규칙은 한 곳에 몰아넣는 게 아니라 **"언제 로드되고, 컨텍스트 비용이 얼마이고, 얼마나 정밀한가"**로
계층을 나눈다.

| 계층 | 위치 | 로드 시점 | 무엇을 넣나 | 자기생성 적합도 |
|---|---|---|---|---|
| **CLAUDE.md** | 프로젝트 루트 | 매 세션 상시 | 항상 참인 사실·컨벤션·명령어 (<200줄) | △ (초안만, 사람이 다듬기) |
| **경로 규칙** | `.claude/rules/*.md` | 매칭 경로 파일 접근 시 | **도메인별 깊은 지식** (globs로 스코프) | ◎ (자동생성 최적) |
| **Skills** | `.claude/skills/<name>/SKILL.md` | 이름·설명으로 필요 시 | 반복 절차·워크플로우 | ○ |
| **Subagents** | `.claude/agents/` | 복잡·격리 작업 시 | 자율 전문가(자체 컨텍스트) | ○ |
| **Hooks** | 설정 | 결정론적 트리거 | "반드시 실행"되는 강제 규칙(린트·포맷 등) | ○ |
| **자동 메모리** | `~/.claude/projects/<proj>/memory/` | 매 세션(MEMORY.md 상단) | **Claude가 스스로 학습한 패턴** | ◎ (자동) |

핵심 원칙(공식·커뮤니티 공통):
- **CLAUDE.md는 손으로 다듬어라.** 가장 레버리지가 큰 파일이라 자동생성은 평범한 결과를 낸다.
  `/init`으로 초안을 뽑되 반드시 프루닝. 200줄 이하, "이 줄을 지우면 Claude가 실수하나?"로 취사선택.
- **도메인 규칙은 경로 스코프(`.claude/rules/`)로.** 관련 파일을 만질 때만 로드되어 컨텍스트 낭비 없음.
  이곳이 **자동생성이 가장 잘 통하는 자리**다.
- **결정론적 규칙(항상 포맷/린트/테스트)은 hooks로.** 프롬프트로 "항상 ~해"라고 적지 말고 hook으로 강제.

### 6.2 자기생성 파이프라인 (5스텝 루프)

```
[1] 부트스트랩      /init → CLAUDE.md 초안 → 사람이 프루닝
        │
[2] 도메인 분석     "services/billing/** 를 분석해 규칙 초안을 만들어줘"
        │           → .claude/rules/billing.md (globs 포함) 자동 생성
        │
[3] 큐레이션        사람이 초안 리뷰·수정·승인 (draft=Claude, decision=사람)
        │
[4] 자기학습 축적   자동 메모리가 세션 학습을 기록 → 주기적으로 /memory 감사
        │
[5] 승격 루프       eval 실패/반복 실수 → 근본원인 → 규칙으로 승격 → 경로 스코프
        └────────────────────────── 다시 [2]로 (도메인이 늘 때마다)
```

이 루프의 정신: **"Claude가 초안을 쓰고(draft), 사람이 결정한다(curate), 실패가 규칙을 낳는다(promote)."**

### 6.3 도메인 규칙 파일 구조 예시

```
프로젝트루트/
├── CLAUDE.md                      # 항상 참인 코어 (손으로 다듬음, <200줄)
├── .claude/
│   ├── rules/
│   │   ├── api.md                 # globs: ["src/api/**"]   — REST 규약·에러 포맷
│   │   ├── db.md                  # globs: ["src/db/**"]    — 스키마·마이그레이션 규칙
│   │   ├── security.md            # globs: ["**/*"]         — 입력소독·시크릿 금지
│   │   └── ui.md                  # globs: ["src/ui/**"]    — 디자인 토큰·접근성
│   ├── skills/
│   │   ├── add-endpoint/SKILL.md  # 반복 절차: 새 API 엔드포인트 추가
│   │   └── run-evals/SKILL.md     # eval 하네스 실행 워크플로우
│   └── agents/
│       └── code-auditor.md        # 자기감사 전담 서브에이전트
├── evals/
│   └── EVALS.md                   # 정답 케이스 + 다차원 통과기준
└── knowledge/
    └── domain.json                # MaestrIA식 도메인 지식(용어·규칙·기준값)
```

각 `.claude/rules/*.md`는 상단 프론트매터에 **`globs`(적용 경로)**를 두어,
그 경로의 파일을 만질 때만 로드되게 한다 (컨텍스트 절약 + 도메인 격리).

### 6.4 "규칙을 스스로 만들게" 하는 4가지 실전 방법

1. **도메인 분석 → 규칙 초안 생성(온디맨드).**
   특정 디렉토리/도메인을 지정해 "이 코드베이스를 분석해 이 도메인에서 반복되는 컨벤션·함정·판단
   기준을 뽑아 `.claude/rules/<domain>.md` 초안(globs 포함)으로 만들어줘"라고 시킨다. → 6.5 템플릿 T1.

2. **자동 메모리로 상시 학습(자동).**
   Claude가 세션 중 배운 결정·제약·아키텍처 선택을 `memory/`에 자동 기록한다.
   주기적으로 `/memory`로 감사해 **안정적으로 반복되는 학습은 경로 규칙으로 승격**시킨다.

3. **eval 실패 → 규칙 승격(핵심 자기개선 루프).**
   eval에서 떨어진 케이스마다 "왜 틀렸는지 근본원인을 찾고, 재발을 막을 규칙 한 줄을 만들어
   가장 좁은 경로에 스코프해 추가해줘"라고 시킨다. → 템플릿 T2. (MaestrIA·EDD의 정신)

4. **메타 규칙(규칙에 대한 규칙)을 CLAUDE.md에 심는다.**
   "새로운 컨벤션을 발견하면 CLAUDE.md에 쌓지 말고 해당 경로의 `.claude/rules/`에 스코프해서 넣어라",
   "반드시 실행돼야 하는 규칙은 hook을 제안하라" 같은 **자기조직화 지침**을 코어에 둔다. → 템플릿 T4.

### 6.5 안티패턴 (하지 말 것)

- ❌ **CLAUDE.md 비대화.** 모든 규칙을 여기 몰면 매 세션 토큰을 태우고 정작 중요한 지시의 준수율이 떨어진다.
- ❌ **경로 스코프 없는 규칙.** 스코프 없는 규칙은 사실상 CLAUDE.md에 붙인 것과 같다(항상 로드).
- ❌ **자동생성 CLAUDE.md를 그대로 신뢰.** 초안일 뿐. 반드시 사람이 프루닝.
- ❌ **"항상 ~해"를 프롬프트로.** 결정론적 강제는 hook/린터가 더 싸고 정확하다.
- ❌ **검증 없이 신뢰.** 그럴듯해 보이는 diff를 돌려보지도 않고 병합하지 말 것. 실행하고 diff를 읽어라.

## 8. 부록 A: 복붙용 프롬프트 템플릿

**T1 — 도메인 규칙 자동 생성**
```
[디렉토리/도메인]을 분석해줘. 이 도메인에서 반복되는 코딩 컨벤션, 자주 나오는 함정(pitfall),
그리고 사람이 매번 설명하게 되는 판단 기준을 추출해서, .claude/rules/<domain>.md 규칙 파일
초안으로 만들어줘. 조건:
- 상단 프론트매터에 globs(적용 경로)를 반드시 넣을 것
- 항상 참인 것만, 간결하게. 추측이면 [확인필요]로 표시
- 결정론적으로 강제할 항목은 규칙 대신 "hook 후보"로 따로 목록화
초안만 만들고, 내가 승인하기 전엔 파일을 확정하지 마.
```

**T2 — eval 실패 → 규칙 승격**
```
이번 eval에서 실패한 케이스들을 하나씩 근본원인까지 분석해줘. 각 실패에 대해:
1) 무엇이·왜 틀렸는지
2) 재발을 막을 규칙 한 줄(가능한 한 좁게)
3) 그 규칙이 들어갈 가장 좁은 경로 스코프(.claude/rules/의 어느 파일, globs)
를 제시하고, 내 승인 후 해당 파일에 추가해줘. CLAUDE.md는 건드리지 마.
```

**T3 — 규칙 감사·정리(리팩터링)**
```
현재 CLAUDE.md와 .claude/rules/ 전체를 검토해줘.
- CLAUDE.md에서 특정 경로에만 해당하는 항목 → 경로 규칙으로 이동 제안
- 중복·모순·죽은 규칙 → 삭제/병합 제안
- "항상 실행" 성격의 항목 → hook 전환 제안
변경은 제안 목록으로만 주고, 내가 고른 것만 적용해.
```

**T4 — CLAUDE.md에 심는 메타 규칙(자기조직화)**
```
## 규칙 관리 원칙
- 새 컨벤션을 발견하면 이 파일에 쌓지 말고, 해당 경로의 .claude/rules/에 globs로 스코프해 추가할 것.
- 반드시 매번 실행돼야 하는 규칙은 프롬프트가 아니라 hook을 제안할 것.
- 다음 기능을 만들기 전에, 방금 만든 것의 결함을 먼저 감사(audit)할 것.
- 기능 구현 전 스펙·단계별 액션플랜·보안모델을 먼저 제시하고 승인받을 것.
```

**T5 — 구현 전 스펙·보안 설계(승자 공통)**
```
[기능]을 바로 구현하지 말고, 먼저 다음을 순서대로 제시해줘:
1) 스펙(무엇을·왜), 2) 단계별 액션플랜(수용 기준 포함),
3) 보안 모델(입력 소독·속도 제한·출처 검증·스키마 검증).
내가 승인하면 그때 구현하고, 큰 기능은 diff 단위로 나눠서 보여줘.
```
