# Ocul-PM 제품 방향과 첫 가치 경험 개선 보고서

작성일: 2026-09-21 · 작성자: codex / GPT-6 · 상태: 구현 전 제안

이 문서는 사용자 확보 문제에 대한 저장소 기반 진단과, 다음 세션이 이어서 설계·구현할 수 있는 상세 제안이다. 사용자 행동을 실측한 연구 보고서가 아니다. 문서 작성은 요청받았지만, 여기 적힌 모든 제품 변경·배포·외부 연락이 승인되거나 완료된 것은 아니다. 다음 세션에 사용자가 구현을 요청하면 그 범위에서 진행한다.

## 1. 배경과 핵심 판단

사용자는 “왜 아무도 내 앱을 사용해주지 않을까?”라고 물었고, 직접 문제점을 파악해 달라고 요청했다. 이어서 “너라면 어떻게 바꿀 것인가”를 물었으며, 마지막으로 이 계획을 다른 세션과 에이전트에게 전달할 상세 문서로 남기도록 요청했다.

현재 가장 유력한 가설은 **앱이 제공하는 기능의 범위에 비해, 처음 써야 할 구체적인 이유와 첫 보상을 작게 보여준다는 것**이다. 자동 일지·검증·콘솔·편집기·계획 관리가 함께 소개되지만, 새 사용자가 기존 작업 환경에 Ocul-PM을 추가해서 얻는 즉각적인 이득은 상대적으로 흐리다.

추천 방향은 **“AI가 지난 작업을 기억하고 이어가게 만드는 앱”**이다. 일지는 저장하는 산출물이자 다음 작업의 입력이다. 핵심 경험을 `작업 → 근거 있는 기록 → 다음 세션에서 관련 기록 찾기 → 맥락을 확인하고 작업 재개`로 연결한다.

이 제안은 앱 전체를 처음부터 다시 만드는 계획이 아니다. 이미 있는 기록·검색·회상·플러그인·변경 검토 기능을 연결하고, 첫 사용자에게 보이는 우선순위를 조정하는 계획이다. 좁은 경로의 성공을 확인한 다음 화면 구조를 확대 변경한다.

## 2. 조사 범위와 증거의 한계

### 확인한 자료

- README와 한국어 랜딩 소스, 시작 안내, 지원 에이전트 계약.
- WelcomeWizard의 단계와 완료 조건, Today·일지 빈 상태 안내 문구.
- 첫 5분 개선 일지와 사용자 유입 장벽 진단 일지.
- 활성 플랜의 미완 항목.
- 추가로 회상 판정·예산 코드, 프런트엔드 회상 사용량 스토어, DB 회상 통계 구현.
- 공개 GitHub 페이지. 웹 도구가 제공한 결과는 과거 캐시였으므로 최신 배포 상태 근거로 사용하지 않았다.

### 확인하지 못한 자료

- 실제 사이트 방문자, 다운로드 전환율, 활성 사용자, 재방문율, 유입 채널별 성과.
- 처음 설치하는 외부 사용자의 행동 관찰과 인터뷰.
- 이번 조사에서 설치본의 첫 실행을 직접 재현한 결과.
- oculpm.com 실시간 배포 화면. 웹 도구 접근 실패로 로컬 소스를 대신 확인했다. 접근 실패는 사이트 장애의 증거가 아니다.
- 경쟁 제품과의 최신 기능·가격·시장 비교. 이 문서에 경쟁 우위가 검증됐다는 주장은 없다.

따라서 “사용자가 0명이다”, “기능이 많아서 이탈했다”, “홍보만 하면 해결된다”를 확정하지 않는다. 문서의 우선순위는 확인된 제품 구조를 근거로 세운 검증 순서다.

## 4. 제품 방향과 우선 사용자

### 우선 사용자 가설

같은 저장소를 여러 날·여러 세션에 걸쳐 수정하며, AI에게 이전 결정·실패·남은 일을 반복 설명하는 개발자. 첫 검증은 현재 지원과 관측이 잘 되는 한 에이전트·한 실행 경로로 좁힌다. Claude Code 앱 통합 또는 외부 플러그인 중 실제 왕복 검증이 쉬운 경로를 Phase 0에서 고른다.

“AI를 사용하는 모든 개발자”를 첫 대상으로 삼지 않는다. 간단한 일회성 질문만 하는 사람은 기록 재사용 필요가 낮을 수 있다. 팀 동기화·회사 보고를 먼저 요구하는 사용자도 초기 가설과 분리한다.

### 사용자가 해결하려는 일

“어제의 작업을 다시 이해하는 데 시간을 쓰지 않고, 현재 코드를 기준으로 다음 작업을 시작하고 싶다.”

이 요구는 다음 세 질문으로 구체화된다.

1. 마지막으로 어디까지 했는가?
2. 이전에 왜 그렇게 결정했고, 무엇이 실패했는가?
3. 지금 고칠 파일과 관련해 무엇을 먼저 확인해야 하는가?

### 제안하는 메시지

주 문구 후보: **지난번에 왜 이렇게 고쳤는지, 다음 AI도 알고 시작합니다.**

보조 설명 후보: “작업의 결정과 실패를 프로젝트에 기록하고, 다음 세션이 관련 기록을 찾아 이어가도록 돕습니다. 기존 작업 도구와 함께 사용할 수 있습니다.”

이는 출시 문구 초안이다. 실제 전달·회상 경로가 검증되지 않은 에이전트까지 약속하지 않는다. ‘반복 실수 방지’, ‘시간 절약’, ‘자동 기억’은 관찰 근거와 지원 조건을 붙일 수 있을 때만 강하게 표현한다.

## 5. 검토한 대안과 추천

| 대안 | 이점 | 비용·위험 | 판단 |
|---|---|---|---|
| A. 현재 기능 중심 소개를 유지하고 홍보 확대 | 제품 변경이 적다 | 첫 성공 경로 문제가 있으면 방문만 늘고 재사용은 안 늘 수 있다 | 유입 부족 가설을 확인할 보조 실험 |
| B. 기억 재사용 중심으로 진입 경험 연결 | 기존 자산 활용, 다음에 다시 쓸 이유가 분명하다 | 기록 관련성과 전달 관측이 실제로 작동해야 한다 | 추천 |
| C. 통합 IDE·에이전트 콘솔 기능 확대 | 한 앱에서 작업을 끝낼 수 있다 | 기존 도구에서 옮겨올 부담과 구현 범위가 커진다 | 초기 우선순위 낮춤 |
| D. 플러그인만 남기고 데스크톱 축소 | 진입 부담이 낮다 | 변경 검토·시각적 탐색의 강점을 잃을 수 있다 | 삭제 대신 플러그인을 주 진입점으로 활용 |

추천은 B이며, D의 낮은 진입 부담을 채택한다. 플러그인과 데스크톱 중 하나를 강제로 고르게 하기보다, 기존 도구에서 시작하고 앱에서 기록을 검토할 수 있도록 연결한다.

## 6. 목표 사용자 여정

### 여정 A — 기록이 전혀 없는 새 프로젝트

1. 사용자가 자신의 실행 환경을 선택한다. 앱 안 에이전트인지, 외부 도구와 함께 쓸 것인지 구분한다.
2. 기존 프로젝트 폴더를 선택한다. 생성·수정할 기록 폴더와 규칙 파일을 이해할 수 있게 설명한다.
3. 해당 경로의 준비 상태를 확인한다. 실행 파일 존재, 연동 설정 존재, 실제 연결 확인을 서로 구분한다.
4. 사용자가 원래 하려던 작은 작업을 시작한다. 가짜 작업을 강제로 만들거나 자동 커밋하지 않는다.
5. 작업 후 같은 프로젝트·세션에 귀속되는 일지 생성 여부를 확인한다.
6. 성공하면 실제 일지와 관련 변경을 열어준다. 작업 기록과 검토 여부를 구분한다.
7. 다음 세션에서 이 일지를 찾고 읽는 경험을 제공한다. 여기까지가 핵심 재사용 검증이다.

### 여정 B — 일지는 없지만 기존 커밋이 있는 프로젝트

첫 화면에서 기존 커밋으로 기록을 만드는 경로를 제공한다. 기존 백필 기능을 재사용한다. 단, 커밋에 없는 결정 이유를 사실처럼 복원하지 않는다. “커밋 기반 기록”이라는 출처를 유지하고, 과거 실패나 의도는 자료가 없으면 알 수 없다고 표시한다. 백필 성공을 에이전트 자동 기록 성공으로 집계하지 않는다.

### 여정 C — 이미 Ocul-PM을 쓰는 프로젝트

기존 사용자를 첫 실행으로 되돌리지 않는다. 현재 화면·단축키·프로젝트 설정을 유지하고 ‘이어하기’를 추가 진입점으로 먼저 제공한다. 기존 일지와 플랜에서 필요한 근거를 읽어 보여주되, 기록을 일괄 재작성하거나 폴더 구조를 강제로 바꾸지 않는다.

### 여정 D — 외부 에이전트에서 다음 작업 시작

기존 플러그인·MCP가 작업 관련 파일 또는 검색어로 일지를 찾는다. 관련 원문을 읽고, 읽은 기록의 출처를 사용자에게 표시할 수 있는 범위를 확인한다. 앱은 실제 도구 호출로 관측한 것만 표시한다. 외부 프로세스를 볼 수 없으면 상태를 ‘확인할 수 없음’으로 둔다. 앱이 실행 중이지 않아도 저장된 마크다운과 기존 플러그인 기능이 유지되어야 한다.

## 7. 첫 성공을 위한 온보딩 설계

### 단계 제안

`실행 환경 선택 → 프로젝트 선택 → 연결 확인 → 실제 작업 시작 → 첫 기록 확인`

언어·테마는 시스템 값을 초기값으로 쓰고 언제든 바꿀 수 있게 한다. 기존 사용자의 설정은 덮어쓰지 않는다. 언어와 기록 언어가 별개인 기존 정책을 유지하며, 기존 기록의 언어를 일괄 변환하지 않는다.

### 상태와 행동

| 상태 | 사용자에게 보여줄 것 | 다음 행동 |
|---|---|---|
| 프로젝트 미선택 | 어떤 폴더가 필요한지 | 기존 폴더 선택 |
| 실행 환경 미확인 | 선택한 도구의 확인 결과 | 확인 실행 또는 다른 경로 선택 |
| 설정 존재·연결 미확인 | 설정은 있으나 실제 연결은 아직 확인 전 | 연결 확인 |
| 준비 완료 | 이제 실제 작업을 시작할 수 있음 | 작업 시작 |
| 실행 중 | 작업 중이며 기록 완료는 아직 아님 | 실행 화면으로 이동 |
| 기록 대기 | 작업 종료와 기록 도착을 구분 | 다시 확인, 원인 보기 |
| 기록 확인 | 해당 세션의 실제 일지 제목·출처 | 일지 및 변경 열기 |
| 확인 불가 | 관측 범위 밖이거나 세션 귀속 근거 없음 | 수동 확인 경로 |
| 실패 | 실패한 단계와 복구 방법 | 해당 단계 재시도 |

일지가 원래 있던 프로젝트에서 총 개수가 1 이상이라는 이유만으로 성공 처리하지 않는다. 관측 시작 전 기준값 또는 해당 세션 식별자를 사용한다. 재시도·재실행에서 중복 기록이나 중복 성공 이벤트가 생기지 않도록 한다.

닫기·건너뛰기는 허용한다. 기존 `onboarded`의 의미를 몰래 바꾸지 않는다. 필요하다면 별도의 초기 경험 진행 상태를 두되 저장 범위(사용자 전체/프로젝트/실행 경로)를 먼저 결정한다. 앱을 다시 열었을 때 미완 단계를 회복하는 방식도 함께 정한다.

### 완료 기준

- 선택한 경로에서 실제 작업의 일지를 보여줄 수 있다.
- 준비 확인과 기록 성공을 혼동하지 않는다.
- 도구 없음, 연결 실패, 기록 없음, 귀속 불명 각각에서 다음 행동이 있다.
- 새 프로젝트와 기존 프로젝트에서 모두 파일 초기화 시점이 정직하다.
- 기록이 생겼다는 사실을 코드가 검증됐다는 뜻으로 표현하지 않는다.

## 8. ‘이어하기’ 화면 상세

### 첫 화면의 정보 순서

1. 프로젝트와 기준 시각.
2. 마지막 작업 요약. 원본 일지로 이동 가능.
3. 활성 계획의 다음 항목. 미완 상태와 관련 근거 표시.
4. 현재 작업과 관련한 결정·실패 기록. 무관한 최근 기록 전체를 넣지 않는다.
5. ‘이 맥락으로 작업 시작’. 전달 전에 포함할 내용을 확인할 수 있다.
6. 보조 행동: 변경 검토, 모든 기록, 계획 보기.

예시 문구는 데이터가 실제로 있을 때만 사용한다.

> 마지막 작업: 저장 시 파일 충돌 처리 수정
> 남은 일: 외부 변경이 들어온 상태에서 저장 동작 확인
> 참고 기록: 같은 경로의 덮어쓰기 오류 조사
> [이 맥락으로 작업 시작] [근거 보기]

### 데이터 선택 원칙

- 현재 프로젝트를 기본 경계로 한다. 다른 프로젝트의 기록은 자동 혼합하지 않는다.
- 최근 작성 시각 하나만으로 현재 코드의 정답이라고 판단하지 않는다.
- 활성 계획의 실제 상태와 잠긴 계획의 상태를 구분한다.
- 실패 기록은 과거 상황의 결과다. 현재 환경에서도 실패한다고 단정하지 않는다.
- 상충되는 결정은 최신 기록으로 조용히 덮기보다 양쪽 근거를 보여준다.
- API 키가 없거나 오프라인이어도 기본 목록과 원문 링크는 동작해야 한다.
- 초기 버전은 결정적 목록·발췌로 충분하다. LLM 요약을 필수 경로에 넣지 않는다.

### 경계 사례

일지 없음: 첫 기록 또는 백필로 안내. 플랜 없음: 없는 상태를 그대로 보여주고 자동으로 계획을 만들지 않는다. 파일 삭제·이름 변경: 원문 링크와 현재 파일 상태를 구분한다. git 저장소 아님: 브랜치·커밋 정보를 생략하고 기록 기반 기능 유지. 기록을 외부에서 수정함: 새 내용을 다시 읽고 오래된 요약을 최신으로 표시하지 않는다.

## 9. 기억 전달과 관측의 의미

### 구분해야 하는 다섯 단계

| 단계 | 확인 가능한 사실 | 사용 가능한 표현 |
|---|---|---|
| 검색 결과 | 후보 기록이 검색 결과에 나타남 | 관련 기록을 찾았습니다 |
| 원문 읽기 | 도구가 특정 기록 본문을 반환함 | 기록을 불러왔습니다 |
| 컨텍스트 포함 | 특정 호출 입력에 기록이 포함됨 | 이번 요청에 기록을 전달했습니다 |
| 답변의 명시적 참조 | 답변이 출처와 함께 기록을 언급함 | 답변에서 이 기록을 참조했습니다 |
| 실질적 도움 | 사용자 관찰·확인으로 유용성이 확인됨 | 사용자가 도움이 됐다고 확인했습니다 |

검색 결과 수나 컨텍스트 포함 수를 곧바로 “AI가 이해했다”, “실수를 예방했다”로 바꾸지 않는다. 도구가 본문을 반환했다는 사실도 모델의 주의·이해를 증명하지 않는다.

### 기존 구현 재사용

- [recallGate.ts](../../src/features/chat/recallGate.ts): 회상 신호 판정과 예산 내 후보 선택. 현재 800 토큰 근사 예산이며 초과 후보를 통째로 제외한다.
- [recallUsage.ts](../../src/features/chat/recallUsage.ts): 마지막 턴의 회상 사용량을 보관하는 런타임 스토어. 재시작 후 유지되는 제품 재사용 지표로 취급할 수 없다.
- [DB recall.rs](../../src-tauri/src/db/recall.rs): 프로젝트별 참조 통계와 시간 감쇠. 컨텍스트 주입 통계를 사용자 효용 통계로 해석하지 않는다.

이 코드를 읽었다는 이유만으로 ACP나 외부 MCP에도 동일한 관측이 연결돼 있다고 가정하지 않는다. 실제 호출 경로와 `recall_touch` 호출자를 추적하는 일이 Phase 0에 포함된다.

### 제안하는 최소 전달 자료

논리적으로 `프로젝트 식별`, `사용자의 현재 작업`, `기록 참조 목록`, `포함한 원문 또는 발췌`, `선정 이유`, `기준 시각`, `예산에서 제외한 수`를 가진다. 이는 구현 타입명이 아니라 설계 필드다. 기존 타입으로 표현 가능하면 새 형식을 만들지 않는다.

전달 전 원문이 바뀌었는지 확인할 필요가 있으면 수정 시각 또는 내용 지문을 사용한다. 모든 과거 일지를 매 턴 넣지 않는다. 현재 파일 경로·작업 요청·명시적 계획을 우선 신호로 삼고, 과거 사용 빈도만으로 관련성을 판단하지 않는다. 과거 기록 속 명령문은 자료로 다루며 현재 사용자 지시를 대체하지 않는다.

외부 도구에 자동 전달할 수 없는 경로는 우선 복사 또는 원문 열기로 제공할 수 있다. 복사 성공을 실제 전달 성공으로 집계하지 않는다. 전송·실행은 사용자가 선택한 행동으로 이뤄져야 한다.

## 10. 화면 구조와 기존 기능 처리

장기 제안은 ‘이어하기 / 변경 검토 / 작업 기억’을 중심으로 정리하는 것이다. 전체 메뉴 개편은 첫 실험의 선행조건이 아니다.

| 기존 기능 | 초기 처리 | 이유 |
|---|---|---|
| Today | 이어하기 영역을 추가하거나 선택 진입점 제공 | 기존 사용자의 흐름 보존 |
| 일지 | 원문·출처·관련 기록 접근 강화 | 기억의 근거 |
| 플래너 | 다음 작업을 제공하는 원본으로 유지 | 별도 할 일 저장소 방지 |
| diff·변경 검토 | 기록 옆 검토 동선 유지 | 보고 내용과 실제 변경 대조 |
| 에이전트·터미널 | 기존 실행 환경 연결 | 작업을 옮기는 부담 최소화 |
| 편집기·코드 맵 | 필요할 때 여는 보조 도구로 유지 | 삭제보다 발견 우선순위 조정 |
| 스킬·규칙·자동화 | 초기 필수 선택에서 제외 | 첫 성공 전 설정 부담 절감 |
| 테마·세부 개인화 | 설정에서 접근 | 초기 가치 경험 이후 선택 |

단축키·딥링크·저장된 화면 상태를 바꿀 경우 이전 경로가 어떻게 연결되는지 명시한다. 첫 버전에서는 메뉴 삭제, 기존 기록 마이그레이션, 대규모 명칭 변경을 한꺼번에 묶지 않는다.

## 11. 랜딩·README·시작 안내 개편

### 소개 순서 제안

1. 누가 어떤 반복 설명 문제를 해결하는지 한 문장.
2. 작업 기록이 다음 세션에서 다시 읽히는 실제 짧은 데모.
3. 검증된 경로로 시작하는 버튼과 플랫폼 조건.
4. 세 단계: 작업하기 → 기록 확인 → 다음 세션에서 이어가기.
5. 기록 원문·변경 검토·로컬 보관의 근거.
6. 지원 환경과 조건, 상세 기능 링크.
7. 변경 이력·기술 구조·후원 등 보조 정보.

다운로드와 플러그인 시작 중 주 CTA는 검증 경로에 맞춰 정한다. 버튼이 두 개라면 각각 누구를 위한 경로인지 짧게 설명한다. 첫 화면에 기능 목록과 여러 설치 방식을 동등하게 늘어놓지 않는다.

### 데모 촬영 시나리오

샘플 프로젝트에서 작은 결함 수정 → 실제 일지 생성 → 새 세션 시작 → 같은 파일 관련 일지 검색·원문 읽기 → 근거를 확인하고 다음 작업 시작. 샘플임을 표시하고 실제 사용자의 기록처럼 꾸미지 않는다. 서로 다른 에이전트를 쓰는 시연은 양쪽 연결을 검증한 다음 촬영한다.

영상 길이 30~60초는 제작 목표일 뿐 사용성 검증 결과가 아니다. 설명 없이도 연결을 이해하는지 확인한다. “몇 분 절약” 수치를 실측 없이 넣지 않는다.

### 문서 일치성

README·한국어/영어 랜딩·시작 위키·플러그인 안내·앱 문구가 같은 조건을 말해야 한다. 위키의 네이티브 규칙 파일 지원 설명은 에이전트별 어댑터와 대조한다. 과거 경고 우회법이나 오래된 화면 이름이 현재 설치의 필수 단계처럼 보이지 않도록 한다. 실제 배포와 소스 버전은 별도로 확인한다.

## 12. 구현 순서와 작업 단위

각 Phase는 예상 날짜 대신 선행조건과 완료 증거로 관리한다. 제품 코드가 바뀌면 프로젝트 규칙에 따라 해당 일지와 플래너를 갱신한다.

### Phase 0 — 기준선과 한 경로 확정

- P0-1: 현재 git 변경·활성 플랜·최신 관련 일지를 확인한다. 다른 세션의 변경과 겹치는 경로를 찾는다.
- P0-2: 새 샘플 프로젝트에서 현재 첫 실행 → 첫 기록 흐름을 재현하고 단계·클릭·실패 위치를 기록한다.
- P0-3: 앱 AI 패널, 앱 ACP, 외부 플러그인에서 검색·읽기·전달 관측 범위를 표로 만든다.
- P0-4: 첫 검증 경로 하나를 고르고 기존 데이터·API 재사용 범위를 확정한다.
- 완료 증거: 실제 재현 기록, 관측 가능 범위표, 변경 후보 파일, 제한사항.

### Phase 1 — 첫 기록 성공 연결

- P1-1: 실행 환경별 준비 상태와 실패 복구 동선을 구현한다.
- P1-2: 프로젝트별 첫 기록 확인을 기존 온보딩/Today 흐름에 연결한다.
- P1-3: 재시도·닫기·재실행·기존 기록 보유 프로젝트를 처리한다.
- P1-4: 선택한 경로의 안내 문구를 실제 조건과 일치시킨다.
- 완료 증거: 새 프로젝트에서 해당 세션의 실제 일지로 도착, 실패 시 복구, 기존 사용자 회귀 없음.

### Phase 2 — 다음 세션에서 이어가기

- P2-1: 기존 기록·활성 플랜을 읽어 이어하기 자료를 구성한다.
- P2-2: 근거 원문 확인과 전달 내용 미리보기를 제공한다.
- P2-3: 기존 에이전트 실행 또는 외부 전달 경로 하나에 연결한다.
- P2-4: 검색·읽기·전달의 관측 의미를 구분해서 표시한다.
- 완료 증거: 세션 A의 기록을 세션 B에서 관련 근거로 불러오는 실제 왕복. 불필요한 기록 제외와 예산 제한 확인.

### Phase 3 — 소개와 유입 경로 정렬

- P3-1: README 상단과 랜딩을 핵심 경험 중심으로 편집한다.
- P3-2: 실제 왕복을 촬영하고 샘플·지원 조건을 표시한다.
- P3-3: 시작 위키·영어 문서와 앱 문구를 동기화한다.
- 완료 증거: 신규 사용자가 소개를 이해하고 안내만으로 시작할 수 있음, 링크·플랫폼·설치 경로 확인.

### Phase 4 — 작은 사용자 검증

- P4-1: 대상 조건에 맞는 소규모 사용자 관찰을 준비한다.
- P4-2: 도움 없이 첫 기록까지 도달하는지 관찰한다.
- P4-3: 다음 실제 작업에서 기록을 자발적으로 다시 찾는지 확인한다.
- P4-4: 유입·준비·첫 기록·재사용 중 어느 단계가 막히는지 분리한다.
- 완료 증거: 관찰 노트, 분모가 있는 결과, 실패 이유, 유지·수정·중단 판단.

### Phase 5 — 근거가 생긴 뒤 확장

재사용이 확인되면 메뉴 정리·다른 에이전트·검색 품질·변경 검토 연결을 확대한다. 처음부터 모든 에이전트와 모든 화면을 개편하지 않는다. 반대로 첫 기록에는 성공하지만 다시 찾지 않는다면 화면 확장보다 사용 대상과 재사용 가치부터 재검토한다.

## 13. 코드 탐색 지도

아래는 현재 존재하는 파일과 탐색 출발점이다. 모두가 수정 대상은 아니며, 존재 확인과 전체 동작 검증은 다르다.

| 영역 | 출발 파일 | 확인할 내용 |
|---|---|---|

## 14. 검증 계획

### 핵심 기능 검증

| 시나리오 | 기대 결과 |
|---|---|
| 새 프로젝트, 준비된 실행 환경 | 첫 작업 일지를 올바른 세션과 연결 |
| 플러그인/CLI 없음 | 없는 항목과 다음 행동 표시, 가짜 성공 없음 |
| 설정 파일만 있고 서버 연결 실패 | 준비 완료로 잘못 표시하지 않음 |
| 기존 일지가 많은 프로젝트 | 과거 기록을 이번 첫 성공으로 오인하지 않음 |
| 병렬 세션 둘 | 다른 세션 기록으로 성공 판정하지 않음 |
| 기록 후 다음 세션 | 관련 원문을 찾고 전달 내용 확인 가능 |
| 무관한 과거 기록 | 관련 기록인 것처럼 자동 포함하지 않음 |
| 예산보다 긴 기록 | 반쪽 근거를 무심코 주입하지 않고 제외 사실 표시 |
| 원문 수정·삭제·상충 | 오래된 상태를 확정 사실로 보여주지 않음 |
| 오프라인·키 없음 | 기본 목록·원문·무료 경로 유지 |
| 닫기·재실행 | 설정·기록 보존, 중복 기록·이벤트 없음 |
| 한국어/영어·키보드 | 번역·레이아웃·초점·재시도 동선 정상 |

단위 테스트는 상태 전이·귀속·예산·원문 변동처럼 결함을 잡을 수 있는 부분에 둔다. 문구를 그대로 복사한 테스트를 대량 추가하지 않는다. 실제 에이전트 왕복은 모의 테스트 통과만으로 대체하지 않는다.

구현 후 저장소의 타입·관련 테스트·린트·빌드 요구를 따른다. 전체 테스트를 반복 실행하기보다 변경 범위와 실패 근거에 맞게 확장한다. 설치본 실행 중 개발 빌드를 피해야 한다는 기존 플랜 메모가 있으므로 실행 환경을 확인한 뒤 검증한다.

### 사용자 관찰 프로토콜

첫 탐색은 대상 사용자 3~5명 규모로 시작할 수 있다. 이는 통계적 검증 표본이 아니라 마찰을 찾는 제안이다. 모집·연락은 사용자가 명시적으로 요청할 때 진행한다.

관찰 과제: “평소 쓰는 프로젝트에서 작은 작업 하나를 하고, 다음 작업을 시작할 때 이전 맥락을 확인해 주세요.” 처음부터 어떤 버튼을 누를지 알려주지 않는다. 도움을 준 지점·실패 원인·실제 도달 단계·다음 작업에서 자발적 재사용 여부를 기록한다. 도움을 받아 성공한 경우를 무도움 성공과 분리한다.

질문 예: 무엇을 해주는 앱으로 이해했는가? 첫 기록을 보고 무엇을 알게 됐는가? 다음 작업에서 어떤 기록을 찾았는가? 다시 쓴 이유 또는 쓰지 않은 이유는 무엇인가? 실제 사례를 묻고 추상적인 만족도만 수집하지 않는다.

## 15. 지표 정의와 판단 규칙

개인정보와 로컬 우선 약속을 유지한다. 서버 텔레메트리를 자동 도입하지 않는다. 초기에는 동의한 관찰 세션의 수기 기록 또는 사용자가 확인하고 내보내는 로컬 진단으로 충분하다. 기록 본문·명령·경로·계정 정보를 동의 없이 외부 수집하지 않는다.

| 지표 | 분모·의미 | 주의점 |
|---|---|---|
| 시작 도달 | 소개를 본 관찰 참가자 중 실제 시작한 사람 | 공개 사이트 전환율과 다름 |
| 준비 성공 | 선택한 경로의 준비 확인을 시작한 사람 중 성공 | 설정 존재만으로 성공 아님 |
| 첫 기록 성공 | 실제 작업을 시작한 사람 중 해당 작업의 일지를 확인한 사람 | 백필·수동·에이전트 기록 출처 구분 |
| 첫 기록까지 시간 | 온보딩 시작부터 해당 일지 확인까지 | 모델 작업 시간과 설정 시간을 분리 |
| 다음 세션 재사용 | 첫 기록 성공 후 다음 작업 기회가 있었던 사람 중 기록을 다시 불러온 사람 | 다음 작업 자체가 없었던 사람은 별도 |
| 유용성 확인 | 기록 재사용 중 구체적 도움 사례가 확인된 경우 | 읽기 횟수로 대체 불가 |

관측 이벤트가 필요하면 `setup_checked`, `journal_confirmed`, `recall_returned`, `context_delivered` 등의 이름을 쓸 수 있으나 제안 이름일 뿐 현존 API가 아니다. 시간·프로젝트 범위·실행 경로·중복 방지 식별·실패 사유 정도의 최소 필드를 먼저 검토한다. 로컬에서도 보존 기간·삭제·내보내기 범위를 결정한다.

기준선이 없으므로 임의의 목표 전환율을 확정하지 않는다. 결과는 “80%”만 쓰지 말고 “관찰 5명 중 4명, 도움 없음”처럼 분모와 조건을 남긴다. 반복해서 같은 설정 단계에서 막히면 온보딩을 수정한다. 첫 기록에는 성공하지만 다음 작업에서 찾지 않으면 메시지·대상·재사용 효용 가설을 다시 검토한다. 관련 없는 기록 때문에 작업이 방해되면 자동 전달 확대를 멈추고 선택·미리보기 방식을 우선한다.

## 16. 기존 플랜과의 관계

- `improvement-round-2026-09-14#acp-journal-draft`: 세션 식별 매핑과 기록 귀속은 첫 성공 판정과 겹칠 수 있다. 기존 항목을 확인하고 중복 구현을 피한다.
- `#eyes-first-run`: 현재 첫 실행 재현 확인과 연결된다. 문서 작성만으로 완료 처리하지 않는다.
- `#eyes-claude-integration`: 실제 실행 경로 검증과 연결된다. 관련 항목의 구체 범위를 다시 읽는다.
- `#star-outreach`: 소개 개편 후 홍보 단계와 연결되나, 미완 항목만 보고 과거 홍보가 없었다고 결론 내리지 않는다.
- `#i18n-finish`: 새 문구는 한국어·영어를 함께 작성하되 전체 i18n 미완을 이번 작업에서 해결했다고 주장하지 않는다.
- `monaco-editor-round` 및 최적화 계획: 이 보고서 때문에 자동 폐기하지 않는다. 제품 우선순위 제안과 기존 결함·유지보수 의무를 분리한다.

이 문서에는 실행 완료 체크를 누적하지 않는다. 구현에 착수할 때 최신 활성 플랜을 읽고 적합한 곳에 넣거나, 별도 실행 플랜을 MCP로 만든다. 논의의 후보와 권고는 현재 보고서에, 실제 진척은 플래너에, 작업 결과는 일지에 둔다.

## 17. 위험과 완화

| 위험 | 완화 |
|---|---|
| 그럴듯한 제품 방향이 실제 수요와 다름 | 한 경로·소수 관찰로 먼저 확인 |
| 메모리가 모델의 판단을 오염 | 근거·시점 표시, 관련성 필터, 미리보기, 예산 제한 |
| 과거 기록이 현재 지시처럼 실행됨 | 자료와 현재 지시 분리, 기존 승인·도구 권한 유지 |
| 오래된 결정이 최신 정답처럼 노출 | 원문·기준 시각·상충 표시 |
| 기존 사용자에게 메뉴 변경 부담 | 추가 진입점부터 도입, 기존 경로 보존 |
| 자동화 약속이 관측 범위를 초과 | 실행 경로별 준비·검색·읽기·전달 단계 구분 |
| 새 계측이 로컬 우선 약속 훼손 | 기본 로컬, 자발적 내보내기, 최소 수집 |
| 모든 에이전트 지원을 한 번에 구현 | 검증 경로 하나 완료 후 확장 |
| 데모와 실제 첫 사용이 다름 | 깨끗한 프로젝트·실제 설치 경로로 재현 |

문제가 생기면 새 이어하기 진입점이나 전달 기능을 비활성화해도 원본 일지·플랜과 기존 탐색이 남아야 한다. 초기 단계는 되돌리기 쉬운 추가·연결 중심으로 구현한다.

## 18. 다음 세션의 첫 작업과 산출물

사용자가 “이 계획대로 구현하라”고 요청하면 Phase 0부터 시작한다. 이미 확인한 사실을 장황하게 다시 조사하지 말고, 마지막 조사 이후 바뀐 소스와 실제 실행 경로를 확인한다.

첫 구현 단위의 추천 범위는 **검증된 실행 경로 하나에서 프로젝트 열기부터 첫 일지 확인까지 연결하기**다. 메뉴 전체 개편이나 새로운 기억 DB 구축부터 시작하지 않는다.

다음 세션이 남겨야 할 산출물:

1. 선택한 실행 경로와 이유, 실제 준비 조건.
2. 현재 흐름의 재현 결과와 변경 전 실패 위치.
3. 수정 파일·상태 전이·기존 기능 재사용 근거.
4. 실제 첫 기록과 다음 세션 재사용 검증 결과. 아직 안 했으면 미검증으로 명시.
5. 관련 일지와 플래너 상태, 다음 한 작업.

핵심 성공 장면은 “설정을 끝냈다” 또는 “일지가 많이 쌓였다”가 아니다. **이전 작업의 근거가 다음 작업에서 실제로 다시 열리고, 사용자가 그 연결을 이해할 수 있는 상태**다.
