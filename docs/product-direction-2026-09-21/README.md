## 사용자 요청과 현재 상태

사용자는 앱 사용자가 늘지 않는 이유를 직접 진단하고, 어떻게 바꿀지 제안한 뒤, 다른 세션에 전달할 상세 문서로 남기라고 요청했습니다. 현재 완료한 것은 조사와 계획 문서 작성입니다. 앱 코드 변경·배포·외부 사용자 연락은 이번 문서 작업에 포함되지 않았습니다.

핵심 제안: **AI가 지난 작업의 결정과 실패를 찾아 다음 작업을 이어가도록, 첫 기록 성공부터 다음 세션 재사용까지 연결한다.**

추천 첫 구현 단위: 검증된 실행 경로 하나에서 `프로젝트 열기 → 준비 확인 → 실제 작업 → 해당 세션의 첫 일지 확인`을 연결합니다. 이어서 `다음 세션 → 관련 기록 찾기 → 전달 내용 확인 → 작업 시작`을 검증합니다.

## 반드시 지킬 해석

- 사용자 0명·전환율·재방문율은 확인하지 못했습니다. 제품 구조에서 발견한 장벽을 실제 이탈 원인으로 확정하지 마세요.
- 빈 화면 CTA·백필·플러그인 안내·회상 기능은 이미 있습니다. 새로 만들기 전에 기존 경로를 확인하세요.
- `recallUsage`는 런타임 사용량입니다. 영속적 재사용·효용 지표가 아닙니다.
- AI 패널의 회상 기능을 ACP·외부 MCP에도 동일하게 연결돼 있다고 가정하지 마세요.
- 검색됨, 원문 반환됨, 요청에 포함됨, 답변에서 참조됨, 실제 도움 됨은 다른 상태입니다.
- 마법사 완료와 기록 성공, 기록 성공과 코드 검증을 구분하세요.
- 보고서의 UI·이벤트 이름은 제안입니다. 현재 API나 구현 완료 기능으로 해석하지 마세요.
- 제안한 메뉴 축소는 초기 구현의 선행조건이 아닙니다. 기존 편집기·터미널·단축키를 일괄 삭제하지 마세요.

## 구현을 요청받은 세션의 시작 절차

1. 현재 사용자 지시로 구현 범위를 확인합니다. 단순히 문서를 전달받은 것을 외부 게시·연락 허가로 해석하지 않습니다.
2. `git status --short`, 관련 `journal_search`, `plan_status`로 최신 변경과 중복 과제를 확인합니다.
3. `agent_register` 후 수정할 경로를 `claim_paths`로 선점합니다. 다른 세션의 변경은 되돌리지 않습니다.
4. 보고서 Phase 0의 실제 첫 사용 재현과 경로별 관측 가능 범위를 확인합니다.
5. Phase 1의 작은 구현 단위부터 진행합니다. 사용자에게 이미 승인된 범위는 반복 확인하지 않습니다.
6. 테스트·실제 에이전트 왕복을 구분해서 검증하고, 작업 단위마다 일지를 기록합니다.
7. 대응 플래너 항목을 최신 hash로 갱신합니다. 보고서나 논의 문서를 진척 원장처럼 사용하지 않습니다.
