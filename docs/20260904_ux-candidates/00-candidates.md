# UX 후보 조사 (2026-09-04)

코드 화면 트리에 **포인터 드래그 이동**을 넣으면서 그 주변에서 실제로 걸리는
자리들을 함께 조사했다. 일반론이 아니라 **이 저장소에서 확인한 사실**만 적는다 —
각 항목에 "지금 코드가 어떤 상태인지"를 근거로 달았다.

순위는 `막힌 사람 수 × 막히는 빈도 ÷ 비용` 으로 매겼다.

---

## P0 — 방금 넣은 드래그가 곧바로 부딪히는 것

> **P0 네 항목 전부 구현됨** (2026-09-04).

### 1. 이동 되돌리기 (토스트 안 [되돌리기]) — ✅ 구현됨
**근거** — `src/lib/toast.ts:19` 에 `ToastAction` 이 이미 있고 여러 화면이 쓴다.
그런데 파일 이동(`runRename`)과 삭제(`confirmDelete`)는 결과 토스트만 띄우고
되돌릴 길을 주지 않는다. 이동은 `code_rename` 의 인자를 뒤집기만 하면 되는
**정확한 역연산**이고, 삭제는 OS 휴지통이라 앱 안에서는 되돌릴 방법이 아예 없다.

**왜 지금** — 드래그는 "손이 미끄러지는" 입력이다. 실수 비용이 어제보다 커졌다.

**결과** — `useFileOps.ts` 가 옮기기·이름 바꾸기를 한 벌(`MovePair[]`)로 다루고
성공한 만큼에만 [되돌리기] 를 단다. 되돌리기는 **역순**이다 — `a→b`, `b→c` 사슬을
앞에서부터 풀면 되돌린 것을 다음 되돌리기가 다시 데려간다.

**삭제에는 달지 않았다.** `trash` 크레이트의 복원 API(`os_limited`)는 소스에서
`cfg(any(windows, all(unix, not(macos), …)))` 로 걸려 있다 — **macOS 에는 아예
없다.** 이 앱의 주 무대에서 프로그램이 휴지통을 되짚을 방법이 없으므로, 눌러도
안 되는 버튼을 다느니 "휴지통으로 보냈습니다" 라고 말하는 편이 정직하고 그
문장이 이미 복구 경로다.

### 2. 다중 선택 (⌘/⇧ 클릭) → 한꺼번에 옮기기·지우기 — ✅ 구현됨
**근거** — `CodeScreenV2` 의 선택은 `selected: string | null` 하나다. 트리에서
파일 열 개를 다른 폴더로 옮기려면 **열 번** 끌어야 한다.

**결과** — 규칙은 전부 `treeSelection.ts`(순수)에 있다. 선택은 `Set` 이 아니라
**`Map<경로, 폴더여부>`** 다: 삭제 확인 문구가 파일/폴더로 갈리는데, 뽑아 둔 경로가
스크롤 밖으로 나가거나 부모가 접힌 뒤에는 트리에서 그 사실을 되찾을 수 없다.

구현하며 나온 함정 둘 — `pruneNested`(폴더와 그 안의 파일을 함께 옮기면 두 번째
이동이 **없는 경로**를 가리킨다)와, ⇧ 범위의 기준을 **보이는 행**으로 한정하는 것
(접힌 폴더의 자식까지 넣으면 고른 적 없는 파일이 조용히 딸려 간다).

### 3. 트리 키보드 이동 (↑↓←→ · Enter · Space · F2 · ⌫) — ✅ 구현됨
**근거** — 트리는 `role="tree"` / `role="treeitem"` 을 쓰지만 `CodeTree.tsx` 에
화살표 처리가 없다 (`onKeyDown` 은 이름 입력칸 하나뿐). WAI-ARIA 트리 규약을
절반만 지키고 있는 셈이고, **드래그를 못 쓰는 사용자에게는 이동 기능이 아예
없는 것**과 같다. 파일 조작은 우클릭 메뉴로만 닿는다.

**결과** — 뜻풀이는 `treeKeys.ts`(순수), 실행은 `useTreeKeys.ts`. WAI-ARIA Tree View
규약대로 **로빙 tabindex** 를 넣었다: 행마다 기본 tabindex 를 두면 파일 300개짜리
저장소에서 Tab 이 300번 걸린다. 서 있던 행이 사라지면(옮김·삭제·필터) 첫 행으로
돌아간다 — 없는 경로가 tabindex 의 주인이면 트리에 **아예 들어갈 수 없다**.

`→` 는 접힌 폴더를 열고 열린 폴더에서는 첫 자식으로 들어간다, `←` 는 열린 폴더를
접고 그 밖에서는 부모로 올라간다 (VS Code 와 같다). ⌘·⌃·⌥ 조합은 트리가 손대지
않는다 — 그 자리는 ⌘X/⌘V 의 것이다.

### 4. ⌘X → ⌘V 로 옮기기 — ✅ 구현됨
**근거** — ⌘V 는 이미 `useCodeImport.pasteFiles` 가 Finder 클립보드를 받는다.
앱 안에서 잘라낸 경로면 가져오기 대신 이동으로 분기하면 되고, 드래그가 어려운
깊은 트리(스크롤 두 번 이상)에서는 이쪽이 늘 더 빠르다.

**결과** — 한 키가 두 갈래를 나눠 쓴다: 잘라 둔 것이 있으면 **옮기고**, 없으면
Finder 클립보드를 들여온다. 사용자에게는 같은 동작("여기에 넣어라")이고 어디서
왔는지는 앱이 가른다. 잘린 행은 사라지지 않고 점선으로 흐려진다 — ⌘V 를 안 눌러도
안전하다는 것이 보여야 한다. 우클릭 메뉴에도 [잘라내기]·[여기에 붙여넣기] 가 붙고
(붙여넣기는 잘라 둔 것이 있을 때만 — 회색으로 놔두면 왜 못 누르는지 모른다),
⌘/ 치트시트의 '코드' 묶음에 트리 다섯 줄이 들어갔다.

## P1 — 플래너

### 5. 계획 항목 드래그로 순서·단계 바꾸기
**근거** — `PlanEditOp`(bindings.ts:5036)에 `move_phase` 는 있는데 **`move_item`
이 없다**. 단계는 올리고 내릴 수 있지만 항목은 만든 자리에 영영 묶인다. 계획을
살아 있는 문서로 쓰겠다는 제품 전제(`docs/planner-upgrade/`)와 정면으로 어긋난다.

**비용** — 백엔드 `PlanEditOp::move_item { item_id, phase, before }` 한 줄 +
마크다운 SSOT 재작성. 프런트는 이번 `useTreeDrag` 를 거의 그대로 쓸 수 있다.

### 6. 호버 카드에서 바로 행동하기
**근거** — 오늘 넣은 `PlanHoverCard` 는 `pointer-events: none` 인 순수 정보판이다.
"보관", "일지 열기", "id 복사" 를 여기에 붙이면 행을 두 줄로 유지한 채 동작을
줄 수 있다. 다만 카드가 인터랙티브가 되는 순간 손이 카드로 건너갈 시간(안전
삼각형)이 필요해져 난이도가 한 단계 올라간다 — 지금 당장은 아니다.

## P2 — 전역

### 7. 화면 뒤로/앞으로 (⌘[ / ⌘])
**근거** — 화면이 13개인데(`navRegistry.ts`) `state.uiV2View` 는 **현재 값 하나**만
들고 있다. 일지 → 코드 → 그래프로 건너간 뒤 "방금 그 일지" 로 돌아오려면 ⌘번호를
외우거나 목록을 다시 찾아야 한다. 브라우저·IDE 가 전부 갖고 있는 것이라 없으면
곧바로 티가 난다.

**비용** — 작다. `WorkspaceContext` 에 링 버퍼 하나 + 단축키 두 개. 다만 화면
안의 위치(어느 파일·어느 계획)까지 기억해야 진짜 뒤로가기가 된다.

### 8. 목록 행의 잘린 글자 되돌려 주기 — 이번 카드의 확장
**근거** — 오늘 계획 레일에만 넣었다. 같은 문제가 저널 타임라인·검색 결과·
문서 트리·코드 탭에도 그대로 있다(전부 `text-overflow: ellipsis`). 카드 껍데기를
공용 프리미티브로 올리면(`.pln-hover` → `.hovercard`) 나머지는 붙이기만 하면 된다.

## 조사했지만 **하지 말자**고 본 것

- **트리 인라인 미리보기(호버로 파일 내용 엿보기)** — 미리보기 탭(`preview`)이
  이미 같은 일을 더 정확하게 한다. 두 개를 두면 어느 쪽이 진짜인지 흐려진다.
- **애니메이션 강화** — `base.css:48` 이 `prefers-reduced-motion` 을 이미 존중한다.
  여기서 더 늘리는 것은 de-AI 규율(`scripts/check-design-discipline.mjs`)과 싸운다.
- **트리 가상 스크롤** — 지연 로딩이라 한 번에 그리는 행이 폴더 한 단계뿐이다.
  아직 문제가 아니다.
