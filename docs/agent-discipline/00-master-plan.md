# 00. 에이전트 규율(스킬·규칙) 재설계 — 마스터 플랜 (SSOT)

> 상위 선례: [`../claude-integration/00-master-plan.md`](../claude-integration/00-master-plan.md) (CI0~CI8 이 만든 표면을 재배치한다).

## 0. Executive Summary

가설을 세우기 전에 **이 저장소의 Claude Code transcript 136개를 직접 계측**했다. 결과는 "안 쓴다"가 아니었다.

| 계측 | 값 | 해석 |
|---|---|---|
| `Skill` 도구 발동 | **11회 / 136 세션** (0.08회/세션) | 스킬은 사실상 죽어 있다 |
| 그중 `oculpm:*` 스킬 | **1회** | 우리가 배포한 스킬조차 안 걸린다 |
| 이 저장소 `.claude/skills/` | **디렉터리 없음** | 샵 28종·갤러리 5종을 만든 저장소가 정작 0개 설치 |
| 이 저장소 `.claude/rules/` | **디렉터리 없음** | 프로젝트 규칙 0개 |
| 전역 규칙 자동 주입 | **1,812회 누적 / 세션당 30파일·90KB(≈22K 토큰)** | 규칙은 안 쓰이는 게 아니라 **폭주 중** |
| 그 30개의 정체 | react-native 8 · arkts(HarmonyOS) 5 · vue 1 포함 | **Tauri 데스크탑 앱에 무관한 규칙이 매 세션 주입** |

원인은 규칙 파일의 glob 이다. ECC 규칙들이 `paths: ["**/*.ts", "**/*.tsx"]` 로 걸려 있어, TS 파일 하나만 만져도 React Native·Vue·HarmonyOS 규율이 통째로 딸려온다. **이걸 보여주는 도구가 세상에 없고, 그걸 보여줘야 할 도구가 우리 규칙 허브다.**

그러므로 결론:

> 문제는 기능이 부족한 게 아니라, **현재 설계가 "파일 관리자"라는 것**이다.
> 사용자는 파일을 관리하고 싶은 게 아니라 **에이전트 행동을 고치고 싶다.**
> 관리 화면은 동기가 없을 때 가는 곳이라, 영원히 안 간다.

재설계의 명령: **① 발동을 계측해 보이게 하고, ② 만드는 순간을 화면이 아니라 사건 위로 옮기고, ③ 만든 뒤에도 살아 있음을 계속 증명하게 한다.**

## 1. 현재 설계의 실패 지점

`SkillsScreenV2` = 12번째 화면 · 5탭 허브(`스킬 | 샵 | 규칙 | 훅 | 플러그인`) · 각 탭이 2-pane CRUD.

| # | 실패 | 근거 |
|---|---|---|
| F1 | **위치가 사건에서 멀다** | 규칙은 "에이전트가 또 같은 실수를 했을 때" 태어난다. 그 순간 사용자는 일지·diff·터미널에 있지, 12번째 화면에 없다 |
| F2 | **효과가 0으로 관측된다** | 만든 규칙/스킬이 실제로 걸렸는지 앱이 모른다. 피드백 없는 행동은 습관이 되지 않는다 |
| F3 | **승격 루프가 갇혀 있다** | `rule_promotion`·`skill_promotion`(CI4/CI5) 은 완성돼 있는데 **회고 화면에만** 노출된다. 회고는 매일 가는 곳이 아니다 |
| F4 | **생성 비용이 높다** | 규칙=빈 템플릿, 스킬=영문 `description` 을 사람이 잘 써야 발동. 그런데 잘 썼는지 알 방법이 없다(F2 와 순환) |
| F5 | **결정 비용이 높다** | 샵 28종을 훑고 고르는 건 작업이 아니라 쇼핑이다. `stack_detect.rs` 가 이미 스택을 아는데 안 쓴다 |
| F6 | **가장 큰 실제 손해가 안 보인다** | 세션당 ~22K 토큰의 무관 규칙 주입. 규칙 허브가 이걸 안 보여준다 |

## 2. 재설계 원칙

1. **계측 없이는 습관 없다.** 규칙·스킬은 "발동했다"가 보여야 산다. 안 보이면 자산이 아니라 쓰레기다.
2. **만드는 순간은 화면이 아니라 사건이다.** 진입점을 일지·diff·터미널·Today 로 분산시키고, 허브는 결과를 모아 보는 곳으로 강등한다.
3. **규칙은 자산이 아니라 재고다.** 안 걸리는 규칙은 비용(컨텍스트)만 먹는다. 스스로 정리를 제안하게 만든다.
4. **draft=AI, decision=사람** — CI4/CI5 의 구조적 보장을 그대로 승계한다. 어떤 제안도 승인 없이 파일을 쓰지 않는다.

## 3. 아키텍처 결정

### D1 — 발동 원장(Firing Ledger): transcript 에서 결정론적으로 관측한다 {#d1}

Claude Code transcript JSONL 에 **관측 가능한 두 신호**가 실재한다 (2026-08-29 실측):

```jsonc
// 규칙 주입 — 조건부 로드가 실제로 걸린 순간
{"type":"attachment","attachment":{"type":"nested_memory","path":"/Users/…/.claude/rules/ecc/arkts/coding-style.md"}}
// 스킬 발동
{"name":"Skill","input":{"skill":"oculpm:oculpm-journal"}}
```

- 신규 모듈 `oculpm/firing_ledger.rs` — `transcript.rs` 의 방어적 파싱 규율을 그대로 승계(모르는 라인 무시·한 줄 깨져도 계속).
- 스캔 대상은 `~/.claude/projects/<경로슬러그>/*.jsonl`. 훅 옵인 없이도 동작한다(훅이 켜져 있으면 `transcript_path` 로 정확도 상승).
- 결과는 **파생 캐시**(SQLite `context_firings`) — SSOT 는 여전히 transcript. 재빌드 가능해야 한다.
- 산출 지표(규칙/스킬 단위): `발동 횟수(30일) · 마지막 발동 · 주입 바이트 합 · 발동 세션 수`.

**이것이 나머지 전부의 전제다.** 계측이 있어야 정리 제안·범위 교정·트리거 교정이 성립한다.

### D2 — 화면: 5탭 관리자 → 1화면 3존 {#d2}

`스킬 | 샵 | 규칙 | 훅 | 플러그인` 5탭을 **"지금 이 프로젝트의 에이전트에게 걸려 있는 것"** 단일 뷰로 접는다. 종류(스킬/규칙/훅/CLAUDE.md/MCP)는 필터일 뿐 탭이 아니다.

- **존 1 — 컨텍스트 예산 바** (상단 1줄)
  세션당 주입량 게이지: `CLAUDE.md + 항상-로드 규칙 + 조건부 규칙(실측 주입) + 스킬 description`.
  기준선 = 이 저장소 실측 **90KB / 세션**. 무관 항목은 경고 조각으로 분리 표시 → 클릭하면 존 3 의 정리 카드로 점프.
- **존 2 — 걸려 있는 것 (Live)**
  단일 리스트. 각 행에 **발동 배지**(`30일 12회` / `마지막 8/27` / `한 번도 안 걸림`). 기본 정렬 = 발동 많은 순.
  발동 0회 항목은 하단 **"휴면"** 섹션으로 자동 강등(접힘) — 목록이 스스로 청소된다.
- **존 3 — 제안 인박스 (Inbox)**
  액션 카드 큐. 승인 시에만 파일이 쓰인다.

| 카드 | 트리거 | 재사용 |
|---|---|---|
| 실패→규칙 승격 | 같은 영역 error/bug 2건+ | `rule_promotion.rs` (완성) |
| 반복→스킬 승격 | 같은 tag 일지 3건+ | `skill_promotion.rs` (완성) |
| **범위 교정** | 주입 N회인데 대상 확장자 파일 0개 | 신규 + `stack_detect.rs` |
| **정리** | 30일 발동 0회 | 신규 (D1 의존) |
| **트리거 교정** | 스킬 발동 0회 | 신규 — `description` LLM 재작성 제안 |

- 편집은 화면이 아니라 모달/`code` 화면 위임으로 축소한다(2-pane 편집기 2벌 유지 비용 제거).
- 샵·플러그인 탭은 존 3 하단 **"추가하기"** 로 흡수 — 쇼핑을 독립 탭에서 빼고, 스택 감지 추천 3종만 먼저 보인다(F5).

### D3 — 진입점을 사건 위로 분산 {#d3}

허브를 고쳐도 안 가면 소용없다. **만들 이유가 생기는 화면마다 버튼 하나**를 둔다.

| 위치 | 액션 | 근거 |
|---|---|---|
| 일지 상세(bug/error) | "이걸 규칙으로" | 실패를 본 직후가 승격의 자연 시점 |
| Diff 화면 | "이 변경을 규칙으로" | 리뷰 중 발견한 패턴을 그 자리에서 |
| 터미널 명령 블록 | "이 절차를 스킬로" | 명령 블록이 이미 캡처된다 (5c20e32) — 같은 시퀀스 3회 반복 감지 |
| Today | 제안 카드 N건 | 회고(F3) 대신 **매일 보는 곳**으로 이동 |
| ⌘K 팔레트 | "규칙 추가" / "스킬 추가" | 어디서든 |

회고 화면의 `RuleCandidates` / `SkillCandidates` 는 **컴포넌트를 그대로 재사용**해 Today 로 승격시킨다(신규 백엔드 0).

### D4 — 규칙 다이어트: 첫 체감 가치 {#d4}

이 저장소에서 세션당 ~22K 토큰이 무관 규칙에 쓰인다. 되찾는 것이 "규칙 기능"의 **첫 번째 눈에 보이는 이득**이다.

- 진단: `주입 횟수 × 대상 확장자 실존 여부` 로 무관 규칙을 결정적으로 지목 (LLM 0).
  예: `arkts/coding-style.md` 56회 주입 · 이 프로젝트 `.ets` 파일 0개 → **무관 확정**.
- 처방 제안: ① `paths` 축소(전역 파일 수정 — 소유권상 반드시 승인 필요) ② 해당 규칙 비활성 ③ 무시.
- **전역 파일은 사용자 것이다.** 우리 소유 마커가 없는 파일은 제안만 하고, 승인 시에도 원본 백업 후 최소 행 치환(`rulesModel.setRulePaths` 규율 = 다른 키·본문 바이트 보존).

### D5 — 발동을 만들어내는 쪽(옵인, 후순위) {#d5}

`hooks/plan-context.sh` 가 `additionalContext` 주입 선례를 만들었다. 같은 방식의 **규칙 리마인더**(PreToolUse Edit|Write 시 매칭 규칙의 *제목만* 1줄)는 가능하지만, 본문은 Claude Code 가 이미 네이티브로 로드하므로 **중복 주입 금지**. D1~D4 로 계측·정리가 선 다음에만 검토한다. 예산을 늘리는 기능은 예산을 볼 수 있게 된 뒤에 붙인다.
