## 3. 기술 선택 — 라이브러리를 넣지 않는다

`react-i18next` / `react-intl` 을 넣지 않고 **~80줄짜리 자체 구현**으로 갑니다.

근거:

- 필요한 기능이 좁습니다. 언어 2개, 복수형 규칙 불필요(한국어는 복수형이 없고 영어는 이 UI 에서 거의 안 씀), 지연 로딩 불필요(사전 2개가 수십 KB), 네임스페이스 불필요.
- `react-i18next` 는 의존성 트리와 초기화 흐름을 끌고 옵니다. 이 앱은 이미 `SettingsContext`(SQLite 백엔드)라는 설정 채널이 있어서 그 위에 얹는 게 더 짧습니다.
- 번들 크기가 실제로 중요합니다 — `ShellV2` 청크 분할(`ShellV2.tsx:11-18`)에 공들인 코드베이스라 무상관 의존성을 늘리는 건 결이 안 맞습니다.

날짜·숫자 포맷은 표준 `Intl.DateTimeFormat` / `Intl.NumberFormat` 을 씁니다.

## 4. 설계

### 4.1 사전 구조

> **구현 완료 (Phase 0, 2026-08-11).** 아래는 실제 코드와 일치합니다.

```
src/i18n/
  index.ts        언어 스토어 + t() / tAll() / useT() / resolveLang
  ko.ts           한국어 (정본 — 키 집합을 여기서 정의)
  en.ts           영어
```

키는 **점 표기 flat** 입니다. 중첩 객체로 하면 경로 타입(`"nav.today"` 를 중첩에서 유도)에 타입 곡예가 필요한데, flat 은 `keyof typeof ko` 만으로 완전한 타입 안전을 얻습니다. grep 도 쉽습니다 — `"nav.today"` 하나로 사전과 사용처가 함께 잡힙니다.

```ts
export const ko = {
  "nav.today": "Today",
  "nav.journal": "작업 일지",
  "settings.language.title": "언어",
  "common.cancel": "취소",
} as const;
```

`en.ts` 는 `ko.ts` 의 키 집합으로 제약됩니다:

```ts
export const en: Record<keyof typeof ko, string> = { … };
```

이러면 **키 누락이 타입 에러**가 됩니다 — `pnpm typecheck` 가 사전 완결성을 검증하므로 별도 검사기도, 런타임 테스트도 필요 없습니다. (초과 키도 excess property 로 잡힙니다.)

타입이 못 잡는 것 — 빈 문자열 값, 영어 사전에 남은 한글 — 은 `__tests__/i18n.test.ts` 가 덮습니다.

### 4.1.1 언어를 React 컨텍스트가 아니라 모듈 스토어에 둔다

번역 대상의 상당수가 컴포넌트가 아니라 **순수 모듈**에 있습니다 — `lib/toast.ts`, `lib/updater.ts`, `features/planner/planList.ts`, `features/projects/managerModel.ts`. 컨텍스트에만 두면 이들은 `t()` 를 못 부릅니다.

```
SQLite settings.language → SettingsContext → setLangSetting() → 모듈 스토어
                                                                  ├─ t()     (순수 모듈에서 직접)
                                                                  └─ useT()  (React, useSyncExternalStore 구독)
```

`useT()` 의 `t` 아이덴티티는 **언어가 바뀔 때만** 변합니다 (`useMemo([lang])`). 렌더마다 새 함수를 돌려주면 `t` 를 deps 에 넣은 소비처 `useMemo`(⌘K 팔레트 아이템 목록)가 매 렌더 재계산됩니다.

### 4.1.2 검색 색인은 `tAll()`

⌘K 팔레트는 현재 UI 언어와 무관하게 **양 언어로** 찾혀야 합니다. 한국어 사용자가 영어 모드를 켰다고 "일지" 로 못 찾으면 손버릇이 끊깁니다.

한 문자열에 두 언어를 욱여넣는 대신(기존 `alias: "journal 일지 timeline 기록"`), 사전에 언어별로 두고 소비처가 `tAll(key)` 로 전 언어 값을 합칩니다. 사람이 양쪽 언어를 기억해 넣어야 하는 규율이 **구조적 보장**으로 바뀝니다.

### 4.2 보간

`t()` 는 두 번째 인자로 치환값을 받습니다:

```ts
t("journal.entryCount", { n: 12 })
// ko: "일지 {n}건"   en: "{n} entries"
```

React 노드 보간(`<b>` 등)이 필요한 몇 곳은 문자열을 쪼개는 대신 컴포넌트로 만듭니다 — 번역 파일에 JSX 가 들어가지 않게 합니다.

### 4.3 언어 결정

`Settings` (`src/lib/settings.ts:70`)에 필드 추가:

```ts
language: "system" | "ko" | "en";   // 기본 "system"
```

`"system"` 은 `navigator.language` 로 해석합니다 (`ko*` → 한국어, 그 외 → 영어).

`SettingsContext` 는 SQLite 백엔드(`settings_*` 커맨드)라 **localStorage 창 격리 작업과 완전히 무관**합니다. 모든 창이 같은 값을 보고, 모바일 웹도 같은 설정을 읽습니다 ([00-master-plan.md](00-master-plan.md) D4).

설정 UI 는 `SettingsPanel` 의 `appearance` 탭에 넣습니다 (테마·글자 크기 옆).

### 4.4 백엔드 — 언어를 인자로 받는다

Rust 쪽은 사전을 두지 않습니다. **에러를 코드로 반환하고 프런트가 번역**하는 게 원칙적으로 맞지만, 130곳을 전부 코드화하면 작업량이 커지고 기존 `Result<_, String>` 계약이 전부 바뀝니다.

절충: **Rust 는 영어만 반환하고, 프런트가 알려진 메시지를 번역 사전에서 찾아 매핑**합니다.

```ts
// 백엔드 에러를 표시 문자열로 — 매칭 실패 시 원문 그대로 (영어)
function tError(raw: string): string { … }
```

이러면:
- Rust 변경이 130곳의 **한글 → 영어 치환**으로 끝납니다 (계약 변경 없음)
- 영어 사용자는 항상 읽을 수 있는 메시지를 봅니다
- 한국어 사용자는 자주 보는 에러부터 점진적으로 사전에 추가하면 됩니다 (매핑 실패해도 영어로 표시될 뿐 깨지지 않음)

완벽하진 않지만 비용 대비 효과가 가장 좋습니다. 에러 코드 도입은 후속 라운드로 기록합니다.

### 4.5 LLM 프롬프트

프롬프트 12파일:

```
commands/  summary.rs · overview.rs · retro.rs · plan.rs · greenfield.rs
           rule_promotion.rs · skill_promotion.rs
oculpm/    reconcile.rs · journal_draft.rs · rule_promotion.rs
           skill_promotion.rs · planner/ai.rs
```

각 프롬프트 빌더에 `lang: &str` 파라미터를 추가하고, 프롬프트 끝에 출력 언어 지시를 붙입니다:

```rust
fn output_language_directive(lang: &str) -> &'static str {
    match lang {
        "en" => "Respond in English.",
        _ => "한국어로 답하세요.",
    }
}
```

프롬프트 본문 자체를 두 벌로 유지하지 **않습니다** — 본문은 한국어 그대로 두고 출력 언어만 지시합니다. 이유: 프롬프트 본문은 모델에게 주는 지시문이지 사용자에게 보이는 문자열이 아니고, 두 벌을 유지하면 한쪽만 고치는 드리프트가 반드시 생깁니다. LLM 은 한국어 지시 + 영어 출력 요구를 문제없이 처리합니다.

단, `plan_dispatch_prompt` (`commands/plan.rs:543`)처럼 **사용자가 복사해서 외부 에이전트에 붙여넣는** 프롬프트는 예외 — 사용자가 읽는 산출물이므로 본문도 번역합니다.

`lang` 은 커맨드 호출 시 프런트가 넘기거나, Rust 가 `settings_get("language")` 로 직접 읽습니다. 후자가 인자 전파 없이 끝나므로 더 낫습니다.

## 5. 회귀 방지 게이트 — Phase 0 의 핵심 산출물

`scripts/check-no-hardcoded-korean.mjs` 를 만들고 `pnpm lint` 에 물립니다.
`scripts/check-no-localstorage.mjs` 와 **같은 구조**(zero-dep Node walker + allowlist)를 그대로 복제합니다.

```js
// src/ 를 걸으며 legacy 제외
// 주석(//, *, /*)과 bindings.ts 를 건너뛰고
// 따옴표·템플릿리터럴·JSX 텍스트 안의 [가-힣] 를 찾아 위반 보고
// ALLOWLIST 에 있는 파일은 통과
```

**핵심은 allowlist 를 역방향으로 쓴다는 것입니다.** Phase 0 에서 현재 한글이 있는 파일을 전부 allowlist 에 넣고 통과시킵니다. **실측 130개** — rg 로 센 133개와 다른 이유는 스캐너가 주석 안 한글을 정확히 제외하기 때문입니다 (그 차이가 곧 이 검사기가 라인 정규식이 아니어야 하는 이유). Phase 2 에서 파일을 하나 번역할 때마다 **allowlist 에서 한 줄씩 뺍니다.**

이 방식의 장점:

- Phase 0 직후부터 **신규 파일은 한글 하드코딩이 불가능**합니다 → Phase 1(멀티 창)의 새 UI 가 자동으로 `t()` 로 작성됩니다
- Phase 2 의 진척도가 `PENDING.size` 로 정확히 측정됩니다 (130 → 0)
- 이미 끝낸 파일의 회귀가 즉시 잡힙니다

Phase 2 완료 기준 = **`PENDING` 이 빈 배열** (`PERMANENT` 만 남은 상태).

기계적 직역을 피합니다. 이 앱의 한국어 카피는 톤이 잡혀 있습니다 ("오늘 기록된 작업이 없어요", "규칙 다시 보내기"). 영어도 같은 결로 갑니다:

| 작업 일지 | Work Journal | Work Diary / Task Log |
| 문제 해결 | Discussions | Problem Solving |
| 변경 diff | Changes | Change Diff |
| 회고 | Retro | Retrospective (길어서 사이드바가 깨짐) |

**레이아웃 리스크:** 영어는 한국어보다 20~40% 깁니다. 248px 고정 사이드바(`ShellV2`)와 툴바 칩이 특히 위험합니다. Phase 2 마지막에 영어 모드로 12화면을 순회하며 오버플로를 잡습니다 — 축약보다 `text-overflow: ellipsis` + `title` 툴팁을 우선합니다.

## 8. 테스트

| 대상 | 방법 |
|---|---|
| 사전 완결성 | `en: Dict = {…}` 타입 제약 → `pnpm typecheck` 가 자동 검증 |
| 하드코딩 회귀 | `pnpm lint` (§5) |
| `t()` 보간 | 단위 테스트 — 치환·누락 키 폴백(`ko` → 키 문자열) |
| 언어 전환 | `SettingsContext` 를 `en` 으로 두고 주요 화면 렌더 → 한글 미검출 assert |
| a11y | 기존 `__tests__/a11y_screens.test.tsx` 를 양쪽 언어로 돌림 (`aria-label` 275곳이 번역 대상이라 회귀 위험이 실재) |

기존 테스트가 한글 문자열로 요소를 찾는 곳(`getByText("취소")` 등)은 전부 갱신 대상입니다. Phase 2 진행 중 각 묶음에서 함께 처리합니다.
