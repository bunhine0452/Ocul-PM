## 01. 경영진 요약: 무엇을 바꾸면 10점인가

Ocul-PM은 이미 아이디어 검증 단계를 상당히 넘어섰다. 마크다운을 원본으로 유지하는 로컬 데이터 모델, 여러 에이전트와의 연결, 일지와 변경 내역의 결합, 플래너, 자동 검사, 네이티브 앱 배포까지 갖췄다. 이번 검토에서 프런트 테스트 2,711개와 타입 검사, 프로덕션 빌드가 통과했다. 따라서 출발점은 “기초부터 다시 만들기”가 아니다.

현재 가장 중요한 간극은 다음 다섯 가지다.

1. **자동 기록의 약속과 실측 사이의 간극.** 기록 기능과 누락 감지 코드는 있지만, 최신 지원 조합별로 실제 작업이 얼마나 완전하게 기록되는지 공개된 근거가 더 필요하다.
2. **동시성·장애 상황의 보존 보장.** 플래너의 CAS와 문서 잠금은 좋은 기반이다. 신규 일지 생성, 재시도, 강제 종료, 디스크 오류까지 같은 수준의 보장을 확장해야 한다.
3. **기록·검토·정확성의 구분.** 일지가 존재한다는 사실, 변경 파일이 일지에 포함됐다는 사실, 테스트가 통과했다는 사실, 사용자가 확인했다는 사실은 서로 다른 상태다.
4. **핵심 사용 흐름과 기능 범위의 간극.** 편집기·디버거·터미널 등 풍부한 기능이 기록과 검토라는 첫 가치를 가릴 수 있다. 기존 기능을 무조건 제거하기보다 기본 노출을 단순화해야 한다.
5. **좋은 개발 관행과 배포 증거의 간극.** CI 검사는 폭넓지만, 배포 태그의 커밋이 검사를 통과했는지와 실제 설치·업데이트 경로까지 연결된 증거가 필요하다.

### 1.1 최우선 투자 순서

| 순서 | 투자 | 사용자가 얻는 변화 | 통과 증거 |
|---|---|---|---|
| 1 | 기록 저장 계약 | 완료된 기록이 조용히 사라지지 않음 | 병렬·재시도·강제 종료·복구 시험 |
| 2 | 상태와 출처 모델 | 무엇이 확인됐고 무엇이 모르는 상태인지 이해 | UI·도구·파일·캐시의 상태 일치 |
| 3 | 최신 기록 벤치마크 | 지원 범위를 믿고 선택 | 고정 조건 반복 실험과 실패 원자료 |
| 4 | 첫 사용·복귀 사용 흐름 | 설정 뒤 가치까지 빠르게 도달 | 첫 기록·첫 검토·맥락 회수 실험 |
| 5 | 배포·보안·복구 검증 | 업데이트와 장애 후에도 안전하게 사용 | 태그 검사·서명 검사·복구 리허설 |

### 1.2 10점의 의미

10/10은 결함이 영원히 없다는 뜻이 아니다. **명시한 지원 범위 안에서 핵심 약속을 반복 검증했고, 실패가 드러나며, 복구할 수 있고, 실제 사용자에게 효용이 확인된 상태**를 의미한다. 이 보고서에 있는 기능을 모두 추가했다고 자동으로 점수가 오르지 않는다. 완료 증거가 있어야 한다.

기존 7.5점은 종합적인 정성 판단이었다. 이후 평가는 100점 가중표와 필수 통과 조건을 사용한다. 이전의 다섯 항목 점수를 새 표에 기계적으로 환산하지 않는다. 평가 기준을 더 정밀하게 만들었기 때문이다.

### 1.3 하지 않아도 되는 일

10점을 받기 위해 Windows·모바일·기업용 권한 관리·모든 에이전트·완전한 IDE를 동시에 완성할 필요는 없다. 지원 범위를 좁고 정직하게 선언하고 그 안에서 탁월하면 된다. 유료 서비스 출시나 사용자 수 증가도 기술적 신뢰성의 대체 증거가 아니다.

### 2.4 중요한 정정과 보완

**동시성 보호가 전반적으로 없는 프로젝트가 아니다.** 플래너에는 내용 해시 기반 CAS, 프로세스 간 잠금, 두 프로세스 경쟁 테스트가 있다. `cas.rs`는 공통 문서 보호를 설명한다. 개선 과제는 그 기반을 재활용하여 신규 생성과 다른 쓰기 경로의 빈틈을 검증하는 것이다. [S06] · [S07]

**성능 측정이 전혀 없는 것도 아니다.** 저장소에는 2026년 9월 4일 기준선과 측정용 테스트가 있다. 그 문서는 실제 병목과 기각된 추정을 구분한다. 보고서의 성능 과제는 기존 측정을 최신 버전·실제 웹뷰·지원 하드웨어로 확장하는 것이다. [S12]

**CSP 비활성은 확인됐지만 실제 침해 경로를 재현한 것은 아니다.** 방어층 강화 과제로 다루고, 단순히 설정 하나로 앱이 취약하다고 단정하지 않는다. [S09] · [S10]

## 03. 제품의 핵심 약속과 지원 범위

### 3.1 권장 제품 약속

> “어떤 에이전트가 무엇을 바꿨는지, 어떤 근거로 완료됐는지, 다음에 무엇을 해야 하는지를 프로젝트 안에 남깁니다.”

이 문장은 세 가지 확인 가능한 결과를 요구한다. 변경의 출처가 있어야 하고, 완료의 근거가 있어야 하며, 다음 행동으로 연결돼야 한다. “자동으로 모든 일을 검증한다”와 같이 실제 관찰 능력을 넘어서는 표현은 사용하지 않는다.

### 3.2 핵심 사용자와 작업

| 사용자 | 반복되는 작업 | 핵심 실패 | 성공 경험 |
|---|---|---|---|
| 개인 개발자 | 하루 여러 에이전트 세션 실행 | 지난 수정 이유를 잊음 | 파일에서 관련 일지와 결정까지 즉시 이동 |
| 소규모 팀 리드 | 여러 변경 검토·주간 정리 | 보고와 실제 변경이 어긋남 | 근거를 가진 브랜치 요약을 검토하고 공유 |
| 장기 프로젝트 유지보수자 | 오래된 결정 재탐색 | 같은 실패를 반복 | 과거 접근·실패·제약을 출처와 함께 회수 |
| 에이전트 집중 사용자 | 여러 작업 병렬 진행 | 기록 충돌·세션 귀속 혼동 | 세션별 기록과 불확실성이 명확히 분리 |

대규모 기업의 인사 평가·개발자 생산성 순위는 기본 목적에서 제외하는 편이 좋다. 일지 수나 코드 변경량은 성과를 공정하게 나타내지 않으며, 그 방향으로 확장하면 기록의 정직성을 해칠 유인이 생긴다.

### 3.3 지원 등급의 분리

현재 문서는 여러 에이전트를 지원한다고 설명하지만, 규칙 파일을 읽는 지원과 MCP·훅·앱 내 세션 지원은 같지 않다. 다음과 같이 등급을 표시한다.

| 등급 | 약속 | 필수 검증 |
|---|---|---|
| 규칙 호환 | 일지 규격과 작업 지침 제공 | 규칙 설치·제거·업데이트 보존 |
| 구조화 기록 | MCP를 통한 읽기·쓰기·플랜 갱신 | 도구 계약·오류 복구·호환 버전 |
| 세션 관측 | 세션 시작·종료와 일부 변경 근거 관측 | 정상 종료·강제 종료·중복 세션 |
| 앱 통합 | 도구 승인·출력·기록을 앱에서 연결 | 실제 앱 E2E·권한·프로세스 복구 |

각 에이전트마다 지원 등급, 검증한 버전, 마지막 검증일을 적는다. 규칙 호환에 불과한 조합에 자동 기록 완전성을 약속하지 않는다. 플랫폼도 공식 배포 대상인 macOS Apple Silicon을 우선 범위로 삼고 다른 플랫폼은 별도 상태로 표시한다. [S01] · [S03]

### 3.4 변경하지 말아야 할 강점

- 마크다운 원본의 가독성과 프로젝트 단위 이동성.
- 클라우드 계정 없이 가능한 기본 기록·검색·검토.
- 앱을 먼저 설치하지 않아도 시작할 수 있는 플러그인 경로.
- 일지와 실제 변경을 함께 보는 구조.
- `Undecided`처럼 모르는 상태를 인정하는 판정 철학.
- 실패한 실험과 기각된 추정을 공개하는 개발 태도.

## 04. 10/10 평가표와 필수 통과 조건

### 4.1 새 가중 평가표

| 영역 | 배점 | 만점에 필요한 증거 |
|---|---:|---|
| 기록 무결성·복구 | 25 | 동시성·재시도·장애·복구 시험과 데이터 보존 계약 |
| 기록 정확성·출처 | 20 | 상태 구분, 세션 귀속, 최신 기록 벤치마크 |
| 사용자 가치·집중도 | 20 | 첫 가치 도달·복귀 사용·맥락 회수 실험 |
| 보안·프라이버시 | 15 | 경계별 위협 모델, 차단 시험, 전송 제어, 지원 범위 검토 |
| 배포·운영 신뢰성 | 10 | 검사된 커밋 배포, 서명·업데이트·복구 검증 |
| 성능·유지보수성 | 10 | 재현 가능한 기준선, 회귀 관리, 모듈 계약 |
| 합계 | 100 | 100점/10 = 10점 |

모든 항목은 “설계됨 → 구현됨 → 검사 통과 → 실제 환경 검증 → 지속 관찰”로 증거가 강화된다. 문서만 있는 상태를 구현 점수로 세지 않는다. 구현이 있어도 사용자 행동에 대한 증거가 없으면 사용자 가치 항목을 만점으로 주지 않는다.

### 4.2 점수와 별도로 적용하는 차단 조건

다음 중 하나라도 열려 있으면 총점이 높아도 10/10을 부여하지 않는다.

1. 지원 경로에서 재현되는 조용한 기록 유실·덮어쓰기.
2. 오류·관측 불가를 성공 또는 검증 완료로 표시하는 경로.
3. 알려진 지원 범위 내 중요 보안 결함에 대한 미조치.
4. 릴리스 커밋과 통과한 검증 결과의 연결 부재.
5. 백업에서 원본을 복구하거나 캐시를 재구축하는 절차의 미검증.
6. 자동 기록·생산성 관련 핵심 홍보 주장의 근거 부재.

이는 영구적인 완벽성을 요구하는 조건이 아니다. 정해진 시점에 알려진 중요 위험을 통제하고 있다는 증거를 요구한다.

### 4.3 목표값의 사용 규칙

이 보고서의 수치는 모두 **제안 목표**다. 기준 하드웨어, 프로젝트 규모, 에이전트 버전, 표본 수를 먼저 정해야 실제 판정에 쓸 수 있다. 불가능하거나 제품 효용과 무관하다는 실측이 나오면 목표를 수정하되 사유를 남긴다. 실패를 숨기기 위해 사후 분모를 바꾸지는 않는다.

## 06. 목표 아키텍처: 하나의 기록 계약, 여러 진입점

### 6.1 권장 계층

| 계층 | 책임 | 금지할 결합 |
|---|---|---|
| 에이전트·CLI·앱·확장 어댑터 | 입력 변환, 신원·능력 전달 | 각자 다른 저장 규칙 구현 |
| 기록 도메인 | 유효성, ID, 출처, 상태 전이, 중복·충돌 처리 | UI 문구와 파일 경로 규칙의 혼합 |
| 저장 계층 | 안전한 생성·교체·잠금·복구 | 요청 성공 전에 미완성 원본 노출 |
| 파생 계층 | SQLite 색인, 검색, 요약용 자료 | 캐시만 갱신하고 원본 성공으로 보고 |
| 화면·도구 응답 | 저장·색인·검토 상태 전달 | 관측 불가를 성공으로 축약 |

기존 Rust 라이브러리와 MCP 서버가 구현을 공유하는 방향은 유지한다. 새 마이크로서비스나 외부 데이터베이스를 추가할 이유는 현재 증거만으로 없다. 핵심은 디렉터리 재배치보다 **모든 진입점이 같은 성공·실패 계약을 사용하게 하는 것**이다.

### 6.2 기본 처리 순서

1. 요청 ID와 세션·프로젝트 식별자를 확인한다.
2. 경로·규격·민감정보 정책을 검사한다.
3. 요청이 재시도인지 판별한다.
4. 신규 문서 생성 또는 기존 문서 갱신의 동시성 규칙을 적용한다.
5. 원본을 완전한 상태로 게시한다.
6. 게시 결과와 내용 해시를 응답한다.
7. 색인을 갱신한다. 실패하면 원본 저장 성공과 색인 지연을 분리해서 보고한다.
8. UI·도구·복구 처리에서 같은 결과 상태를 사용한다.

### 6.3 도입 방식

먼저 기존 쓰기 경로 목록을 만들고 계약 테스트를 씌운다. 신규 일지 생성 하나를 공통 저장 API로 옮긴 뒤 수동 작성·백필·자동 초안 순으로 확대한다. 한 번에 모든 도메인을 재설계하면 회귀 범위가 너무 커진다. 기존 CAS와 잠금을 재사용할 수 있는지부터 검토한다. [S04] · [S05] · [S06]

### 6.4 구조 개선의 완료 기준

- 같은 입력이 앱·MCP·CLI에서 같은 저장 결과를 낸다.
- 신규 생성과 기존 문서 교체의 API가 구분된다.
- 파생 캐시 장애가 원본 성공·실패 판정을 바꾸지 않는다.
- 회복 가능한 오류에 안정적인 오류 코드와 다음 행동이 있다.
- 어댑터별 예외는 능력 차이로 표현되고 저장 규격의 분기로 번지지 않는다.

## 07. 기록 저장 무결성: 신규 생성, 재시도, 충돌

### 7.1 검증할 가설

현재 신규 일지 생성 경로는 `pick_nonconflicting_path`로 사용하지 않는 이름을 고르고 `write_atomic`으로 저장한다. 함수 사이에는 시간이 있다. 두 MCP 프로세스가 같은 분·같은 유형·같은 slug로 요청하면 둘 다 같은 경로가 비어 있다고 판단할 수 있다. 임시 파일 이름이 서로 달라도 최종 대상 이름이 같으면 뒤의 rename이 앞의 문서를 교체할 수 있다. [S04] · [S05]

이는 현재 정적 분석 가설이다. 앱의 다른 보호가 어떤 경로에 적용되는지까지 포함하여 실제 두 프로세스 시험으로 확정한다. 플래너에 잠금이 있다는 이유만으로 신규 일지도 보호된다고 추정하지 않는다.

### 7.2 권장 저장 계약

| 작업 | 계약 |
|---|---|
| 신규 기록 | 이미 존재하는 다른 기록을 절대로 덮어쓰지 않음 |
| 같은 요청 재시도 | 동일 결과를 반환하고 새 기록을 중복 생성하지 않음 |
| 같은 제목의 다른 작업 | 각각 별도 ID로 보존 |
| 기존 기록 정정 | 새 정정 기록 연결 또는 명시적 CAS 편집 정책 적용 |
| 저장 실패 | 성공 응답 금지, 원본 보존, 재시도 가능 여부 표시 |
| 색인 실패 | 저장된 원본은 유지, 화면에 색인 지연과 재처리 경로 제공 |

### 7.3 구현 대안 비교

| 대안 | 장점 | 주의점 | 판단 |
|---|---|---|---|
| 파일명에 고유 ID 추가 | 이름 경쟁을 크게 줄임, 세션과 독립 | 충돌 확률 감소만으로 재시도 중복은 해결되지 않음 | 신규 스키마의 기본 권장 |
| 디렉터리 잠금 후 이름 선택·게시 | 기존 파일명 호환에 유리 | 모든 작성 경로가 같은 잠금을 써야 함 | 이행 단계에 적합 |
| 배타적 파일 생성만 사용 | 이미 존재하면 실패하므로 덮어쓰기 방지 | 최종 파일을 직접 채우면 독자가 부분 파일을 볼 수 있음 | 단독 적용 금지 |
| 완성된 임시 파일의 비덮어쓰기 게시 | 완전성·이름 충돌 방어를 함께 달성 | OS별 게시 연산과 오류 의미 검증 필요 | 지원 OS 기준으로 검토 |
| SQLite를 유일 원본으로 변경 | 트랜잭션 편의 | 마크다운 원본이라는 핵심 강점과 충돌 | 우선순위에서 제외 |

권장 조합은 **고유 기록 ID + 요청 재시도 키 + 완성된 파일 게시 + 필요한 범위의 프로세스 간 잠금**이다. “파일명을 UUID로 바꾸면 끝”이라고 처리하지 않는다.

### 7.4 재시도 키 설계

`request_id`는 네트워크나 프로세스 응답 유실 후 같은 논리 요청을 식별한다. `record_id`는 저장된 기록을 식별한다. 두 값을 분리한다. 동일 `request_id`에 동일 정규화 입력이면 기존 결과를 반환하고, 다른 입력이면 명시적인 충돌로 반환한다.

중복 판정 표는 원본에서 재구축 가능해야 한다. 캐시가 지워졌다고 같은 요청을 다시 기록하면 안 된다. 민감한 본문을 별도 중복 테이블에 평문으로 복제하기보다 요청 키와 내용 해시를 저장한다. 오래된 클라이언트가 요청 키를 제공하지 않는 경우에는 보존은 보장하되 중복 억제 보장 범위를 명시한다.

### 7.5 인수 시험

- 서로 다른 실제 OS 프로세스 2·8·32개를 장벽에서 동시에 출발시킨다.
- 시각·slug를 고정하고 각 프로세스 본문에 다른 표식을 넣는다.
- 반환 성공 개수뿐 아니라 최종 파일 수, 고유 ID, 모든 본문 표식의 보존을 검사한다.
- 동일 요청을 10회 반복해 파일이 하나인지 확인한다.
- 저장 완료 직후 응답을 끊고 재시도해 같은 결과를 반환하는지 확인한다.
- 경로가 이미 존재하거나 권한·디스크 오류가 있으면 성공으로 보고하지 않는지 확인한다.
- 수동 기록·MCP·백필을 섞어도 같은 계약이 적용되는지 검사한다.

**완료 판정:** 정의한 시험 집합에서 조용한 덮어쓰기·부분 문서 성공 응답·재시도 중복이 0건. 시험 횟수와 환경을 결과에 함께 적는다. 이것을 모든 환경에서의 수학적 무결성 증명으로 표현하지 않는다.

## 08. 장애 복구와 데이터 수명주기

### 8.1 실패를 시간축으로 나눈다

| 장애 지점 | 허용 상태 | 복구 원칙 |
|---|---|---|
| 유효성 검사 전 | 새 원본 없음 | 요청 오류 반환 |
| 임시 파일 작성 중 | 기존 원본 유지, 임시물 존재 가능 | 재시도·임시물 정리 |
| 게시 직전 | 완성된 임시물, 새 원본 미게시 | 중복 없이 재개 또는 폐기 |
| 게시 후 응답 전 | 새 원본 존재, 호출자는 결과 모름 | 요청 ID로 결과 회수 |
| 원본 게시 후 색인 전 | 원본 존재, 캐시 지연 | 재색인 큐로 수렴 |
| DB 손상 | 원본 정상 | 캐시 재구축, 기존 DB 격리 |
| 사용자가 원본 수동 편집 | 새 내용 존재 | 재파싱·출처·충돌 상태 반영 |

현재 `write_atomic`은 임시 파일·동기화·rename을 사용한다. 좋은 출발점이다. 다만 원자적인 이름 교체와 전원 장애 이후의 영속성은 같은 보장이 아니다. 지원 파일시스템에서 파일·디렉터리 메타데이터 동기화 요구사항을 별도로 검토하고, 검증한 범위를 문서화한다. 이 보고서는 전원 장애 유실을 실제 재현했다고 주장하지 않는다. [S05]

### 8.2 복구 UX

사용자에게 “인덱싱 에러”만 보이지 않는다. “원본 기록은 저장되었습니다. 검색 반영이 지연되고 있습니다”처럼 데이터 상태와 다음 행동을 분리한다. 복구 동작은 최근 기록 확인, 캐시 다시 만들기, 진단 내보내기 순서로 제공한다.

원본이 잘못된 경우에는 문서를 임의로 삭제하거나 자동 정상화하지 않는다. 파싱 실패 파일의 위치, 오류 구간, 마지막 정상 표시값을 보여주고 원본을 열게 한다. 자동 복구가 필요하면 복구 전 사본과 변경 요약을 제공한다.

### 8.3 보관·삭제·백업

- 일지 원본, 대화 원문, 임시 파일, 캐시, 임베딩, 로그의 보관 정책을 분리한다.
- 프로젝트 연결 해제와 기록 삭제를 다른 동작으로 만든다.
- 삭제 시 파생 색인과 검색 결과에도 반영되도록 재색인·삭제 큐를 검증한다.
- 백업에는 원본·스키마 버전·관련 첨부를 포함하고 API 키·민감 로그는 기본 제외한다.
- 복원은 빈 디렉터리에 먼저 수행하고 기존 프로젝트 덮어쓰기를 기본값으로 두지 않는다.
- Git 커밋은 유용하지만 커밋 전 유실·로컬 미추적 파일·민감정보 보관 문제까지 해결하지 않는다.

### 8.4 목표 복구 지표

제안 목표는 기준 프로젝트 10,000개 일지에서 **캐시 재구축 5분 이내**, **사용자의 원본 접근 즉시 가능**, **동일 원본으로 재구축한 검색·집계의 의미적 결과 일치**다. 먼저 현재 수치를 측정한 뒤 데이터 크기별 목표를 고정한다. 파일 수뿐 아니라 본문 크기·첨부 크기도 결과에 포함한다.

### 8.5 복구 리허설

릴리스 후보마다 원본을 복사한 시험 프로젝트에서 DB 제거·파싱 오류·프로세스 강제 종료·쓰기 실패를 주입한다. 업데이트 전 스냅샷으로 되돌린 뒤 새 버전과 이전 버전의 동작을 확인한다. 실제 사용자 원본에 장애를 주입하지 않는다.

## 09. 데이터 모델: 기록, 근거, 검토를 분리한다

### 9.1 하나의 ‘완료’ 표시가 만드는 오해

에이전트가 “고쳤다”고 적었다고 테스트가 통과한 것은 아니다. 테스트 통과도 사용자가 원하는 동작을 확인했다는 뜻은 아니다. 사용자가 읽었다고 이후 변경까지 검증된 것은 아니다. 이 세 층을 하나의 초록 체크로 합치면 기능이 정교해질수록 과신 위험이 커진다.

현재 `verified_by_user` 같은 필드와 세션 판정이 존재한다. 이를 폐기하기보다 상태별 의미와 근거의 범위를 명확히 확장한다. [S01] · [S08]

### 9.2 권장 상태 축

| 축 | 예시 값 | 의미 |
|---|---|---|
| 저장 | 대기·저장됨·저장 실패 | 원본이 디스크에 게시됐는가 |
| 관측 | 충분·부분·불가 | 실제 작업 변화를 관측할 수 있는가 |
| 기록 범위 | 연결됨·일부 미기록·판정 불가 | 관측한 변경과 일지를 얼마나 연결했는가 |
| 검증 근거 | 없음·성공·실패·만료 | 테스트 등 실행 근거가 있는가 |
| 사람 검토 | 미검토·확인·추가 조치 필요 | 사용자가 해당 버전을 검토했는가 |

사용자 화면에는 다섯 축을 모두 상시 노출하지 않는다. 기본 카드에는 “저장됨 · 변경 4/5개 연결 · 테스트 근거 없음”처럼 중요한 요약만 보여준다. 세부 근거는 펼쳐서 확인한다.

### 9.3 제안 필드

아래 필드는 설계 제안이며 현재 저장소의 구현을 설명하는 것이 아니다. 실제 명칭과 스키마 버전은 호환성 설계를 거쳐 확정한다.

| 필드 | 역할 | 설계 주의점 |
|---|---|---|
| `record_id` | 경로 변경에도 유지되는 기록 ID | 파일명·제목과 독립 |
| `request_id` | 동일 작성 요청의 재시도 식별 | 서로 다른 요청 재사용 거부 |
| `session_id` | 작업 세션 연결 | 모델명·OS PID만으로 대체 금지 |
| `segment_id` | 긴 세션 내부 작업 구간 구분 | 재개·분기·압축 후 관계 유지 |
| `source_kind` | 에이전트 직접 기록·관측 초안·수동·백필 | 출처별 확신 수준 표시 |
| `evidence_refs` | diff·테스트·커밋·결정 참조 | 원문·시점·내용 해시 포함 |
| `content_hash` | 현재 원본 내용 식별 | 정규화 기준 버전 고정 |
| `reviewed_hash` | 사람이 확인한 버전 | 내용 변경 시 검토 효력 만료 |
| `supersedes` | 정정하는 이전 기록 | 정정 전 이력 유지 |

### 9.4 검증 근거의 유효기간

테스트 성공에는 실행 명령, 종료 코드, 실행 시점, 대상 커밋 또는 관련 파일 상태를 연결한다. 변경 범위가 테스트 이후 달라지면 “이전 상태에서 통과”라고 표시한다. 최신 변경이 없는 경우 매번 테스트를 다시 실행할 필요는 없지만, 어느 상태에 대한 근거인지 숨기면 안 된다.

수동 검토도 동일하다. 사용자가 기록을 확인한 뒤 에이전트가 본문이나 연결 diff를 바꾸면 검토 상태를 유지하지 않는다. 단순 표시 언어 변경처럼 의미가 달라지지 않는 변경은 별도 정책으로 정의한다.

### 9.5 정정과 직접 편집의 일관성

에이전트에게는 기존 일지 수정 금지 규칙을 제시하면서 앱에는 편집 기능이 있을 수 있다. 이를 모순으로 방치하지 않는다. 에이전트 정정은 새 기록 연결, 사용자 편집은 CAS와 변경 이력 보존, 시스템 마스킹은 정책상 이유와 버전 표시처럼 주체별 정책을 문서화한다.

## 10. ‘자동 기록’의 신뢰성 개선

### 10.1 세 층으로 설계한다

**첫 번째 층: 에이전트가 이유를 기록한다.** 작업 의도·실패한 접근·검증 결과는 에이전트가 가장 가까이 알고 있다. 구조화 도구로 기록하되 저장 계약을 서버가 책임진다.

**두 번째 층: 시스템이 관측 가능한 사실을 수집한다.** 파일 변경·도구 종료·세션 상태·커밋 관계를 읽는다. 관측 사실만으로 개발 의도나 해결 여부를 지어내지 않는다.

**세 번째 층: 둘의 불일치를 보여준다.** 변경은 있는데 일지가 없거나, 일지에는 파일이 있는데 실제 근거가 불명확하면 사용자에게 정정 경로를 제공한다.

현재 코드의 `Clear`, `Objection`, `Undecided` 구분은 좋은 기반이다. 목표는 이를 최신 지원 경로 전체에서 동일하게 작동시키고, 판정 불가가 통계에서 사라지지 않게 하는 것이다. [S08]

### 10.2 관측 능력에 따른 약속

| 상황 | 시스템이 말할 수 있는 것 | 말하면 안 되는 것 |
|---|---|---|
| 세션과 파일 변경이 연결됨 | 해당 세션에서 관측한 변경 | 모든 변경 의도를 정확히 안다는 주장 |
| 여러 세션이 같은 파일 수정 | 공동 변경 또는 귀속 불명 | 특정 세션의 책임으로 단정 |
| 세션 종료 후 일지 없음 | 관측 범위에서 기록을 찾지 못함 | 아무 작업도 하지 않았다는 주장 |
| Git 백필만 수행 | 커밋에 존재하는 변경과 메시지 | 당시 에이전트의 내부 판단 |
| AI가 초안 작성 | 관측 자료에서 생성한 초안 | 원 작업자가 작성·확인한 일지 |

### 10.3 누락 복구 흐름

1. 누락 또는 판정 불가 상태를 원장에 남긴다.
2. 원본 자료가 충분하면 비용 없는 사실 기반 초안을 먼저 제공한다.
3. 의도나 설명이 필요한 경우 선택적인 모델 호출을 제공한다.
4. 생성 초안에 근거·추정·미확인을 구분한다.
5. 사용자가 확인하거나 에이전트가 정정하면 관련 기록을 연결한다.
6. 원래 누락 상태를 이력에서 지우지 않고 해결 상태로 전환한다.

### 10.4 경고 피로를 줄이는 조건

동일 세션·동일 누락에 경고를 반복하지 않는다. 일지 작성 후에는 경고를 해소한다. 다른 에이전트가 동시 작업 중이라 판정할 수 없다면 “미기록 확정” 대신 “현재는 귀속을 확인할 수 없음”으로 표시한다. 방해 없이 작업을 마칠 수 있도록 보류·나중에 검토를 제공하되 보류를 기록 완료로 세지 않는다.

### 10.5 기록 강제와 개발 흐름의 균형

완료를 무한히 막는 훅은 사용자가 통합을 끄게 만들 수 있다. 지원 클라이언트의 종료 규약 안에서 유한한 재시도·명확한 사유·탈출 경로를 둔다. 필수 기록 정책을 켤 수 있더라도 기록 서버 장애 때문에 사용자의 코드 작업을 잃게 해서는 안 된다. “작업 결과는 보존됐으나 기록은 대기”를 정상적으로 표현할 수 있어야 한다.

## 11. 최신 벤치마크와 효과 입증 계획

### 11.1 기존 결과의 올바른 해석

2026년 7월 31일 실험은 6개 합성 티켓을 각 조건에서 2회 수행했다. Ocul-PM 조건의 헤드리스 단발 세션에서 기록은 0/12였다. 작은 표본이며 대화형·장기 세션·현재 버전 전체의 결과가 아니다. 보고서 자체도 한계를 설명한다. [S11]

따라서 다음 실험의 목적은 과거 결과를 숨기는 것이 아니라 **현재 제품에서 어떤 조건은 개선됐고 어떤 조건은 여전히 제한되는지** 밝히는 것이다.

### 11.2 실험을 세 종류로 분리한다

| 실험 | 질문 | 수행 방식 |
|---|---|---|
| 계약 시험 | 저장·도구·훅이 약속대로 동작하는가 | 모델 없이 결정적 입력과 장애 주입 |
| 에이전트 실험 | 실제 모델이 기록하고 누락이 복구되는가 | 고정 버전·격리 환경 반복 실행 |
| 사용자 실험 | 사람이 과거 맥락을 더 빠르고 정확하게 찾는가 | 실제 질문·정답 기준·순서 교차 |

모델 비용 때문에 모든 회귀를 실제 에이전트로 검사할 필요는 없다. 저장·상태 전이·오류는 모델 없는 시험으로 넓게 덮고, 행동 의존 부분만 실제 에이전트로 측정한다.

### 11.3 최소 실험 매트릭스

| 차원 | 수준 |
|---|---|
| 지원 조합 | 우선 2개 핵심 에이전트·통합 조합, 정확한 버전 고정 |
| 실행 형태 | 헤드리스 단발 / 대화형 장기 / 2개 이상 동시 세션 |
| 작업 | 버그 수정 / 기능 / 리팩토링 / 실패 후 회복 / 문서 / 변경 없는 조사 |
| 저장소 상태 | 깨끗함 / 기존 미커밋 변경 / 중첩 저장소·worktree |
| 이상 조건 | 종료 신호 / 응답 유실 / 기록 도구 실패 / 사용자가 중간 수정 |

초기 규모는 예를 들어 핵심 조합 2개 × 실행 형태 3개 × 작업 6개 × 반복 5회 = **180세션**이다. 이 180세션은 모든 상태·이상 조건의 완전 조합이 아니며, 핵심 행동 기준선이다. 경계 조건은 별도 계약 시험과 표적 에이전트 실험으로 추가한다. 표본 수는 예산·변동성을 본 뒤 사전 확정한다.

### 11.4 지표 정의

| 지표 | 계산·판정 |
|---|---|
| 유효 기록률 | 유효한 작업 기록이 남은 대상 세션 / 기록 대상 세션 |
| 변경 연결 재현율 | 기록에 연결된 관측 가능 변경 단위 / 전체 관측 가능 변경 단위 |
| 변경 연결 정밀도 | 실제 근거가 있는 연결 / 기록이 주장하는 전체 연결 |
| 누락 감지 재현율 | 감지한 실제 누락 / 전체 실제 누락 |
| 누락 경고 정밀도 | 실제 누락인 경고 / 전체 누락 경고 |
| 판정 불가율 | 귀속·관측 불가 세션 / 전체 세션 |
| 중복률 | 같은 논리 작업에 불필요하게 생성된 중복 / 전체 기록 |
| 추가 비용 | 도구·모델·시간의 대조 조건 대비 차이 |
| 맥락 회수 성공률 | 근거를 포함한 정답을 찾은 사용자 시도 / 전체 시도 |

파일 단위 커버리지만으로 충분하다고 보지 않는다. 파일 하나의 작은 수정과 큰 수정이 같은 한 건으로 계산되기 때문이다. 초기에는 파일 단위 지표로 시작하되 변경 묶음·diff 구간 표본 검토를 보조 지표로 사용한다. `.oculpm/` 생성 자체가 작업 변경 분모를 늘리지 않게 제외 규칙을 사전 정의한다.

### 11.5 제안 목표

- 공식적으로 완전 관측을 지원하는 경로의 유효 기록률 **99% 이상**을 목표로 한다.
- 변경 연결 정밀도 **99% 이상**, 재현율 **95% 이상**을 목표로 한다.
- 누락 경고의 오탐 비율은 **2% 이하**를 초기 목표로 삼는다. 양성 경고가 적을 때는 비율과 절대 건수를 함께 보고한다.
- 지원 경로별 판정 불가율을 공개하고 “성공” 분모에서 몰래 제외하지 않는다.
- 추가 시간·토큰 비용은 먼저 측정하고 사용자 효용과 함께 판단한다. 기록으로 인한 비용 증가가 무조건 0이어야 한다고 가정하지 않는다.

이 목표는 제안이다. 180세션에서 높은 비율이 나와도 99%의 보편적인 신뢰성을 입증했다고 말할 수 없다. 표본별 신뢰구간과 실패 유형을 함께 보고하고, 희귀 실패를 확인하려면 더 큰 지속 표본이 필요하다.

### 11.6 사용자 가치 실험

질문 예시는 “지난달 이 함수가 바뀐 이유는?”, “이 버그를 어떤 조건에서 재현했나?”, “이 브랜치에서 검토하지 않은 변경은?”, “이 계획이 막힌 근거는?”이다. 정답은 해당 프로젝트 소유자가 미리 근거와 함께 정의한다.

참여자 8~12명 수준의 탐색 실험으로 이해 문제를 찾고, 방향이 확인되면 더 큰 표본으로 효과를 검증한다. 같은 사람이 대조 조건과 Ocul-PM을 사용하되 순서를 교차하고 다른 문제 세트를 사용하여 학습 효과를 줄인다. 초기 목표는 동일 정확도를 유지하면서 중앙값 회수 시간을 30% 줄이는 것이다. 이 수치는 현재 효과가 아니라 검증할 가설이다.

### 11.7 결과 공개 형식

버전·모델·OS·실험 입력·스캐폴드·성공 판정·제외 사유·실패 로그의 민감정보 제거본을 남긴다. 성공한 시도만 선택하지 않는다. 비교 중 변경된 모델 버전은 같은 집계로 합치지 않는다. 과거 보고서는 삭제하지 않고 새 결과에서 차이를 설명한다.

## 12. 플래너·브랜치·일지의 의미적 일관성

### 12.1 현재 강점을 보존한다

플래너의 내용 해시와 잠금은 이미 구현되어 있고 별도 프로세스 경쟁 테스트도 있다. 이를 다시 개발하는 항목으로 잡지 않는다. 개선 범위는 클라이언트 복구, 일지 연결, 완료 근거, 아카이브 상태가 같은 규칙을 따르는지 확인하는 것이다. [S06] · [S07]

### 12.2 충돌 해결 UX

CAS 충돌은 “다시 시도” 버튼만 제공해서는 안 된다. 사용자가 본 이전 상태와 현재 상태를 비교하고, 어느 항목이 바뀌었는지 보여준다. 서로 다른 항목 변경은 검토 가능한 병합 후보로 제공할 수 있지만, 동일 항목의 의미가 충돌하면 사용자·에이전트가 다시 판단해야 한다.

클라이언트가 최신 해시만 받아 같은 명령을 무조건 재실행하는 방식은 내용 확인이라는 CAS의 의미를 약화한다. 실패 응답에는 현재 버전, 다시 읽을 방법, 안전하게 재시도할 수 있는 조건을 담는다.

### 12.3 완료 조건

- 계획 항목 완료는 관련 일지 또는 사용자 제공 근거와 연결한다.
- 근거가 없는 수동 완료도 허용할 수 있으나 “근거 없음” 상태를 유지한다.
- 하위 항목으로 계산되는 부모 상태는 직접 편집하지 않는다.
- 아카이브된 미완료 항목은 기본 활성 목록과 분리하되 찾을 수 있어야 한다.
- 브랜치 이름 변경·삭제·rebase 후에도 기록을 잃지 않는다.
- 커밋 하나가 여러 작업을 담거나 한 작업이 여러 커밋으로 나뉘는 관계를 허용한다.

### 12.4 잠금의 경계 시험

기존 잠금은 오래된 락 처리 정책을 가진다. 긴 OS 정지·절전 복귀·느린 파일시스템·시계 변화·프로세스 종료 직후 경쟁 상황에서 소유권이 어떻게 유지되는지 시험한다. 오래됐다는 이유만으로 살아 있는 작성자의 락을 회수하는 상황이 가능한지 검증하고, 필요하면 소유 토큰·세대 번호 등으로 오래된 소유자가 새 락을 제거하지 못하게 한다. 이것은 추가 검증 과제이며 현재 사고가 재현됐다는 뜻은 아니다.

## 13. 첫 5분: 설치보다 첫 가치를 설계한다

### 13.1 첫 사용 성공 조건

“앱이 실행됐다”를 활성화로 세지 않는다. 사용자가 자기 프로젝트에서 **첫 기록을 보고 실제 변경과 연결해 확인한 시점**을 첫 가치로 정의한다. 플러그인만 사용하는 사용자는 구조화 일지 하나가 만들어지고 다시 검색 가능한 시점을 별도로 측정한다.

### 13.2 권장 온보딩

| 단계 | 화면의 질문 | 실제 동작 | 성공 증거 |
|---|---|---|---|
| 1 | 어느 프로젝트를 추적할까요? | 폴더·Git 상태·기존 설정 확인 | 선택한 경로 표시 |
| 2 | 어떤 에이전트를 쓰나요? | 설치 여부와 지원 등급 검사 | 버전·능력 목록 |
| 3 | 무엇이 추가되나요? | 규칙·MCP·폴더 변경 요약 | 변경 전후 미리보기 |
| 4 | 연결이 작동하나요? | 읽기 중심 진단과 임시 시험 기록 | 실제 왕복 결과 |
| 5 | 첫 작업을 확인하세요 | 실제 일지·diff·근거로 이동 | 사용자의 첫 검토 |

시험 기록은 사용자의 실제 작업 성과에 섞이지 않도록 명확히 표시하고 쉽게 제거할 수 있어야 한다. 자동으로 실제 코드 파일을 수정하여 데모를 만들지 않는다.

### 13.3 실패 상태 설계

에이전트 미설치, 실행 경로 문제, 지원하지 않는 버전, 플러그인 중복, MCP 미연결, 쓰기 권한 없음, 초기 모델 다운로드 실패를 서로 구분한다. 각 상태에는 감지 근거와 다음 행동 하나를 둔다. 모든 문제를 “설정을 확인하세요”로 요약하지 않는다.

사용자가 API 키를 넣지 않아도 기본 기록·텍스트 검색·diff 확인까지 경험하도록 한다. 의미 검색이나 생성형 요약이 준비되지 않았다는 이유로 첫 화면을 막지 않는다.

### 13.4 빈 상태

빈 일지에는 “아직 기록이 없습니다”와 함께 실제 연결 상태·다음 기록 방법을 보여준다. 계획이 없으면 계획 만들기, 기록이 있는데 검색이 안 되면 색인 상태 확인으로 연결한다. 기능 홍보 문구와 실제 활성 상태가 일치해야 한다.

### 13.5 제안 인수 기준

- 사전 설치된 지원 에이전트가 있는 시험 환경에서 도움 없이 첫 기록 확인까지 중앙값 5분 이내.
- 탐색 실험 참여자의 80% 이상이 연결 상태와 다음 행동을 정확히 설명.
- 취소 시 이미 변경한 설정과 남는 파일을 정확히 안내.
- 설치되지 않은 기능을 설치 완료라고 표시하는 경로 0건.
- 새 프로젝트 설정이 다른 프로젝트의 규칙을 덮어쓰지 않음.

수치는 탐색 목표이며 사용자 표본과 환경을 고정한 뒤 채택한다.

## 14. 정보 구조와 화면별 개선안

### 14.1 기본 탐색 구조

기본 탐색은 **오늘 / 기록 / 계획 / 변경 / 검색**의 다섯 목적을 중심으로 검증한다. 에이전트 실행과 터미널은 작업 공간으로 묶고, 코드 맵·편집기·스킬·설정은 사용 빈도에 따라 확장 노출한다. 현재 메뉴를 한 번에 삭제하거나 단축키를 다시 배정하지 않는다. 사용자 테스트와 점진적 전환이 먼저다.

### 14.2 Today

Today는 많은 카드의 집합보다 “오늘 무엇을 확인하고 이어갈까”에 답해야 한다. 우선순위는 기록 저장 실패, 검토할 변경, 막힌 계획, 최근 완료, 다음 행동이다. 동일 사실을 여러 카드에서 중복 경고하지 않는다. 각 카드가 원본 근거로 이동해야 한다.

### 14.3 일지 상세

상단에 작업 제목·출처·저장 상태·검증 근거를 둔다. 본문은 이유·변경·검증으로 읽되, 관련 diff와 계획을 옆에서 확인한다. 원문은 항상 열 수 있어야 한다. 자동 요약이 원문을 대체해서는 안 된다.

### 14.4 변경 검토

파일별로 연결 일지, 변경 시점, 테스트 근거, 사용자 검토 상태를 표시한다. “기록됨”과 “검토됨”을 다른 배지로 표현한다. 삭제·이름 변경·바이너리·생성 파일은 서로 다른 검토 경험을 제공한다. 큰 diff는 잘랐다는 사실과 전체 열기 경로를 표시한다.

### 14.5 브랜치

브랜치는 커밋 수보다 작업 목적·계획·기록되지 않은 변경·검증 근거를 요약한다. 브랜치의 모든 변경을 한 사람이 했다고 가정하지 않는다. rebase 이전 참조가 해석되지 않으면 원본 스냅샷과 미해결 참조를 보여준다.

### 14.6 에이전트 세션

활성·대기·승인 필요·종료·연결 끊김을 구분한다. 응답이 느리다는 사실만으로 실패를 표시하지 않는다. 승인 카드에는 실제 명령과 대상·쓰기 범위를 표시하고 일지 작성 여부와 실행 승인을 혼합하지 않는다. 종료된 세션의 기록이 늦게 도착해도 연결을 유지한다.

### 14.7 공통 상태 문구

| 상황 | 권장 표현 |
|---|---|
| 원본 저장, 색인 지연 | 기록은 저장됐습니다. 검색에 반영 중입니다. |
| 근거 없는 완료 주장 | 에이전트가 완료로 기록했습니다. 검증 근거는 없습니다. |
| 공동 변경으로 귀속 불가 | 여러 세션이 이 파일을 수정해 작업별 구분을 확인할 수 없습니다. |
| 검토 이후 내용 변경 | 확인한 뒤 내용이 변경됐습니다. 다시 검토해 주세요. |
| 과거 테스트 성공 | 이 테스트는 이전 파일 상태에서 통과했습니다. |
| 충돌 | 다른 작업에서 이 계획을 수정했습니다. 변경 내용을 확인해 주세요. |

## 15. 접근성·한국어·일관성

### 15.1 기본 원칙

핵심 흐름은 키보드만으로 완수할 수 있어야 한다. 색상만으로 기록·검증·경고를 구분하지 않는다. 포커스가 열린 패널 뒤로 사라지지 않게 하고, 모달을 닫으면 시작 위치로 돌아오게 한다. 동적 기록 상태는 화면 읽기 도구에 과도하게 반복되지 않는 방식으로 전달한다.

### 15.2 구체 시험

- 프로젝트 연결부터 일지 검색·diff 확인·검토까지 키보드 경로를 기록한다.
- 확대·작은 창·긴 한국어 제목·긴 경로에서 주요 버튼이 사라지지 않는지 확인한다.
- 한국어 IME 조합 중 Enter가 제출·저장으로 잘못 동작하지 않는지 검사한다.
- 한·영 전환 후 날짜·상태·오류·단축키 설명이 일관적인지 확인한다.
- 리스트 가상화가 포커스와 화면 읽기 순서를 깨뜨리지 않는지 검사한다.
- 자동 접근성 검사와 실제 보조기술 사용 검증을 구분한다.

### 15.3 디자인 체계

상태 배지·오류 패널·빈 상태·확인 대화상자·근거 링크를 공통 요소로 만든다. 시각적으로 유사한 컴포넌트를 합치는 것보다 상태 의미를 통일하는 것이 먼저다. 자동 린트로 가능한 규칙과 사람이 화면에서 확인해야 하는 규칙을 분리한다.

## 16. 검색과 맥락 회수의 품질

### 16.1 검색의 성공은 결과 수가 아니다

사용자가 원하는 것은 관련 일지가 많다는 사실보다 “이 결정의 이유를 찾았다”는 결과다. 경로·심볼·기간·세션·작업 유형 필터를 조합하고, 결과에 일치 이유와 해당 근거 구절을 제공한다.

### 16.2 권장 검색 계층

1. 명시 경로·ID·정확한 용어는 정확 일치와 구조화 필터를 우선한다.
2. 심볼 관계는 AST 기반 검색으로 보완한다.
3. 자연어 의도는 의미 검색으로 확장하되 정확 일치를 밀어내지 않는다.
4. 생성형 답변은 검색된 근거를 인용하고 자료에 없는 설명은 추정으로 구분한다.

현재 의미·심볼·텍스트 검색을 제공하는 방향은 유지한다. 새 벡터 DB를 도입하기 전에 기존 결과의 누락·순위·필터 문제를 실제 질문 집합으로 평가한다. [S01]

### 16.3 평가 세트

프로젝트 소유자가 자주 묻는 질문 50~100개를 모은다. 정답 문서와 관련 없는 유사 문서를 함께 지정한다. 파일명 변경, 오래된 결정, 폐기된 계획, 동일 오류의 반복, 한국어·영어 혼용을 포함한다. 상위 5개 안 정답 포함률, 잘못된 근거 인용률, 질문 해결 시간을 측정한다.

### 16.4 최신성과 과거 보존

정정된 기록은 검색에서 최신 정정을 우선하되 원래 기록을 열 수 있게 한다. 삭제된 파일과 과거 브랜치의 기록도 회수할 수 있어야 한다. 캐시가 뒤처져 있다면 검색 시점을 표시한다. 의미 검색 모델이 준비되지 않으면 텍스트 검색으로 정상 동작한다.

## 17. 보안·프라이버시 개선 설계

### 17.1 경계를 먼저 정의한다

| 경계 | 신뢰하지 않을 입력 | 보호할 대상 | 필수 시험 |
|---|---|---|---|
| 저장소 → 앱 | 문서·파일명·SVG·링크·규칙 내용 | 웹뷰·파일시스템·실행 권한 | 렌더링·경로 탈출·악성 링크 |
| 에이전트 → 기록 서버 | 도구 인수·본문·경로 | 원본·다른 프로젝트 | 규격·길이·경로·권한 |
| 앱 → 외부 서비스 | 선택한 문서·diff·프롬프트 | 민감정보·사용자 선택 | 전송 전 필터·거부·미리보기 |
| 모바일·로컬 연결 → 앱 | 토큰·요청·재전송 | 프로젝트 접근 | 바인딩·인증·해제·재사용 |
| 업데이트 → 설치본 | 번들·메타데이터 | 실행 코드 | 서명·버전·배포 출처 |

네이티브 비밀 저장소 사용과 외부 전송 목록 검사는 좋은 출발점이다. 다만 API 키 저장과 문서에 들어간 비밀 탐지는 다른 문제다. [S13] · [S14]

### 17.2 CSP 활성화

저장소의 CSP 초안을 출발점으로 실제 앱에서 허용할 리소스 종류를 다시 확인한다. 특히 Monaco 워커·WASM 포매터·PDF·이미지·blob URL·업데이트 정보 표시가 영향을 받을 수 있다. 기존 초안을 그대로 붙여 넣고 빌드만 통과했다고 종료하지 않는다. [S09] · [S10]

실행 순서는 다음과 같다.

1. 현재 웹뷰의 스크립트·워커·프레임·연결 경로 목록 작성.
2. 개발·릴리스 환경의 최소 허용 정책 구분.
3. 기능별 실제 WKWebView 시험과 정책 위반 확인.
4. 미허용 스크립트·외부 연결의 차단 시험.
5. 예외별 이유·책임자·재검토 조건 기록.
6. CSP 비활성을 고정하는 기존 테스트를 정책의 허용·차단 계약 테스트로 교체.

지원 웹뷰의 기능 차이는 실제 실행으로 확인한다. 정책을 켜기 위해 광범위한 와일드카드를 추가하면 효과가 약해지므로 예외는 좁게 둔다. CSP는 Rust 측 네트워크 호출을 통제하지 않으므로 전송 정책을 별도로 유지한다.

### 17.3 경로 안전성

루트 `.oculpm` 심볼릭 링크 거부만으로 모든 하위 경로가 안전하다고 보지 않는다. 중간 디렉터리 링크, 상대 경로 탈출, 절대 경로, Unicode 정규화, 대소문자 충돌, 중첩 저장소를 포함한 경로 시험을 만든다. 검사 후 사용 전 파일이 바뀌는 경쟁도 위협 모델에 포함한다.

모든 읽기와 쓰기에 같은 정책을 적용할 필요는 없지만 차이를 명시한다. 외부 파일을 참조할 수 있는 읽기 기능과 프로젝트 내부만 허용하는 기록 쓰기를 구분한다. 오류 응답에 불필요한 민감 절대 경로를 노출하지 않는다.

### 17.4 민감정보 처리

검사 지점은 입력, 원본 저장, diff 보관, 검색 색인, 모델 전송, 내보내기, 진단 로그다. 한 지점의 마스킹이 다른 경로를 보장하지 않는다. 알려진 비밀 패턴에 더해 사용자가 프로젝트별 제외 경로·제외 필드를 지정할 수 있게 한다.

마스킹은 완벽한 탐지라는 약속을 하지 않는다. 감지된 문자열을 로그에 그대로 재출력하지 않고, 누락과 오탐을 합성 시크릿 자료로 시험한다. 마스킹으로 기록 의미가 달라진 경우 정책 적용 사실을 표시한다. 실제 API 키로 테스트하지 않는다.

### 17.5 프롬프트 인젝션과 실행 권한

일지·README·도구 결과·에이전트 간 메시지는 작업 데이터다. 그 안의 “이 파일을 삭제하라”, “외부로 전송하라” 같은 문구가 앱의 권한을 바꾸면 안 된다. 읽기·쓰기·실행·외부 전송 능력을 경계별로 분리하고, 모델이 반환한 명령을 자동 승인하지 않는다.

사용자가 승인한 작업 범위 안에서 반복 확인을 줄이되, 저장소 문서가 새 승인을 대신하지 않도록 한다. 권한 요청은 실제 실행 대상·쓰기 범위·외부 목적지를 사용자가 이해할 수 있게 제시한다.

### 17.6 모바일·로컬 연결

선택 기능의 활성 상태, 바인딩 주소, 페어링 기기, 접근 범위, 해제 방법을 한 화면에서 확인할 수 있어야 한다. 토큰 재사용·만료·기기 해제·잘못된 호스트 요청·동시 요청 제한을 시험한다. 로컬이라고 모두 신뢰하거나 앱 전체 기능을 연결 기기에 노출하지 않는다. 현 구현의 취약성을 단정하는 항목이 아니라 필요한 경계 검증 목록이다.

### 17.7 완료 기준

공식 지원 경로의 위협 모델과 시험 증거가 있고, 알려진 중요 미해결 경로가 없어야 한다. 보안 설정 활성화 자체와 공격 입력 차단을 모두 확인한다. 공개 보고서에는 민감한 재현 자산을 제외하되 검토 범위·날짜·해결 상태는 남긴다.

## 18. 배포 파이프라인과 업데이트 신뢰성

### 18.1 현재 관찰

루트 CI는 프런트·Rust·의존성을 검사한다. 배포 워크플로는 `v*` 태그에서 번들을 만들고 릴리스를 게시한다. 검토한 배포 파일에는 해당 태그의 정확한 커밋이 필수 CI를 통과했는지 확인하는 단계가 명시되어 있지 않다. 실제 GitHub 브랜치 보호·태그 규칙은 이번 평가에서 확인하지 않았으므로, 저장소 정책과 워크플로를 함께 점검해야 한다. [S02] · [S03]

### 18.2 권장 배포 흐름

1. 릴리스 후보 커밋을 확정한다.
2. 그 커밋으로 필수 검사를 실행한다. 다른 커밋의 녹색 결과를 재사용하지 않는다.
3. 버전·변경 이력·플러그인 호환성을 검사한다.
4. 고정된 도구와 의존성으로 후보 번들을 만든다.
5. 서명·공증·업데이트 서명·파일 해시를 확인한다.
6. 깨끗한 환경에서 설치·첫 실행·이전 버전에서 업데이트를 시험한다.
7. 후보 산출물을 승격하여 공개한다. 검증 후 재빌드한다면 다시 동일성·서명을 검증한다.
8. 공개된 다운로드와 업데이트 메타데이터의 일치를 확인한다.

검사와 빌드를 재사용 워크플로로 연결하거나, 배포 직전 필수 결과를 조회하는 방식 중 운영하기 쉬운 것을 택한다. 실패·취소·결과 누락은 통과로 취급하지 않는다.

### 18.3 재현성 개선

Rust 버전은 CI·로컬·배포에서 같은 원천을 읽도록 통일한다. 현재 CI는 핀된 도구 체인을 읽는 구조이고 배포는 stable 액션을 사용하므로 실제 사용 버전이 일치하는지 검증할 필요가 있다. 프런트 설치도 고정 락파일 사용을 명시하고 패키징 도구의 버전 변동을 통제한다. [S02] · [S03] · [S15]

액션을 커밋으로 고정하는 공급망 정책은 유지보수 부담과 함께 결정한다. 중요한 것은 특정 구문 채택 자체보다 “어느 코드·도구·의존성으로 이 파일을 만들었는지” 회수할 수 있는 것이다.

### 18.4 서명 실패는 배포 실패

배포 설명이 서명·공증 완료를 말한다면 실제 산출물 검사가 이를 보장해야 한다. 비밀 값 누락·공증 실패·잘못된 인증서·업데이트 서명 불일치 상황에서 공개 배포를 막는다. 설정에 환경 변수가 있다는 사실만으로 서명이 완료됐다고 가정하지 않는다.

### 18.5 업데이트·롤백

최근 안정 버전과 직전 버전에서 후보 버전으로 업데이트하는 경로를 시험한다. 실행 중인 세션·저장 중인 일지·열려 있는 편집 버퍼·대형 캐시를 포함한다. 데이터 마이그레이션이 역방향 호환을 깨면 “앱만 이전 버전으로 바꾸기”가 안전한 롤백이 아닐 수 있다. 백업·변환·읽기 전용 보호 정책을 함께 정의한다.

### 18.6 배포 증거 묶음

각 릴리스에 커밋 SHA, 필수 검사 실행 ID, 도구 버전, 번들 해시, 서명 검증 결과, 설치·업데이트 결과, 데이터 호환 범위, 알려진 제한을 저장한다. 공개할 수 없는 정보는 제거하되 사용자가 릴리스의 검증 범위를 확인할 수 있어야 한다.

## 19. 테스트 전략: 개수보다 실패를 잡는 능력

### 19.1 현재 테스트를 재사용한다

2,711개 프런트 테스트는 이미 상당한 자산이다. `session_verdict`, `delivery_gate`, `plan_cas_two_process`, `watcher_backpressure`처럼 실제 경로와 경계 조건을 시험하려는 구조도 있다. 새 테스트 프레임워크를 먼저 도입하기보다 빠진 계약과 실행되지 않는 범위를 찾는다. [S07] · [S08] · [S16]

### 19.2 계층별 책임

| 계층 | 검증 대상 | 대표 실패 |
|---|---|---|
| 순수 로직 | 파서·상태 전이·판정·필터 | 잘못된 완료 상태 |
| 저장 계약 | 원자적 생성·CAS·중복·마스킹 | 유실·덮어쓰기·잘못된 성공 |

### 19.4 피해야 할 테스트

- 소스에 특정 함수명이나 문자열이 있는지만 검사하고 실제 행위를 보장하지 않는 테스트.
- 구현 내부 배열을 그대로 복사하여 같은 값을 기대하는 테스트.
- UI 텍스트가 “저장됨”인지 확인하면서 파일 저장은 전부 성공 mock으로 대체하는 테스트.
- 시간 제한을 계속 늘려 원인 불명의 지연을 숨기는 방식.
- 보안 설정이 꺼져 있다는 사실을 최종 품질 조건으로 유지하는 방식.

구조 규칙이나 CSS 핵심 선택자처럼 문자열 검사가 목적에 맞는 경우는 유지한다. 문제는 검사 방식 자체가 아니라 보장 범위를 과장하는 데 있다.

### 19.5 변경별 검사 선택

일지 저장 수정은 저장 계약·두 프로세스·원본 조회까지, 상태 모델 수정은 파서·도구·UI·마이그레이션까지, CSP 수정은 실제 웹뷰까지 검사한다. 문구 수정마다 전체 네이티브 빌드를 요구하지 않는다. 위험에 비례한 필수 검사 표를 만든다.

## 20. 성능: 최신 기준선과 사용 경험 예산

### 20.1 먼저 유지할 원칙

저장소의 기존 성능 문서는 CSS 크기와 DB 큐 같은 가설 일부가 실제 병목이 아니었다고 기록한다. 이것은 좋은 개발 방식이다. 코드 줄 수·번들 크기·비동기 함수 모양만으로 체감 성능을 단정하지 않는다. [S12]

### 20.2 측정 환경

지원 하드웨어 중 보수적인 기준 기기를 한 대 지정한다. 예를 들어 Apple Silicon·16GB RAM·내장 SSD를 기준군으로 삼고 OS·앱·모델 버전을 기록한다. 배터리·전원·초기 모델 다운로드·콜드 캐시·웜 캐시를 구분한다. 외부 에이전트 프로세스의 메모리는 앱 자체와 별도로 측정한다.

### 20.3 제안 성능 예산

| 동작 | 제안 목표 | 측정 조건 |
|---|---|---|
| 앱 콜드 시작 후 첫 유효 화면 | p95 3초 이내 | 모델 다운로드 제외, 실제 설치본 |
| 기본 탐색 전환 | p95 200ms 이내 | 이미 열린 프로젝트 |
| 일지 첫 페이지 조회 | p95 300ms 이내 | 일지 10,000개, 웜 캐시 |
| 텍스트 검색 첫 결과 | p95 500ms 이내 | 규모·본문 분포 고정 |
| 저장 완료 → 화면 반영 | p95 1초 이내 | 정상 로컬 파일시스템 |
| 입력·스크롤 | 장시간 정지 없는 상호작용 | CPU·렌더 긴 작업 함께 기록 |
| 캐시 재구축 | 5분 이내 | 기준 원본 10,000개 |

이 값은 현재 성능 수치가 아니다. 초기 측정 후 하드웨어·데이터 크기별 SLO로 확정한다. p95는 느린 상위 5% 경계값이며, 실행 수가 적으면 불안정하므로 반복 수와 분포를 함께 남긴다.

### 20.4 조사 순서

1. 실제 지연 구간을 계측한다.
2. UI·워처·파서·색인·DB·파일 IO·외부 호출로 분리한다.
3. 가장 큰 비용 또는 사용자를 막는 구간을 하나 선택한다.
4. 변경 전후 같은 자료로 재측정한다.
5. 다른 경로의 메모리·전력·정확성이 나빠지지 않았는지 확인한다.

현재 존재하는 워처 백프레셔·페이지 제한·컨텍스트 분리 등을 새 기능처럼 제안하지 않는다. 최신 경로에 적용되는지와 대규모 전환·삭제·rename 폭주에서 결과가 수렴하는지 확인한다.

### 20.5 대형 기능의 지연 로드

Monaco·디버거·그래프·임베딩 모델 등은 첫 기록 확인에 필요하지 않을 수 있다. 실제 초기 로드 추적에서 비용이 확인되면 필요한 시점에 로드한다. 이번 빌드의 큰 청크 경고는 조사 단서로 기록하되 모든 청크를 무조건 잘게 쪼개지는 않는다.

### 20.6 메모리·장기 실행

한 시간 이상 일지 추가·탭 열기·세션 종료·프로젝트 전환을 반복하고 메모리가 안정화되는지 본다. 탭을 닫아도 남는 웹 워커·이벤트 리스너·PTY·LSP·캐시를 조사한다. 앱을 종료했을 때 사용자가 유지하기로 한 세션과 종료해야 하는 프로세스를 구분한다.

## 21. 유지보수성과 의존성 관리

### 21.1 ‘크다’와 ‘문제다’를 구분한다

파일 길이와 코드 줄 수는 복잡성의 단서다. 줄 수 자체를 줄이기 위해 파일을 쪼개면 의존성이 더 복잡해질 수 있다. 변경 빈도, 결함 발생, 테스트 어려움, 책임 혼합이 겹치는 지점부터 분리한다.

### 21.2 우선 정리할 경계

- 일지 입력 파싱과 저장 정책.
- 도구 스키마와 실행 결과 모델.
- 원본 갱신과 색인 후처리.
- 에이전트별 프로토콜 변환과 공통 세션 상태.
- 화면 상태와 도메인 상태.
- 보안 정책과 기능별 예외.

### 21.3 공통 오류 모델

오류를 문자열 검색으로만 구분하지 않도록 안정적 코드·사람용 설명·재시도 가능 여부·현재 버전 정보를 분리한다. 예시는 `WRITE_CONFLICT`, `STORE_FAILED`, `INDEX_PENDING`, `UNSUPPORTED_SCHEMA`, `CAPABILITY_UNAVAILABLE`이다. 이는 제안 코드이며 기존 API와 호환 이행이 필요하다.

### 21.4 의존성

Rust 의존성 감사는 기존 cargo-deny를 유지한다. 프런트·확장·번들에 대해서도 사용하지 않는 패키지, 런타임에 들어가는 개발 도구, 업데이트 위험, 라이선스 정보를 정기 점검한다. 감사 경고를 무조건 차단하기보다 실제 영향과 예외 만료 조건을 기록한다. 반대로 아무 근거 없는 영구 ignore도 허용하지 않는다.

### 21.5 결정 기록

각 큰 선택에는 문제, 대안, 선택, 포기한 장점, 재검토 조건을 짧게 남긴다. 기존의 풍부한 문서를 한 번에 다시 쓰지 않는다. 현재 유효한 문서와 역사 자료를 구분하고 구현 근거 링크를 업데이트한다. 과거 보고서가 현재 사양처럼 검색되는 일을 줄인다.

## 22. 사용자 검증·채택·지속 사용

### 22.1 좋은 지표와 잘못된 대리 지표

좋은 지표는 첫 실제 기록 확인, 과거 기록 재사용, 근거 있는 검토 완료, 복구 성공, 맥락 회수 시간이다. 설치 수·일지 개수·토큰 사용량·커밋 수만으로 가치가 높아졌다고 판단하지 않는다. 자동 일지 수가 늘어도 사용자가 읽지 않으면 부담만 늘 수 있다.

### 22.2 로컬 우선과 측정의 양립

기본적으로 제품 사용 데이터를 외부로 전송할 필요는 없다. 사용자 동의하에 로컬 진단·자기 보고·시험 세션 자료를 수집할 수 있다. 내보내기 전에 필드와 제거할 민감정보를 보여준다. 본문·코드·경로를 무단 수집하여 지표를 만들지 않는다.

### 22.3 탐색 검증 계획

처음에는 실제 프로젝트를 가진 8~12명의 사용자를 모집한다. 개인정보와 프로젝트 자료를 수집하지 않아도 화면 관찰·작업 성공·시간·짧은 인터뷰로 문제를 찾을 수 있다. 한 번의 데모 만족도보다 1~2주 뒤 실제로 기록을 다시 찾는지 확인한다.

질문은 “좋나요?”보다 “어제 수정 이유를 지금 찾아주세요”, “이 초록 표시는 무엇을 뜻하나요?”, “기록이 실패하면 어디서 해결할 수 있나요?”처럼 행동으로 답하게 한다.

### 22.4 가치 가설

| 가설 | 검증 방식 | 기각 시 대응 |
|---|---|---|
| 기록과 diff 연결이 회수 시간을 줄임 | 교차 과제 시간·정확도 | 검색·정보 구조 개선 |
| 기본 화면 단순화가 첫 가치를 앞당김 | 기존·새 흐름 사용 시험 | 메뉴 축약 방식 재설계 |
| 플러그인부터 시작하는 경로가 도입을 돕음 | 설치·첫 기록 성공 추적 | 진단·설치 문서 개선 |
| 검토 근거가 신뢰를 높임 | 잘못된 완료 상태 발견 과제 | 상태 용어·근거 노출 수정 |

### 22.5 사업성에 대한 입장

이 보고서는 시장 규모나 수익성을 실측하지 않았다. 따라서 매출·성장률·경쟁 제품 대비 우위를 예측하지 않는다. 향후 유료화를 검토한다면 기본 데이터 이동성과 기록 접근성을 훼손하지 않고, 공유·검토·지원의 실제 수요를 먼저 검증한다. 지금 10점 달성의 필수 과제는 결제 기능 추가가 아니다.

## 23. 호환성·마이그레이션·되돌리기

### 23.1 새 필드는 점진적으로 도입한다

기존 문서에 ID가 없다고 전부 잘못된 데이터로 처리하지 않는다. 읽기는 이전 스키마를 지원하고 새 작성부터 새 필드를 넣는다. 기존 자료에 ID를 추가해야 한다면 미리보기·백업·명시적 적용·중단 후 재개가 가능해야 한다.

문서 경로가 참조 ID 역할을 하는 부분은 당분간 병행한다. 새 ID와 기존 경로의 매핑을 유지하고, 파일 이동 후 검색·계획 연결이 깨지지 않는지 검사한다.

### 23.2 호환 행렬

| 조합 | 요구 동작 |
|---|---|
| 새 앱 + 이전 일지 | 읽기·검색 가능, 새 필드 없음 표시 |
| 이전 앱 + 새 일지 | 가능한 범위 읽기 또는 명확한 보호 오류 |
| 새 MCP + 이전 플러그인 | 누락 인수에 복구 지침 제공 |
| 이전 MCP + 새 플러그인 | 능력 협상으로 지원 범위 제한 |
| 새 앱 + 이전 확장 | ID·상태 기본 계약 유지 |
| 앱 없이 마크다운만 사용 | 사람이 읽을 수 있는 본문 유지 |

### 23.3 버전 책임

앱 버전, 파일 스키마 버전, 규칙 템플릿 버전, MCP 계약 버전, 확장 버전은 서로 다를 수 있다. 이 차이를 숨기지 말고 진단 화면에 표시한다. 버전 비교만으로 호환을 추정하기보다 지원 능력 확인을 함께 사용한다.

### 23.4 롤백 원칙

기능 플래그로 되돌릴 수 있는 UI·관측 기능부터 배포한다. 데이터 변환은 되돌리기 절차가 준비되기 전 기본 활성화하지 않는다. 원본과 파생물의 버전을 분리하고, 이전 앱이 새 원본을 조용히 훼손하는 경로를 막는다.

## 24. 실행 로드맵: 일정 대신 통과 조건을 관리한다

### 24.1 일정 가정

아래는 **계획 초안**이다. 전담 개발자 2명 수준의 역량과 부분적인 제품·QA 검토 시간을 가정한다. 실제 작업자는 지정하지 않았고, 구현 견적은 아직 내지 않았다. 에이전트 사용이 인력과 검토 시간을 자동으로 대체한다고 가정하지 않는다.

핵심 개선 트랙의 12주 초안은 사용자 실험 표본·보안 검토·외부 에이전트 변동에 따라 늘어날 수 있다. 모든 백로그를 12주 안에 끝낸다는 약속은 아니다. 1인 개발이면 기간보다 각 단계의 완료 조건을 우선하며 선택 과제를 뒤로 미룬다.

### 24.2 단계별 계획

| 단계 | 가이드 기간 | 핵심 산출물 | 다음 단계 조건 |
|---|---|---|---|
| 0. 기준 확정 | 1주 | 지원 범위·증거 원장·현재 재현 자료 | 불명확한 성공 기준 제거 |
| 1. 저장·복구 | 2~4주 | 신규 생성·재시도·장애 계약 | 핵심 데이터 시험 통과 |
| 2. 상태·검증 | 4~6주 | 출처·검토·근거 상태, 최신 행동 실험 | 오류를 성공으로 표시하지 않음 |
| 3. 핵심 UX | 6~8주 | 첫 사용·Today·일지·변경 개선 | 사용자 과제에서 개선 확인 |
| 4. 배포·보안 | 8~10주 | CI 결합·서명·CSP·경계 시험 | 지원 범위의 중요 위험 해소 |
| 5. 검증·안정화 | 10~12주+ | 설치본 시험·반복 실험·재평가 | 10점 필수 조건 충족 |

기간은 일부 겹친다. 배포 게이트나 측정 준비처럼 독립 작업은 일찍 시작할 수 있다. 데이터 모델이 확정되기 전에 화면 전체를 재설계하지 않는다. 중요 보안 결함이 재현되면 해당 작업을 단계 순서와 관계없이 앞당긴다.

### 24.3 1인 개발의 첫 네 작업

1. 신규 일지 경쟁을 실제 두 프로세스로 재현하고 결과를 남긴다.
2. 저장 성공·응답 유실·재시도 계약을 한 경로에서 완성한다.
3. 태그 커밋의 필수 검사 성공과 배포를 연결한다.
4. 최신 지원 경로 하나에서 기록 누락·판정 불가·복구를 측정한다.

이 네 가지는 큰 화면 개편보다 먼저 제품의 신뢰를 높인다. 동시에 “현재 잘 작동하는가”를 보여주는 근거가 되어 후속 투자 판단을 돕는다.

### 24.4 범위 제한

기본 데이터 계약이 안정화되기 전 새로운 플랫폼·에이전트·고급 IDE 기능의 확장은 선택 과제로 둔다. 기존 사용자가 쓰는 기능의 결함 수리는 계속한다. 10점 목표를 이유로 대규모 기능 삭제나 전면 재작성을 수행하지 않는다.

## 25. 실행 백로그: 48개 작업 카드

## 26. 바로 착수할 상위 10개 작업의 상세 명세

### 작업 1 — 신규 일지 경쟁 재현과 보존

**연결:** B03~B05. **주요 위치:** `mcp/tools/mod.rs`, `manager/mod.rs`, `atomic_io.rs`.

**문제:** 이름 선택과 게시가 분리된 경로의 경쟁 가능성. **구현 방향:** 기존 파일을 교체하지 않는 생성 API와 공통 정책. **시험:** AT01, AT04, 서로 다른 프로세스 32개. **금지:** 성공 응답 개수만 세고 본문 보존을 확인하지 않는 종료. **되돌리기:** 이전 파일 읽기 호환을 유지하고 신규 API 적용을 진입점 단위로 전환.

### 작업 2 — 요청 재시도

**연결:** B06. **문제:** 저장은 됐지만 응답이 사라진 호출의 중복 가능성. **구현 방향:** 요청 ID·본문 해시·결과 회수 계약. **시험:** 응답 직전 종료·재시도·캐시 삭제·다른 본문의 같은 키. **금지:** 시간이나 제목만으로 중복 판정. **되돌리기:** 새 키 없는 구 클라이언트 경로를 명시적으로 유지.

### 작업 3 — 저장과 색인 분리

**연결:** B07. **문제:** 성공 단계가 불분명하면 원본이 있는데 사용자가 재작성하거나, 저장 안 됐는데 성공으로 믿을 수 있음. **구현 방향:** 저장 결과와 색인 상태를 별도 필드로 전달. **시험:** DB 쓰기 실패·워처 지연·재색인 성공. **완료:** 앱·MCP가 같은 원본 상태를 표시.

### 작업 4 — 장애 복구 하니스

**연결:** B08. **구현 방향:** 안전한 시험 디렉터리와 지정된 실패 지점에서만 오류 주입. **시험:** 임시 파일·게시·응답·색인 각 단계의 종료. **완료:** 입력 요청 수, 게시 원본 수, 중복 수, 실패 응답, 복구 후 결과를 자동 보고. **금지:** 실제 프로젝트에서 디스크 오류를 재현.

### 작업 5 — 상태 의미 일치

**연결:** B12. **주요 위치:** `verdict`, `acp/journal_gate.rs`, 관련 훅·화면. **구현 방향:** 관측 불가·미기록·기록됨·검증됨의 계약을 테스트 자료로 공유. **시험:** 공동 변경·종료 지연·세션 재개·잘못된 신원. **완료:** 같은 자료에 모든 진입점이 같은 판정.

### 작업 6 — 최신 기록 실험

**연결:** B15~B16. **구현 방향:** 기존 벤치마크를 버리고 새로 만드는 대신 버전·지원 형태·분모·실패 유형을 보강. **시험:** 파일만 바뀌고 일지가 없는 조건, 도구 실패 조건, 실제 기록 성공 조건. **완료:** 성공률과 판정 불가율·중복·비용을 함께 공개.

### 작업 7 — 배포 게이트

**연결:** B31. **주요 위치:** `.github/workflows/ci.yml`, `release.yml`. **구현 방향:** 같은 커밋의 필수 검사와 배포를 연결. **시험:** 실패·취소·검사 없음·다른 커밋 성공·정상 성공. **완료:** 처음 네 조건에서 공개 산출물 생성 또는 승격 차단.

### 작업 8 — 서명 검증

**연결:** B33. **구현 방향:** 산출물의 실제 서명·공증·업데이트 검증 결과를 확인. **시험:** 비밀 누락·잘못된 서명·정상 번들. **완료:** 릴리스 문구가 약속하는 상태가 실제 파일과 일치. **되돌리기:** 실패한 후보는 비공개로 남기고 마지막 정상 업데이트 유지.

## 28. 완료 정의와 재평가 절차

### 28.1 카드 완료 정의

작업은 코드를 작성한 시점이 아니라 다음 조건을 만족할 때 완료다.

- 문제 또는 가설과 실제 변경 범위가 연결돼 있다.
- 변경 전 실패 또는 개선 필요성을 설명할 근거가 있다.

## 29. 실행 운영과 의사결정

### 29.1 주간 검토 의제

주간 검토는 네 질문으로 제한한다. “새롭게 확인된 사용자 문제는 무엇인가?”, “상위 위험의 증거가 바뀌었나?”, “이번 주 완료한 계약은 무엇인가?”, “다음 단계로 넘어갈 근거가 충분한가?”이다. 커밋 수와 일지 수는 진행 맥락으로만 사용한다.

### 29.2 역할

제품 책임자는 지원 범위·사용자 약속·수용 기준을 정한다. 구현 책임자는 계약과 호환성을 구현한다. 검증 책임자는 실패·복구·실제 환경 증거를 확인한다. 한 사람이 여러 역할을 맡더라도 검토 순간과 체크리스트를 분리한다.

### 29.3 결정해야 할 다섯 가지

1. 10점 평가의 첫 공식 지원 조합은 무엇인가?
2. 기록 보존·재시도 계약을 어느 파일 스키마로 표현할 것인가?
3. 사람이 확인한 기록의 정정·편집 정책은 무엇인가?
4. 실제 앱 검증을 수행할 기준 장비와 릴리스 후보 절차는 무엇인가?
5. 사용자 효용을 검증할 첫 프로젝트·과제·참여자는 누구인가?

이 질문에 답하는 데 외부에 배포하거나 사용자 데이터를 수집할 필요는 없다. 먼저 문서와 시험 자료를 구체화하고 실제 실행이 필요한 시점에 해당 범위의 동의를 받는다.

### 29.4 중단 조건

제안한 개선이 실제 문제를 해결하지 않거나 더 큰 복잡성을 만든다면 중단한다. 예를 들어 검색 기준선이 충분한데 새 검색 엔진을 도입하거나, CSS 파싱이 작게 측정됐는데 파일 분리로 성능 향상을 주장하지 않는다. 기각된 가설을 남기는 것도 유효한 완료다.

## 30. 최종 권고

Ocul-PM의 강점은 이미 연결되어 있다. 에이전트가 기록하고, 프로젝트 안에 원본이 남고, 앱이 변경과 계획을 엮어 보여준다. 이 구조를 유지하면서 신뢰를 더할 때 제품의 차별성이 커진다.

10점에 가장 가까운 개발 순서는 **보존 → 의미 → 실측 → 사용성 → 배포 증거**다. 이는 모든 기능을 순서대로 다시 만들라는 뜻이 아니다. 사용자에게 한 핵심 약속의 빈틈을 먼저 닫고, 그 약속이 지켜지는 장면을 반복해서 확인하라는 뜻이다.

가장 먼저 B04의 신규 일지 경쟁 시험, B06의 재시도 계약, B31의 배포 게이트, B15의 최신 실험 설계에 착수하는 것을 권한다. 그 결과를 보고 화면과 기능 투자의 비중을 결정한다.

**이 프로젝트가 10/10을 받는 순간은 기능 목록이 가장 길어졌을 때가 아니라, 사용자가 “지난 작업을 다시 이해할 수 있고, 빠진 것은 빠졌다고 알려주며, 문제가 생겨도 기록을 되찾을 수 있다”고 실제로 확인했을 때다.**

## 부록 D. 보고서 사용 안내

본문의 목표값은 제안이며 기존 달성 수치와 구분한다. 구현 카드에 착수하기 전 기준 커밋 이후 변경을 확인하고, 이미 해결된 항목은 완료 증거를 연결하여 닫는다. 이 보고서의 권고를 적용하기 위해 원본 저장소를 수정한 상태는 아니다.

별도 CSV는 본문 48개 백로그를 필터·정렬하기 위한 보조 자료다. 의존성은 선행 작업 ID를 뜻한다. 상태는 모두 ‘제안’으로 시작한다. 작업 카드의 완료 기준은 CSV의 요약과 본문의 상세 명세를 함께 사용한다.

HTML은 외부 폰트·분석 스크립트·원격 자산 없이 로컬에서 읽을 수 있다. 목차로 이동하고 브라우저의 본문 찾기를 사용할 수 있으며 인쇄용 스타일을 제공한다. 보고서를 공유할 때는 HTML 하나로 본문을 읽을 수 있고, 편집하거나 다른 문서 도구로 옮길 때는 마크다운을 사용한다.

산출물 검증에서는 30개 장·4개 부록·48개 작업·36개 체크 항목·20개 출처, 작업 의존성의 순환 여부, 목차 링크와 표 구조를 확인했다. HTML의 실제 브라우저 화면과 인쇄 결과는 이번 환경의 브라우저 보안 정책 제한으로 시각 검증하지 못했다. PDF 파일을 별도로 생성한 것은 아니며 HTML의 인쇄 버튼은 사용자의 브라우저 인쇄 기능을 연다.
