## 1. 한 줄 요약 (내 입장)

**방향성에는 동의합니다.** 지금 앱은 "사용자가 일일이 changelog 버튼을 눌러 기록"하는 워크플로우 위에 서 있는데, 정작 사용자는 Cursor/Claude Code/Antigravity 같은 외부 에이전트에서 바이브 코딩을 하고 있어서 **기록의 책임자와 작업의 주체가 분리**돼 있는 상태입니다. 외부 에이전트가 자기 작업을 직접 `.oculpm/` 에 기록하게 하고, 앱은 그 기록을 **읽고/검증/시각화** 하는 쪽으로 역할을 옮기는 건 설계상으로도 더 정합적이라고 봅니다.

다만 이 전환은 **앱의 데이터 소스(source of truth)를 SQLite → 파일시스템으로 옮기는 결정**과 같고, 동시에 **신뢰 경계(외부 LLM이 정직하게 기록한다는 가정)** 를 새로 그려야 합니다. 그래서 큰 그림 합의부터 잡고 들어가는 게 좋겠습니다.

## 2. 제안의 강점 (내가 본 것)

1. **목적 정합성** — "AI 시대의 PM" 이라는 컨셉에 부합. 사람이 기록하는 도구가 아니라 AI가 기록한 걸 사람이 검토하는 도구로 자리를 잡음.
2. **마찰 제거** — 지금은 `CodeWorkbench → AiWorkbench → "오늘 변경사항" → Save to Changelog` 라는 다단계가 필요. 외부 에이전트가 직접 기록하면 이 동선이 통째로 사라짐.
3. **에이전트 중립성** — `.oculpm/` 이 단일 진실 저장소가 되면 Cursor/Claude Code/Antigravity 누가 작업했든 결과물이 같은 모양으로 쌓임. 앱은 어느 에이전트에도 락인되지 않음.
4. **휴대성** — `.oculpm/` 을 레포에 커밋하면 PR 리뷰어/팀원도 "이 PR 동안 무슨 작업이 있었는지" 를 git history 와 별개의 시간축으로 볼 수 있음. (이게 의도된 사용인지 아닌지는 아래 Q3 참고)
5. **기존 자산 재활용 가능** — `docs/2026521/` 의 폴더 구조와 파일명 컨벤션이 이미 잘 잡혀 있어서, 그걸 그대로 `.oculpm/` 의 출력 포맷 명세로 못 박을 수 있음.

## 3. 본격적으로 따져봐야 할 쟁점들

### 3.1 신뢰 경계 — "외부 LLM 이 정직하게 기록한다" 가정의 위험

가장 큰 리스크입니다. 외부 LLM 에게 `.oculpm/.../2055_bugs.md` 를 쓰라고 시켜도:

- **누락**: LLM 이 작업을 끝내고 "다 됐어요" 하고 기록은 안 남길 수 있음 (지시 망각).
- **과장/환각**: 실제로는 1 파일만 고쳤는데 "5개 파일을 리팩토링했다" 식으로 부풀려 쓸 수 있음.
- **포맷 이탈**: 템플릿을 미세하게 어김 → 우리 파서가 깨짐.
- **체크박스 자체 체크**: "[ ] 완료 후 체크" 라고 했는데 LLM 이 자신감 과잉으로 미완료 항목도 `[x]` 로 작성.

**제 제안**: `.oculpm/` 의 기록을 **신뢰 가능한 진실** 로 두지 말고, **두 개의 레이어**를 병행하는 게 안전합니다.

- **레이어 A (사실 / Ground Truth)**: 앱이 직접 측정. 파일 워처 + git diff + 해시 비교. **변조 불가능한 객관 데이터.** 현재 `file_changes` 테이블이 이미 이 역할을 함.
- **레이어 B (해석 / Narrative)**: 외부 LLM 이 `.oculpm/` 마크다운에 기록한 "왜/어떻게" 의 서사. 사람이 읽기 위한 설명.

UI 의 Today 화면에서는 두 레이어를 **나란히** 보여주고, 둘이 일치하지 않으면 (예: A 는 7개 파일이 바뀌었다고 하는데 B 는 3개만 언급) **시각적으로 경고**를 띄우는 식. 이러면 LLM 의 누락/환각이 사용자에게 즉시 노출됨.

질문: **이 이중 레이어 구조에 동의하시나요, 아니면 `.oculpm/` 마크다운 한 가지만 진실로 쓰고 싶으신가요?**

### 3.2 JSON vs Markdown — 포맷 선택

장단점을 정리해봤습니다.

| 항목 | Markdown | JSON | **Markdown + Frontmatter (추천)** |
|---|---|---|---|
| LLM 출력 안정성 | 높음 (LLM 의 모국어) | 중간 (따옴표/콤마 누락 빈번) | 높음 |
| 사람이 읽기 | 매우 좋음 | 나쁨 | 매우 좋음 |
| 파서 안정성 | 낮음 (정규식 의존) | 높음 (스키마 검증) | **높음** (frontmatter 는 구조화, 본문은 자유) |
| diff 친화도 | 좋음 | 보통 | 좋음 |
| 기존 `docs/2026521/` 자산 재활용 | 그대로 | 변환 필요 | 그대로 |
| 부분 손상 시 복구 | 가능 | 한 문자 오류로 전체 실패 | 가능 |

**제 추천**: **YAML frontmatter + Markdown 본문** 의 하이브리드. 예시:

```markdown
---
schema_version: 1
type: bug
slug: changelog-export-param-mismatch
status: fixed
difficulty: medium
created_at: 2026-05-22T20:55:00+09:00
agent: claude-code
agent_version: opus-4.7
files_touched:
  - path: src-tauri/src/db.rs
    op: update
  - path: src/features/code/AiWorkbench.tsx
    op: update
related_files_in_oculpm:
  - 20260522/Bugs/2055_bugs.md
---

# Changelog Export 시 파라미터 개수 불일치

## 발생 원인
`Db::list_changelog_entries` 의 SQL 빌더가 ...

## 해결 방법
...
```

**근거**:
- Frontmatter 는 우리 앱이 **빠르고 안정적으로 인덱싱**할 수 있는 메타데이터.
- 본문은 LLM 이 **자연어로 자유롭게** 쓰는 영역.
- 파서가 frontmatter 만 깨져도 본문은 살아남음 (반대도 마찬가지).
- 기존 `docs/2026521/2055_bugs.md` 같은 파일에 frontmatter 만 위에 붙이면 마이그레이션 끝.

질문: **이 방향(Markdown + Frontmatter)으로 갈까요? 아니면 LLM 의 환각/포맷 이탈을 막기 위해 더 강력한 JSON 스키마 검증을 두는 쪽이 좋을까요?**

### 3.3 `.oculpm/` 의 git 정책 — 커밋하나, 무시하나?

이건 **앱의 정체성을 가르는 결정**이라 따로 빼서 논의해야 합니다.

**옵션 A — `.oculpm/` 을 커밋한다 (기본 추천)**
- 장점: PR 리뷰어가 "이 PR 동안 무슨 일이 있었는지" 의 narrative 를 git history 와 별개 차원에서 본다. 팀 단위 도입 시 강력함.
- 단점: 각 커밋의 diff 가 비대해짐. 민감한 정보(API 키, 내부 경로) 가 LLM 의 narrative 에 섞여들 위험.

**옵션 B — `.oculpm/` 을 .gitignore 한다**
- 장점: 개인 노트북에 머무름. 보안 위험 낮음.
- 단점: 팀 협업의 효용이 사라짐. 노트북 옮길 때 동기화 문제.

**옵션 C — 분리 정책 (추천 변형)**
- `.oculpm/index/` (앱이 생성한 ground truth, 해시/타임스탬프) → **gitignore**
- `.oculpm/journal/` (LLM 이 작성한 narrative) → **commit**
- 사용자가 토글 가능하게.

질문: **A/B/C 중 어느 쪽을 기본으로 하시겠어요?** 그리고 **민감 정보 마스킹(예: API 키 패턴 매칭 후 redact)을 앱 레벨에서 강제할까요?**

### 3.4 외부 에이전트 프롬프트 주입 — 어디까지 자동화?

제안하신 "사용자 환경 감지 → `.agent/rules/ocul-pm.md` 자동 작성" 흐름은 강력하지만 함정이 많습니다.

**감지 방법의 한계**:
- Cursor: `.cursor/rules/` 또는 `.cursorrules`
- Claude Code: `CLAUDE.md` (프로젝트 루트) 또는 `~/.claude/CLAUDE.md`
- Antigravity: `.agent/rules/`
- Gemini CLI: `GEMINI.md`
- Pi-agent / 기타: 미정의

→ **레포의 파일 존재 여부만으로는 사용자가 실제로 어떤 에이전트를 쓰는지 100% 알 수 없습니다.** 사용자가 Cursor 와 Claude Code 를 둘 다 쓰면 어떻게 할까요?

**제 제안**: 자동 감지 + 사용자 설정 병행.
- 앱이 알려진 마커 파일들을 스캔해서 "후보" 를 제시.
- 사용자가 **"이 프로젝트에서 활성화할 에이전트"** 를 명시적으로 토글 (다중 선택 가능).
- 토글된 에이전트들에 대해서만 `.oculpm/` 작성 규칙 파일을 동기화.

**프롬프트의 내용은 단일 진실 소스(SSOT)로 관리**:
- `.oculpm/agents/_template.md` 에 마스터 프롬프트.
- 각 에이전트별 어댑터(`.cursor/rules/ocul-pm.md`, `CLAUDE.md` 의 특정 섹션, `.agent/rules/ocul-pm.md`)는 마스터를 참조/포함하는 얇은 shim.
- 앱이 마스터 변경 시 어댑터들을 자동 재생성. (drift 방지)

질문: **어떤 에이전트들을 1차 지원 대상으로 잡을까요?** Claude Code, Cursor, Antigravity, Gemini CLI 4개로 시작하면 충분할지, 더 좁힐지.

### 3.5 트리거 idempotency — "여러번 작동하면 안 된다"

날짜 폴더 자동 생성 트리거의 엣지 케이스:

- 자정 직전(23:59:55)에 앱을 켰는데, 폴더 생성 후 1분도 안 돼서 자정이 넘어감 → 새 폴더?
- 사용자가 여러 윈도우/프로젝트를 동시에 띄움 → race condition.
- 시계가 뒤로 감겼다(NTP 보정) → 과거 날짜 폴더에 다시 쓰기?
- 사용자가 비행기로 시간대 이동 → 같은 "오늘" 이 두 번?

**제 제안**: 트리거 책임을 둘로 분리.

1. **폴더 생성 트리거** = "오늘 첫 기록을 쓰려는 순간" 에만 발화. 앱 부팅과 분리. (Lazy creation)
2. **날짜 결정 기준** = 사용자가 설정에서 "내 작업 일(workday)" 의 타임존을 선택. 디폴트는 OS 로컬 타임존. UI 의 모든 "오늘" 표시도 이 기준으로 통일.
3. **앱은 자체 락 파일(`.oculpm/.lock`)** 로 다중 인스턴스 race 방지.

이건 우리가 이미 `daily_brief` 의 KST/UTC 버그(`docs/2026521/Bugs/2055_bugs.md` 참고) 에서 한 번 데인 영역이니 처음부터 못 박고 가야 합니다.

질문: **"workday timezone" 을 명시적 설정으로 노출하는 것에 동의하시나요?** (저는 강하게 추천)

### 3.7 앱이 생성한 것 vs LLM 이 생성한 것 — 어떻게 구분?

제안에 "구분을 명확히 지어야 함" 이라고 쓰셨는데, 구체적인 방법을 제안드립니다.

**디렉토리 분리** (제 추천):
```
.oculpm/
├── index/                    # 앱 전용 (LLM 이 건드리면 안 됨)
│   ├── projects.json
│   ├── 20260522/
│   │   ├── file_changes.ndjson    # 파일 워처가 append-only 로 기록
│   │   └── snapshot.json          # 자정/세션 종료 시점의 git/hash 상태
│   └── .lock
├── journal/                  # LLM 작성 영역
│   └── 20260522/
│       ├── Bugs/2055_bug_export-param-mismatch.md
│       ├── Features_to_add/2101_feature_chat-quickedit-merge.md
│       └── Errors/2026-05-21-specta-bigint-export.md
├── agents/                   # 에이전트별 규칙 어댑터의 소스
│   └── _template.md
└── config.toml               # 사용자 설정 (timezone, gitignore 정책 등)
```

**프론트매터로 한 번 더 라벨링**: `agent: claude-code` vs `agent: oculpm-watcher`.

**파일시스템 권한/속성** 으로까지 강제할 필요는 없다고 봅니다 (Tauri 가 OS 의 ACL 까지 건드리면 복잡해짐). **디렉토리 + 프론트매터** 컨벤션만으로도 충분.

질문: **이 디렉토리 구조에 동의하시나요?** 특히 `agents/` 폴더를 `.oculpm/` 안에 두는 게 자연스러운지, 아니면 레포 루트로 빼는 게 좋을지.

### 3.8 기존 SQLite 데이터의 마이그레이션 / 공존

현재 앱은 `src-tauri/src/db.rs` + `commands/changelog.rs` 로 SQLite 에 `changelog_entries`, `file_changes`, `files` 등을 쌓고 있습니다. `.oculpm/` 으로 전환 시:

**옵션 A — 완전 대체**: SQLite 의 changelog 관련 테이블을 다 들어내고 파일시스템으로. (가장 깔끔하지만 마이그레이션 부담)

**옵션 B — SQLite = 인덱스, `.oculpm/` = 정전(canonical)**: 파일이 진실, SQLite 는 빠른 검색용 캐시. 앱 시작 시 `.oculpm/journal/**/*.md` 를 스캔해서 SQLite 재구축.

**옵션 C — 병행 운영 기간**: 신규 프로젝트는 `.oculpm/`, 기존 프로젝트는 SQLite 유지하면서 사용자가 마이그레이션 버튼을 누를 때만 변환.

저는 **B + C 의 조합** 을 추천합니다.
- 새 진실은 항상 `.oculpm/` 에 있고,
- SQLite 는 list/filter/검색의 성능을 위해 유지하되 언제든 파일로부터 재생성 가능 (Lossy cache).
- 기존 SQLite-only 프로젝트는 "이 프로젝트를 `.oculpm/` 으로 전환" 버튼.

질문: **이 방향에 동의?** 마이그레이션 시점은 v2.0 같은 메이저 릴리스로 잡는 게 좋을 듯합니다.

### 3.9 프론트엔드 — Overview 와 Today 의 역할 재정의

제안: "Today 를 메인으로". 동의합니다만, **Overview 를 죽이는 건 아쉽다**고 봅니다. 이유:

- **Today** = 오늘 단위의 narrative + 변경 사항 (시간 축, 좁고 깊음).
- **Overview** = 프로젝트 전체의 상태/지표/누적 (구조 축, 넓고 얕음).
- 둘은 보완 관계.

**제 제안**:
- 프로젝트 진입 시 **디폴트 탭을 Today 로 변경** (✅ 제안 그대로).
- Overview 는 두 번째 탭으로 유지하되, "최근 7일 활동 그래프", "미완료 체크박스 모음", "에이전트별 작성 비중" 같은 **집계/메타 뷰** 로 재포지셔닝.
- Today 화면 내부에 **타임라인 뷰** (시간순 카드 스택) 를 메인으로 두고, 우측 사이드에 "오늘 자동 감지된 파일 변경" (레이어 A) 패널을 둠. 두 레이어가 시각적으로 나란히.

질문:
- **Overview 의 재포지셔닝에 동의?** 아니면 정말로 deprecate 할 생각이신가요?
- **Today 의 메인 뷰는 (a) 시간순 타임라인 / (b) 카테고리 그룹(Bug/Feature/Error) / (c) Kanban (todo/doing/done)** 중 어느 쪽이 가장 자연스러울까요?

### 3.10 작은 것들 (코멘트만)

- **버그 템플릿에 난이도 필드 추가**: 현재 기능에만 있고 버그에는 없습니다. 일관성을 위해 버그에도 동일한 5단계 추가 추천.
- **체크박스 의미 명확화**: 외부 LLM 이 자기 작업을 `[x]` 로 마킹하는 건 **자기보고**이므로, 사용자가 별도로 "검증 완료" 마킹을 할 자리(예: `verified_by_user: true` frontmatter 필드)를 두는 게 깔끔.
- **다국어**: 템플릿이 한글인데 영어 LLM 이 영어로 쓰면? → 프롬프트에 "한국어로 쓸 것" 을 명시하거나, 언어를 frontmatter 에 `language: ko` 로 기록.
- **첨부 파일**: 스크린샷/로그 첨부는? `.oculpm/journal/20260522/_attachments/` 같은 서브폴더로 정리.
